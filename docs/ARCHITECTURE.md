# TERRAIN-X Architecture

Single-View Terrain Reconstruction and Disaster Intelligence Platform — SIH26175 (ISRO / Dept. of Space).

## 1. Guiding principle

**The backend + database are the only source of truth.** The frontend renders what the pipeline produced and stored — it never computes, guesses, or hardcodes an elevation, confidence score, or hazard result. Changing a parameter in the UI (e.g. flood water level) always triggers a real backend computation and a new/updated result row; it never just re-skins an existing visualization client-side.

The AI (`ai/`) and geospatial (`geospatial/`) code are Python **libraries**, not separate network services, imported by the worker process. This keeps the MVP a single deployable backend + single worker type, while the module boundary (clean interfaces, no FastAPI imports inside `ai/`/`geospatial/`) means either can be extracted into its own service later (e.g. a GPU-backed inference microservice) without rewriting the pipeline logic.

Because `ai/`, `geospatial/`, and `storage/` live at the repo root as siblings of `backend/` (not inside it), the backend/worker Docker build context is the **repository root**, and the Dockerfile copies all three packages plus `backend/` into the same image (`backend/Dockerfile`, referenced from `docker/docker-compose.yml` with `context: ..`). In dev, each is also bind-mounted individually for hot-reload.

## 3. Core pipeline (per analysis job)

```
uploaded image
  → validation (format, size, corruption check)
  → metadata extraction (EXIF/GeoTIFF tags, existing CRS if any)
  → preprocessing (normalize, tile if large, color correction)
  → monocular depth estimation (ai/) → relative depth map
  → metric calibration against DEM/GCP reference (geospatial/)
  → metric elevation surface
  → DSM generation
  → semantic feature extraction (ai/)
  → uncertainty/confidence estimation (ai/)
  → terrain derivatives (slope, aspect) (geospatial/)
  → disaster analysis (flood/hazard screening) (geospatial/)
  → result persistence (terrain_results, hazard_results)
  → interactive 2D/3D visualization (frontend)
  → measurements / simulation / export (backend + frontend)
```

Every arrow that crosses into `terrain_results`/`hazard_results` is a real computation over the uploaded raster and any supplied DEM/GCP reference data — no step is stubbed with fixed numbers. As of Phase 7, "monocular depth estimation" through "DSM generation" (§3.3, §3.4), "interactive 2D/3D visualization" (§3.5), "semantic feature extraction" (§3.6, real but **class-agnostic** — see below), and part of "measurements" (§3.7 — point elevation, distance, profile, coordinate; not simulation or export) are implemented for real; "uncertainty/confidence estimation," "terrain derivatives," and "disaster analysis" are not yet implemented. **"Semantic feature extraction" here means real class-agnostic region segmentation (MobileSAM), never a supervised land-cover/object classifier** — Phase 6 deliberately does not claim to detect "buildings," "roads," "vegetation," or any other real-world category (§3.6). "Uncertainty/confidence estimation" remains unimplemented in the sense of a genuine per-pixel probabilistic uncertainty map; Phase 6 instead adds honest, clearly-scoped **image-quality indicators** (sharpness/exposure/valid-pixel-ratio) and exposes the model's own **mask-stability** signal where available — neither is described as "confidence" or "accuracy" anywhere (§3.6).

### 3.1 Dataset ingestion (implemented, Phase 1)

The first two pipeline stages — validation and metadata extraction — are implemented synchronously in the request path (`app/services/dataset_ingestion.py`), since they're fast enough not to need the job queue yet. The RQ job execution framework itself was built in Phase 2 (§3.2); real pipeline stages (depth estimation onward, from Phase 3) run inside that same framework.

```
multipart upload
  → Content-Length pre-check against MAX_UPLOAD_SIZE_MB
  → read first chunk, sniff real magic bytes (never trust extension/Content-Type)
      no match → 422, no dataset row ever created
      match    → normalized file_type + server-determined mime_type
  → create `datasets` row (status=uploaded), flush to get its UUID
  → stream remaining chunks to storage at
      projects/{project_id}/datasets/{dataset_id}/original.{ext}
      (enforcing the byte-limit as it writes; abort + delete partial file + roll back row if exceeded)
  → status=validating
  → geospatial.raster_metadata.extract_raster_metadata() opens the file with GDAL
      success → status=valid; width/height/bands/is_georeferenced/crs/bbox populated from
                what GDAL actually reports (crs is None ⇒ is_georeferenced=False, full stop —
                a .tif extension never implies georeferencing on its own)
      RasterValidationError (unreadable/corrupt) → status=invalid, validation_error set
      unexpected error → status=failed, validation_error set, full traceback logged
  → commit; the dataset resource always exists (HTTP 201) once bytes were accepted —
    "invalid"/"failed" are real, persisted outcomes, not HTTP-layer failures
```

A dataset delete removes both the DB row and the stored file; a project delete cascades the DB rows (`ON DELETE CASCADE`) and additionally removes the whole `projects/{project_id}/` storage prefix, since the FK cascade only cleans up the database side.

### 3.2 Analysis job orchestration (implemented, Phase 2)

**Explicit boundary**: Phase 2 builds the execution *framework* — the job model, queueing, worker orchestration, stage/status tracking, failure handling — that future pipeline stages plug into. It does **not** implement monocular depth estimation, DEM/GCP calibration, DSM generation, semantic segmentation, uncertainty maps, slope/aspect, flood simulation, or 3D terrain rendering. Where a future stage would go, Phase 2 instead does genuine, verifiable preparation work (reopening the file, cross-checking metadata, computing real pixel statistics) — never a placeholder that pretends terrain output exists.

**Lifecycle**: an `AnalysisJob` moves through `status`: `queued → running → completed | failed | cancelled`, and independently through `current_stage`: `queued → preparing → validating_input → loading_model → preprocessing → inference → writing_depth → calibrating → writing_metric_elevation → writing_dsm → validating_results → loading_semantic_model → semantic_preprocessing → semantic_inference → writing_semantic → finalizing → completed` (the Phase 2 pipeline had a single generic `executing` stage in this slot; Phase 3 added everything through `writing_depth`; Phase 4 added the four calibration-related stages; Phase 6 added the four semantic-segmentation stages — see §3.3, §3.4, §3.6). The four Phase 4 stages are only entered if a DEM/GCP reference was requested (§3.4); the four Phase 6 stages are only entered if `enable_semantic_segmentation=true` was requested (§3.6) — either or both may be skipped, in which case the job goes straight from `writing_depth` (or, if calibration ran, from `validating_results`) to `finalizing`. `status` is the outcome; `current_stage` is where it got to (a `failed` job's stage shows which stage it failed in, e.g. `validating_input`, not `completed`). The stage vocabulary is a fixed enum, not frontend-supplied strings, precisely so later phases can add new stage values without changing the status model — Postgres enum types are append-only, so old values (like `executing`) are never removed, only added to, keeping old rows readable forever.

**Progress** is never a separately-tracked, driftable number — it's derived at read time from a fixed `STAGE_PROGRESS` mapping (`app/models/analysis_job.py`: queued=0, preparing=5, validating_input=10, loading_model=18, preprocessing=26, inference=36, writing_depth=44, calibrating=50, writing_metric_elevation=56, writing_dsm=60, validating_results=64, loading_semantic_model=70, semantic_preprocessing=76, semantic_inference=88, writing_semantic=94, finalizing=97, completed=100; legacy `executing`=70) keyed off `current_stage`. There is exactly one source of truth for "how far along is this job," and it can't desync from the stage it's actually in. (Phase 6 re-sliced these percentages to make room for its four new stages — existing stage *names* were never renumbered or removed, only the numeric progress values shifted, which is a presentation detail with no effect on any persisted row.)

**Calibration status** and **semantic status** are two further, independent pieces of job state — `calibration_status` (`uncalibrated` / `calibrating` / `calibrated` / `failed`, plus `calibration_metadata` JSONB, Phase 4) and `semantic_status` (`not_requested` / `processing` / `completed` / `failed`, plus `semantic_metadata` JSONB, Phase 6) — deliberately not folded into `status`/`current_stage`, because whether metric calibration or semantic segmentation succeeded is orthogonal to whether the job itself succeeded (§3.4, §3.6 explain why a failed calibration/segmentation attempt never fails the job). The two are also independent of *each other*: a job can request either, both, or neither, and each tracks its own real outcome.

**Creation → enqueue** (`app/services/analysis_jobs.py`):
```
POST .../datasets/{dataset_id}/analysis
  → dataset must have status=valid (else 422)
  → insert AnalysisJob(status=queued), commit
      a partial unique index (ux_analysis_jobs_active_dataset, WHERE status
      IN ('queued','running')) makes "one active job per dataset" a database
      invariant, not just an app-level check — a concurrent duplicate insert
      gets a real IntegrityError, converted to 409
  → enqueue to RQ with job_id == the AnalysisJob's own id (traceable 1:1)
      if enqueue itself fails (e.g. Redis unreachable): the job row is
      immediately flipped to failed with a clear error, rather than left
      "queued" forever with nothing that will ever process it
  → return 201 with the real row (whatever its real status now is)
```

**Worker execution** (`app/services/analysis_execution.py`, run via `app/jobs/tasks.py:run_analysis_job` — RQ calls this synchronously, so it drives the async implementation with `asyncio.run`):
```
load AnalysisJob by id
  → job missing (e.g. its dataset/project was deleted, cascading it away)
      → log and return; nothing to update, nothing to report
claim it atomically: UPDATE ... WHERE status='queued' → status=running,
current_stage=preparing (see the cancellation-race note below)
  → claim fails (rowcount 0, e.g. already cancelled) → log and return, untouched
  → load the Dataset row; gone? → fail: "dataset no longer exists"
  → re-validate the job's stored `parameters` against AnalysisParametersV1
current_stage=validating_input
  → dataset.status must still be valid
  → storage.exists(storage_key)? if not → fail: "stored file is missing"
  → geospatial.raster_metadata.extract_raster_metadata() reopens the file for real
  → cross-check width/height/bands/is_georeferenced against the datasets row
    (a real drift here — the file changed after upload — is a real failure)
  → reject if width/height exceed MAX_DEPTH_INPUT_DIMENSION_PX (cheap check,
    from metadata already in hand — before any pixel data is read)
current_stage=loading_model
  → ai.registry.get_depth_estimator().load() — idempotent; a no-op after the
    first successful load in this worker process (see §3.3)
current_stage=preprocessing
  → geospatial.raster_io.read_raster_array() reads the real pixel data
  → real per-band min/max/mean computed from it (kept from Phase 2)
  → app.services.depth_pipeline.extract_rgb_uint8() applies the Phase 3
    input-eligibility policy (§3.3) — raises a clear error for anything
    that doesn't qualify, never silently reinterprets it
  → re-check job status; cancelled? → stop here, before any model work (§3.3)
current_stage=inference
  → estimator.predict(rgb_array) — the real, only AI/model step in this
    pipeline (§3.3)
  → re-check job status; cancelled? → stop here, before persisting anything
current_stage=writing_depth
  → geospatial.raster_io.write_single_band_float32() writes the real
    prediction to storage; a real AnalysisArtifact row is created pointing
    at it (§3.3) — on write failure, any partial file is deleted before
    re-raising as a failure
  → if the job's parameters named NO dem_reference_dataset_id/
    gcp_reference_dataset_id: skip straight to finalizing below — Phase 4's
    stages are opt-in, never attempted implicitly (§3.4)
current_stage=calibrating   [only if a reference was requested]
  → app.services.calibration_pipeline.run_calibration() — real DEM/GCP
    sampling, robust fit, validation metrics (§3.4); NEVER raises — always
    returns a CalibrationOutcome, persisted to calibration_status/
    calibration_metadata immediately
  → outcome.status != calibrated (i.e. FAILED)? → skip straight to
    finalizing; the job still completes with its relative_depth artifact
current_stage=writing_metric_elevation   [only if calibrated]
  → write the real Z = a*D + b array to metric_elevation.tif (same CRS/
    transform as the source), create the metric_elevation AnalysisArtifact
current_stage=writing_dsm   [only if calibrated]
  → write the same calibrated array to dsm.tif, create the dsm
    AnalysisArtifact referencing metric_elevation's artifact ID (§3.4)
current_stage=validating_results   [only if calibrated]
  → reopen both just-written files with rasterio and confirm real
    count/dtype/dimensions — a genuine re-verification, not a no-op stage
  → if the job's parameters did NOT request enable_semantic_segmentation:
    skip straight to finalizing below — Phase 6's stages are opt-in,
    never attempted implicitly (§3.6)
current_stage=loading_semantic_model   [only if requested]
  → ai.registry.get_semantic_estimator().load() — a second, independent
    process-local singleton from the depth estimator (§3.6)
current_stage=semantic_preprocessing   [only if requested]
  → real, documented memory-safety downsample if the source exceeds
    MAX_SEMANTIC_INPUT_DIMENSION_PX (a size bound, not a speed
    optimization — measured real inference time was roughly constant
    across tested resolutions, §3.6)
  → re-check job status; cancelled? → stop here, before any model work
current_stage=semantic_inference   [only if requested]
  → app.services.semantic_pipeline.run_semantic_segmentation() — real
    MobileSAM automatic mask generation (§3.6); NEVER raises — always
    returns a SemanticOutcome, persisted to semantic_status/
    semantic_metadata immediately
  → outcome.status != completed (i.e. FAILED)? → skip straight to
    finalizing; the job still completes with its relative_depth (and, if
    requested, calibrated) result
  → re-check job status; cancelled? → stop here, before persisting
    anything (the underlying model call itself cannot be preempted once
    started — same documented limitation as Phase 3's depth inference)
current_stage=writing_semantic   [only if segmentation completed]
  → map the label map back to source resolution via NEAREST-neighbor
    only if it was downsampled above (never bilinear/bicubic — region
    IDs are categorical, not interpolatable)
  → geospatial.raster_io.write_single_band_categorical() writes the real
    label map to storage; a real AnalysisArtifact
    (artifact_type="semantic_segmentation") row is created pointing at
    it, with full provenance back to the source dataset and the depth
    artifact of this same job (§3.6)
current_stage=finalizing
  → build execution_summary (structural re-validation info + a depth_estimation
    sub-object: model name/revision/device/inference_seconds/output dims/
    artifact_id, plus — from Phase 6, computed unconditionally for every
    job regardless of whether segmentation was requested — an
    image_quality sub-object: real sharpness/exposure/luminance/
    valid-pixel statistics over the source RGB array, §3.6), commit
status=completed, current_stage=completed
```
Any `AnalysisExecutionError` raised along the way (each with a message safe to show the user) or any other exception (logged with a full traceback server-side, reported to the user as a generic "An internal error occurred...") is caught once at the top level and turns into `status=failed` + `error_message` + `completed_at` — a job is never left stuck `running` because of a handled failure. A `StaleDataError` (the job's row disappeared mid-execution — e.g. its project/dataset was deleted concurrently, cascading the job away) is handled separately: there's no row left to mark failed, so the handler just rolls back and logs a warning instead of trying to write to a row that no longer exists.

**Cancellation** is intentionally scoped to `queued` jobs only — there is no way to safely preempt a job the worker has already started under this RQ setup (real model inference in particular cannot be interrupted mid-forward-pass). The status flip is a single atomic, conditional `UPDATE ... WHERE status='queued'` (not a read-then-write), so a worker racing to pick up the same job at the same instant can't have its result silently clobbered by the cancel request, and the cancel request can't be silently clobbered by the worker either — whichever operation's `WHERE` clause matches first wins, and the loser gets a clear 409 (for cancel) or simply doesn't claim the job (for the worker). This same atomic-claim pattern is what the worker uses to pick up a job in the first place (see the pseudocode above) — an earlier version used a non-atomic read-then-write here, which was a genuine lost-update race (a concurrent cancel could be silently overwritten back to `running`); fixed by making the claim itself the same kind of conditional UPDATE. Two additional defensive checks — real DB re-reads, not trusting the in-memory object — sit immediately before `inference` and immediately after it (before `writing_depth`), so that even though today's API can't reach a claimed job to cancel it, the pipeline itself never depends on that being true.

**Execution metadata vs. scientific output**: a completed job's `execution_summary` (JSONB on `analysis_jobs`) holds what was verified/computed about the *job's own run* — reopened-file confirmation, structural metadata, band statistics, and (from Phase 3) which model ran, on what device, for how long, producing an artifact of what ID. It is deliberately kept separate from `analysis_artifacts`, the table for real scientific/geospatial output files (from Phase 3: the relative-depth raster; from Phase 4: metric elevation and DSM rasters, see §3.4), and separate again from `calibration_status`/`calibration_metadata` (a third, independent piece of job state — see §3.4 for why calibration outcome is tracked apart from both). Conflating "we checked this" / "we produced this" with "here is a calibrated scientific result" would misrepresent what actually happened — see §3.3 for why the depth output specifically is never described as elevation, and §3.4 for the same rule applied to calibrated output.

**Real-time updates**: the frontend polls `GET .../analysis` at a configurable interval (`VITE_ANALYSIS_POLL_INTERVAL_MS`) only while a job is `queued`/`running`, stopping the instant it sees a terminal status. The service layer has no polling-specific code baked into it — it's a plain REST resource — so swapping polling for WebSockets/SSE later is a frontend-only change.

### 3.3 Monocular depth estimation (implemented, Phase 3)

**Model card**:
| | |
|---|---|
| Model | Depth Anything V2 — Small |
| Hugging Face repo | `depth-anything/Depth-Anything-V2-Small-hf` |
| Source | https://huggingface.co/depth-anything/Depth-Anything-V2-Small-hf |
| Project | https://depth-anything-v2.github.io/ |
| License | Apache-2.0 (the Small checkpoint specifically — V2's Base/Large checkpoints are CC-BY-NC-4.0 and are deliberately not used here, to keep dependencies unambiguously permissive) |
| Architecture | DPT (dense prediction transformer) head over a small DINOv2 backbone |
| Loaded via | `transformers` (`AutoImageProcessor` + `AutoModelForDepthEstimation`), not the original repo's custom code |
| Revision | pinned in `ai/depth_anything.py::MODEL_REVISION` (currently `"main"` — operators deploying to production should pin an exact commit SHA there for full reproducibility, and re-check the model card's license terms if they ever change it) |

**Why this model**: actively maintained, a small (~99 MB) CPU-friendly variant exists (this environment has no NVIDIA GPU), it's loadable through the standard `transformers` API rather than bespoke inference code, and its Small checkpoint's license is unambiguous. This is a practical, documented choice — not a claim of state-of-the-art accuracy, which hasn't been benchmarked here.

**Device selection** (`ai/device.py::select_device`): returns `"cuda"` only if `torch.cuda.is_available()` genuinely reports one at runtime; otherwise `"cpu"`. Never assumes a GPU, never requires CUDA — no CUDA-specific packages are installed (see §4.7). The selected device is recorded in every job's `execution_summary` and every artifact's `artifact_metadata`.

**Model loading & cache** (`ai/registry.py`, `ai/depth_anything.py`): `get_depth_estimator()` is a process-local `lru_cache(maxsize=1)` singleton — the RQ worker processes one job at a time in one long-lived process, so the (large) model is constructed at most once per worker process, and `DepthEstimator.load()` is safe to call unconditionally at the start of every job (it no-ops once `self._model is not None`). The first `load()` call in a fresh environment downloads weights from the Hugging Face Hub — this needs outbound network access; failure raises `ModelLoadError`, which the pipeline turns into a real `failed` job with a clear message, never a silently-stuck one. Downloaded weights are cached under `HF_HOME=/app/storage/model_cache`, which is the same persistent bind-mount used for dataset storage (`../storage` on the host) — so the cache survives container restarts/recreation, and subsequent jobs (even in a freshly recreated worker container) load from local disk.

**Input eligibility policy** (`app/services/depth_pipeline.py::extract_rgb_uint8`) — deliberately conservative: reject rather than scientifically misrepresent an input.
| Input | Bands | Outcome |
|---|---|---|
| JPEG/TIFF/GeoTIFF | 3 (RGB) | accepted as-is |
| PNG | 3 (RGB) | accepted as-is |
| PNG | 4 (RGBA) | alpha dropped, remaining 3 used — alpha carries no radiometric information, so this isn't a scientific judgment call |
| any | 1 (grayscale) | rejected |
| TIFF/GeoTIFF | 4+ | rejected — a 4th band on a TIFF could be alpha or genuine spectral data, and there's no reliable way to tell which from metadata alone, so it's rejected rather than guessed at |
| any | any non-`uint8` dtype (e.g. 16-bit, float) | rejected — no implicit rescaling; a real normalization scheme for higher-bit-depth remote-sensing products is future work, not a silent guess |
| any | width or height > `MAX_DEPTH_INPUT_DIMENSION_PX` (default 4096) | rejected before any pixel data is read, bounding memory use for large remote-sensing imagery |

A rejection here fails the **job**, not the dataset — the dataset itself is a perfectly valid raster (Phase 1 already marked it `valid`); it's simply not eligible for *this* pipeline stage. This is exactly the same principle as Phase 2's "invalid dataset can't be analyzed" check, one level more specific.

**Preprocessing & inference** (`ai/depth_anything.py::DepthAnythingV2Estimator.predict`): the accepted `(H, W, 3)` uint8 array becomes a `PIL.Image`, run through the model's own `AutoImageProcessor` (which resizes/normalizes to the model's expected input size — recorded as `model_input_width`/`model_input_height`), then a real forward pass under `torch.inference_mode()` (no gradients computed — this is inference, not training). The raw model output is bicubically resized back to the *source* image's resolution before being returned, so every output pixel corresponds 1:1 with a source pixel — `output_width`/`output_height` always equal the source dimensions, never the model's internal working resolution. Wall-clock inference time is measured with `time.monotonic()` around the forward pass and persisted verbatim (`inference_seconds`) — never claimed to be faster than measured, and no claim of real-time performance is made anywhere.

**Output semantics — read this before using the output for anything**: the model produces **relative, unitless, *inverse* depth** ("disparity-like"): **larger values mean closer to the camera, smaller values mean farther away**. This is the model's native training convention and is never inverted or rescaled here. The full, real prediction array is written out as-is — never only an 8-bit visualization, which would destroy scientific information. This is monocular relative depth: it has **scale ambiguity** (no absolute unit is recoverable from a single image without external calibration — that's Phase 4+), it was trained predominantly on ground-level/general photographic scenes rather than nadir remote-sensing imagery (a real domain mismatch worth being skeptical of for aerial/satellite input), and it can produce artifacts on textureless regions, reflective surfaces, or scenes far outside its training distribution. **It must never be labeled or treated as "elevation," "meters above sea level," "DSM," or "terrain elevation"** — those require the calibration step this phase deliberately does not implement.

**Artifact** (`app/services/analysis_execution.py`, `geospatial/raster_io.py::write_single_band_float32`): a single-band, float32 GeoTIFF at `projects/{project_id}/analysis/{job_id}/depth.tif`. If the source dataset was genuinely georeferenced, the output carries the *same* CRS and transform (the model's resize-back-to-source-resolution step keeps pixel correspondence valid, so this is a legitimate carry-over, not a fabrication); if the source was not georeferenced, the output has no CRS either — georeferencing is never invented. `AnalysisArtifact.artifact_metadata` records: model name/revision/source/license, device, source dataset ID, source and output dimensions, model input dimensions, inference time, real `depth_min`/`depth_max`/`depth_mean` computed from the actual array, dtype, georeferencing state/CRS, and the value-semantics sentence above verbatim (so a consumer reading only the artifact metadata, without this document, still gets the calibration disclaimer). A write failure deletes any partial output file before the job is marked `failed`.

### 3.4 Metric calibration + DSM generation (implemented, Phase 4)

**The critical scientific rule this phase exists to enforce**: Phase 3's relative depth is *not* elevation, and never becomes elevation just because a job "ran." Turning it into metric elevation requires a real, independent elevation reference (a DEM raster, or surveyed Ground Control Points) — without one, output stays uncalibrated forever; nothing here ever invents a scale, assumes "1 depth unit = 1 meter," or fabricates a CRS/geolocation for a non-georeferenced input.

**Why an affine model** (`geospatial/calibration.py` module docstring has the full derivation): the calibration model is `Z_metric = a * D_relative + b`. This is the mathematically minimal model consistent with what Depth Anything V2 actually outputs — an unknown, roughly-monotonic rescaling of true depth with no known absolute scale or offset (§3.3). Two degrees of freedom (a scale, an offset) is exactly what's needed to recover that from paired `(relative_depth, real_elevation)` observations; a higher-order (e.g. polynomial) fit would not be justified by the model's actual output semantics, would be far more sensitive to reference-sample noise, and would misrepresent a single-view estimate as a more sophisticated calibration than it is. Where the true relationship deviates from affine (e.g. monocular depth degrading on distant/textureless regions), that shows up honestly as larger residuals — never as license to add free parameters until a fit "looks better."

**Reference datasets** (`app/models/dataset.py::DatasetRole`): a DEM or GCP reference is just a `Dataset` row with `role` set to `dem_reference` or `gcp_reference` instead of the Phase 1 default `source_image` — no parallel schema, no separate ingestion table. A DEM reference reuses the exact same raster ingestion path as a source image (`app/services/dataset_ingestion.py`), with one extra rule: it must be georeferenced, or it's marked `invalid` at upload time with a clear reason (a DEM with no CRS can never be aligned to a source image). A GCP reference is a CSV (`app/services/gcp_ingestion.py`) — a genuinely different ingestion path, since a CSV isn't a raster — with a required `x,y,z` header (case-insensitive; extra columns ignored), validated row-by-row (non-numeric values rejected with the exact row number), and a caller-declared CRS (`gcp_crs`) for the `(x, y)` columns: a CSV carries no CRS of its own, so one is never assumed. Both paths reject a reference with too few points/samples to be useful (`MIN_GCP_POINTS`, checked at upload; `MIN_CALIBRATION_SAMPLES`, checked at calibration time after real filtering) and record a real `validation_error`, exactly like any other invalid Phase 1 dataset.

**Attaching a reference to a job**: `AnalysisParametersV1` gained two optional fields, `dem_reference_dataset_id`/`gcp_reference_dataset_id` (at most one may be set — the other combination is rejected by a Pydantic model validator, 422). This deliberately reuses job creation as the single place calibration is both configured and started, rather than a separate stateful "attach, then start" workflow: the whole pipeline (depth → calibration → DSM) is one job, one row, one real execution. Omitting both fields reproduces Phase 3 exactly — `calibration_status` stays `uncalibrated`, no calibration stage ever runs. `app/services/analysis_jobs.py::_validate_reference_dataset` checks existence/role/status at job-creation time (fast 422 feedback); the worker re-validates the same three things again at execution time (`calibration_pipeline.py::_load_reference_dataset`) since time passes between creation and execution and the reference could have been deleted or changed — the same "never trust a stale read" principle Phase 2/3 apply to the source dataset itself.

**Alignment — CRS-aware, never index-matched** (`geospatial/calibration.py::sample_dem_pairs`/`sample_gcp_pairs`): a DEM or GCP reference is never assumed to share the source image's CRS. For a DEM: a uniform grid of source-raster pixel coordinates (stride chosen so the candidate count is close to `CALIBRATION_MAX_SAMPLES` — deterministic and spatially even, not random) is converted to real map coordinates via the source's own affine transform, reprojected into the DEM's CRS with `rasterio.warp.transform` only if the two CRSs actually differ, checked against the DEM's real bounds, and then read with `rasterio.DatasetReader.sample()` — point sampling, so an arbitrarily large DEM is never loaded fully into memory. For GCPs: each point's `(x, y)` is reprojected from its declared `gcp_crs` into the source image's CRS, converted to a pixel index via the source transform's inverse, and rejected if that pixel falls outside the source raster (nearest-pixel indexing — a documented simplification, no sub-pixel interpolation). In both paths, every candidate is checked for NaN/Inf/DEM-NoData/out-of-bounds and dropped if invalid — real counts (`total_candidates`, `valid_count`) are always recorded, so a rejected point is counted, never silently disappeared.

**Robust fitting** (`geospatial/calibration.py::fit_robust_affine`): an OLS affine fit (`numpy.polyfit`, degree 1) refined by iterative sigma-clipping — fit, compute residuals, drop points whose residual exceeds `CALIBRATION_OUTLIER_SIGMA` standard deviations, refit on the remainder, repeat until convergence or `CALIBRATION_MAX_ITERATIONS`. This is a standard, dependency-free robust-regression technique (a hard-weight instance of IRLS), explicitly permitted as this phase's alternative to RANSAC — deterministic, and needs no random sampling/consensus parameters beyond one threshold. Raises `DegenerateCalibrationError` if the relative-depth samples have near-zero variance (no scale is determinable from constant input) or if too few inliers remain to keep fitting — always caught and recorded as `calibration_status=failed`, never a fabricated fit.

**Validation metrics** (`geospatial/calibration.py::compute_validation_metrics`): real residuals (`predicted - reference`) over the final inlier set — MAE, RMSE, bias (signed mean residual), min/max residual, plus sample/inlier/outlier counts. Never called an "accuracy percentage," and no single confidence number is invented. These are **in-sample** statistics over the fit's own **inliers** (the persisted key is kept for compatibility, with `validation_metrics_scope = "in_sample_inliers"` beside it). They are optimistic twice over: they are measured on the training data and exclude the samples the fit rejected.

**Calibration quality gate (P1-2)** (`geospatial/calibration.py`, "P1-2: calibration quality gate" section; orchestrated by `calibration_pipeline.run_calibration`). A fit alone never makes a calibration `CALIBRATED`, because `fit_robust_affine` returns some line for any input with depth variance. The gate never changes the fit: the production `a`/`b` are still one `fit_robust_affine` over all valid samples, bit-identical to before. Three criteria decide:

- **G0: validation feasibility.** The held-out procedure must be possible. It is not when there are fewer than 2 non-empty validation groups, when the reference elevations have (near-)zero variance (the mean baseline and skill are then undefined), or when a training fold cannot be fitted (e.g. zero depth variance). This is a precondition, not a threshold. When G0 fails, G2 is recorded as `not_evaluated`, never as passed.
- **G1: expected scale sign.** `scale_a * EXPECTED_SCALE_SIGN` must be > 0, with `EXPECTED_SCALE_SIGN = +1`. This is **not** a universal rule about monocular depth. It follows from the current estimator's declared convention (larger relative depth = closer, §3.3) and from the calibration geometry (only map-projected, overhead sources are accepted; looking down, closer means higher). The relative-terrain mesh already assumes the same direction. A negative fitted scale would produce an inverted surface.
- **G2: held-out skill.** `1 - SSE_cv / SSE_baseline_cv` must be > `CALIBRATION_MIN_CV_SKILL` (default `0.0`). The baseline predicts each training fold's mean reference elevation, i.e. "calibration that ignores depth". Zero is the skill score's natural reference point, not a tuned value. It means only that depth predicted held-out reference elevations better than ignoring depth. **It is not an accuracy guarantee.**

Cross-validation reuses `fit_robust_affine`, sigma-clipping included, independently in each training fold. The held-out side is never clipped, so every held-out sample is scored.
- **DEM path:** leave-one-spatial-block-out over `CALIBRATION_CV_BLOCKS_PER_SIDE`² (default 4×4) contiguous source-image blocks. A random split would leak each held-out sample's spatially autocorrelated neighbours into training and just reproduce in-sample R².
- **GCP path:** leave-one-out, since each GCP is an independent surveyed point. With the minimum 3 GCPs each fold is a two-point line, so a small-n pass is weak evidence. `fold_count` and `effective_sample_count` make that visible.
- **Effective sample count:** DEM sampling records the DEM cell behind each sample (the same `rowcol` mapping `dem.sample()` uses) and reports the number of **distinct** DEM cells as `effective_sample_count`. A DEM coarser than the sampling stride makes many samples read one cell, and those are not independent observations.

In-sample R², Pearson r and Spearman ρ (numpy-only, tie-averaged ranks), plus all-valid-sample MAE/RMSE/bias, are persisted in `fit_diagnostics` as **reporting-only** diagnostics. None of them gates: in-sample R² rewards any chance fit on the data it scores, and any correlation cut-off would be arbitrary. `CALIBRATION_MIN_CV_SKILL`, `CALIBRATION_CV_BLOCKS_PER_SIDE` and `CALIBRATION_QUALITY_POLICY_VERSION` are **engineering acceptance-policy settings, not empirically validated accuracy standards**. No value was derived from any dataset, GAMUS included. The applied policy, with its own statement to that effect, is persisted in `calibration_metadata.quality_gate.policy` on every result, so each decision remains reproducible if defaults change.

A gate failure uses the existing `CalibrationStatus.FAILED` path; no new enum value or migration is needed. `calibration_metadata` keeps every diagnostic plus `quality_gate` and a human-readable `error` naming each failed criterion with its real values. No `metric_elevation`/`dsm` is written, the job still completes, and the terrain falls back to the job's `relative_depth` exactly as for any other calibration failure (§3.10). The single-tile GAMUS experiment (global fit R² 0.005, fitted scale −3.67) is evidence that the generic model *can* produce such a fit on overhead imagery. It is not a source of any threshold.

**Orchestration** (`app/services/calibration_pipeline.py::run_calibration`) — deliberately never raises. Every anticipated failure (non-georeferenced source, reference gone/wrong-role/invalid CRS, insufficient valid samples, degenerate fit, a quality-gate rejection, an unexpected internal error) becomes a real `CalibrationOutcome(status=FAILED, metadata={"error": ...})`; only a genuine full success returns `CALIBRATED` with the fitted array and full metadata. This means a failed calibration attempt **never fails the analysis job** — the relative-depth artifact from Phase 3 already exists and is a valid, useful result on its own; only the calibration-specific outputs are absent.

**Metric elevation + DSM artifacts** (`app/services/analysis_execution.py`): on `CALIBRATED`, the fitted `Z = a*D + b` array is written twice — once as a `metric_elevation` `AnalysisArtifact` and once (numerically identical in this phase — see limitations below) as a `dsm` artifact — both real single-band float32 GeoTIFFs carrying the *source's* CRS/transform/dimensions exactly (`geospatial/raster_io.write_single_band_float32`), never a different or invented georeferencing. Both are re-opened with rasterio immediately after writing (`validating_results` stage) to confirm real count/dtype/dimensions before the job is allowed to reach `finalizing`. Full provenance is reconstructable two ways: from each artifact's own `artifact_metadata` (`dsm.metric_elevation_artifact_id` → `metric_elevation.depth_artifact_id` → the `relative_depth` artifact → `source_dataset_id`), and from the job's own `calibration_metadata` (which also carries `metric_elevation_artifact_id`/`dsm_artifact_id` plus the reference dataset ID used).

**The georeferencing rule, concretely enforced**: `run_calibration` checks `source_crs is None or source_transform is None` as its very first step and returns `FAILED` immediately with an explicit reason — a non-georeferenced source image never reaches sampling, never gets a fabricated EPSG code, and never produces a "metric spatial DSM." This is checked before any reference dataset is even loaded.

**Configuration** (`app/core/config.py`): `CALIBRATION_MAX_SAMPLES` (default 2000, DEM grid-sampling density), `MIN_CALIBRATION_SAMPLES` (default 3, minimum valid pairs after filtering before calibration is declared impossible), `CALIBRATION_OUTLIER_SIGMA` (default 2.5), `CALIBRATION_MAX_ITERATIONS` (default 5), `MIN_GCP_POINTS` (default 3, checked at GCP CSV upload time), `CALIBRATION_MIN_CV_SKILL` (default 0.0), `CALIBRATION_CV_BLOCKS_PER_SIDE` (default 4) and `CALIBRATION_QUALITY_POLICY_VERSION` (default `"v1"`). The last three are quality-gate policy settings (see above), not accuracy standards.

**Scientific limitations (read before using calibrated output for anything)**:
- **Scale ambiguity remains partially unresolved by design**: the affine fit recovers *a* consistent scale/offset for the reference data actually supplied, not a universally "correct" one — a different DEM/GCP set covering the same scene could yield a measurably different `a`/`b`. The validation metrics describe fit quality against the reference used, not absolute truth.
- **No terrain/object-top separation**: neither DEM nor GCP calibration can tell a rooftop, treetop, or the ground beneath them apart in a single monocular image — the resulting "metric elevation"/DSM is a calibrated version of whatever surface the depth model saw, not a bare-earth terrain model. This is stated verbatim in every calibrated artifact's own metadata, not just here.
- **The Phase 4 DSM is not yet a real DSM-specific product**: it is numerically identical to the metric elevation artifact — no hydro-flattening, void-filling, or terrain/surface separation has been applied. The name reflects the pipeline stage's intended eventual role, not additional processing performed so far. Read `dsm` as a **calibrated monocular surface-elevation estimate**, not a photogrammetric or LiDAR DSM. P1-3 (§3.12) derives the separate `dtm`/`ndsm` *estimates* from it and leaves its values and meaning unchanged.
- **Nearest-pixel GCP correspondence**: a GCP is matched to the depth array via `floor()` pixel indexing, not bilinear/sub-pixel interpolation — a documented simplification that adds a small, unquantified positional error especially at coarse source resolutions.
- **Never claim more than measured**: nothing in this phase's code or output may describe a result as "100% accurate," "meter-level accuracy," or "survey-grade" — those are claims about real-world validation this phase has not performed. The only accuracy language that appears anywhere is the actual computed MAE/RMSE/bias/residual range against the specific reference used.

### 3.5 Terrain/GIS visualization workspace (implemented, Phase 5)

**What this phase adds, and what it deliberately doesn't**: a real 2D (Leaflet) and 3D (Three.js) viewer over the actual Phase 3/4 artifacts (relative depth, metric elevation, DSM) and the source imagery — read-only presentation of data that already exists, with **no new database table and no migration** (`app/schemas/visualization.py`'s response models are assembled entirely from existing `Dataset`/`AnalysisJob`/`AnalysisArtifact` rows plus on-demand raster reads). It does not add measurements, semantic layers, uncertainty visualization, or hazard overlays — those remain later phases.

**API surface** (`app/api/v1/endpoints/visualization.py`), following the project's existing nested-ownership route convention rather than the flat `/api/visualization/...` shape a generic spec might suggest:
```
GET .../projects/{project_id}/datasets/{dataset_id}/visualization/context    real layer/terrain availability for one dataset
GET .../projects/{project_id}/datasets/{dataset_id}/visualization/preview    PNG of the raw source file
GET .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/visualization/metadata        real raster statistics
GET .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/visualization/preview         PNG (colorized for scientific rasters)
GET .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/visualization/window          PNG of a real pixel sub-region
GET .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/visualization/value           real value at one pixel (cursor inspection)
GET .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/visualization/terrain/metadata   real terrain-grid metadata
GET .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/visualization/terrain/grid       binary Float32 height grid
```
Every route enforces the same ownership chain as the existing dataset/analysis routes (project -> dataset, or project -> job -> artifact), via two new shared dependencies added to `app/api/deps.py` (`get_owned_analysis_job`, `get_owned_artifact`) mirroring `analysis.py`'s own private helpers — `analysis.py` itself was left untouched rather than refactored to share them, per the "don't rewrite working Phase 0-4 systems unnecessarily" rule.

**Visualization context** (`app/services/visualization.py::build_visualization_context`): looks up the dataset's most recently **completed** `AnalysisJob` (not every historical job — the current, real state of the dataset) and reports four layers — `rgb` (the dataset's own source file, not an `AnalysisArtifact`), `relative_depth`, `metric_elevation`, `dsm` — each `available: true` with real fields, or `available: false` with a real `unavailable_reason` string (never a disabled placeholder pretending data exists). If calibration failed or hasn't run, `metric_elevation`/`dsm` are `unavailable` with the actual `calibration_metadata.error` quoted, exactly per this phase's requirement that a failed calibration never be presented as available metric elevation. `terrain.available` is `true` only when a real `dsm` artifact exists. Width/height/min/max are read from each artifact's own persisted `artifact_metadata` where present (Phase 3/4 already computed and stored these — no need to reopen the file); where absent (Phase 4's `dsm` artifact didn't originally persist elevation min/max — a real gap this phase fixed going forward in `analysis_execution.py`, plus a live fallback in `_artifact_layer` that computes the real statistic on demand for any artifact, old or new, that lacks it) the real file is opened and the actual statistic computed, never borrowed from a sibling artifact or fabricated.

**Raster statistics and previews** (`geospatial/raster_preview.py`): `compute_raster_statistics` reads real structural metadata plus a real finite-value min/max for band 1 — computed from a decimated (`out_shape`, GDAL-level) read when the raster exceeds a configurable sample dimension, honestly flagged `stats_sampled=True` rather than silently presented as full-resolution. `generate_preview_png`/`generate_window_png` render either true-color passthrough (3/4-band uint8, alpha dropped) or, for a single-band continuous scientific raster, a fixed 8-stop hand-picked color ramp (a viridis-like approximation — not a matplotlib dependency) normalized by the raster's own real finite min/max; NoData/NaN/Inf pixels get `alpha=0` (fully transparent), never a fabricated color or a silent 0. Both are presentation derivatives only — generated on demand, never persisted, never fed back into any pipeline stage; the original GeoTIFF (opened read-only) remains the sole scientific artifact. `sample_pixel_value` supports real cursor inspection (Part 25): a 1x1 windowed read of the actual stored value at one pixel, `None` for out-of-bounds or NoData/NaN/Inf (rendered by the frontend as "No data," never coerced to 0).

**Terrain height-grid extraction** (`geospatial/terrain_grid.py::extract_terrain_grid`): reads band 1 of a real DSM artifact via a decimated, block-averaged read bounded by `MAX_TERRAIN_DIMENSION` (default 256 — deliberately small, since it becomes `width * height` real Three.js vertices rendered client-side) — this is real, deterministic downsampling (uniform decimation, not random or cropped), and `source_width`/`source_height` in the response always report the DSM's true original dimensions so the frontend never mistakes the downsampled grid for the full raster. NoData/invalid cells are encoded as `NaN` in the binary payload, never `0` — a fabricated "sea level" would be scientifically wrong for a terrain surface.

**CRS handling for the local 3D coordinate frame** — three real cases, never guessed:
- **Not georeferenced**: `local_crs=None`, `cell_size=(1, 1)`, `origin=(0, 0)` — the grid is used directly as pixel coordinates. The frontend labels this explicitly ("Local coordinates — not georeferenced.").
- **Georeferenced, projected CRS** (e.g. the UTM CRS every test fixture in this project uses): the *actual* affine transform of the (already-decimated) grid is used directly — `origin_x`/`origin_y` is that transform's real top-left map coordinate, `cell_size_x`/`cell_size_y` its real (signed) pixel size. The frontend computes each vertex's local position as `(col + 0.5) * cell_size_x`, `(row + 0.5) * cell_size_y` — the centre of grid cell (row, col), in a local frame whose (0, 0) is the grid transform's origin corner, so `map = origin + local` (D1, see docs/D1_3D_HALF_CELL_GEOREFERENCING_FIX.md). Small numbers (grid extent, not raw UTM-scale coordinates).
- **Georeferenced, geographic CRS** (plain lat/lon): standard UTM-zone selection (`floor((lon+180)/6) + 1`, hemisphere from latitude — a well-defined rule, not a coordinate approximation) picks a real local projected CRS, and `rasterio.warp.reproject` — real GDAL/PROJ, never an ad-hoc degree-to-meter multiplication — reprojects the small (already-decimated) grid into it before the same origin/cell-size treatment above applies. **This path has less real-world exercise in this project's own test fixtures than the projected-CRS path** (every DEM/GCP fixture used elsewhere in this repo is already in a projected UTM CRS) — flagged honestly here as a known lighter-tested code path, not a limitation of the approach itself.

**2D map view** (`frontend/src/components/terrain/MapView2D.tsx`): a real Leaflet map. For a georeferenced dataset, the backend additionally reprojects the dataset's real bounds to EPSG:4326 (`app/services/visualization.py::_dataset_bbox_wgs84`, again via `rasterio.warp.transform_bounds` — real GDAL/PROJ, per the "use rasterio/pyproj, not ad-hoc conversion" rule) purely so a standard lat/lon web basemap (env-configurable tile URL/attribution, `VITE_MAP_TILE_URL`/`VITE_MAP_TILE_ATTRIBUTION`, defaulting to OpenStreetMap — no hardcoded commercial API key) can host an `L.imageOverlay` of the active layer's preview PNG at its true geographic extent. Every `relative_depth`/`metric_elevation`/`dsm` artifact shares the source dataset's exact CRS/transform by construction (Phase 3/4 always carry it through unchanged), so this one reprojected bounding box is reused for whichever layer is displayed rather than recomputed per artifact. A non-georeferenced dataset instead uses `L.CRS.Simple` with plain pixel-space bounds and no tile layer, with a visible "Local coordinate view" banner — never a fake latitude/longitude. Clicking the map estimates the corresponding source pixel by linear interpolation within the WGS84 bounding box (an honest approximation — accurate for the small, non-rotated footprints this project's imagery has, not a full inverse-CRS-transform) and calls the `/value` endpoint for the active scientific layer.

**3D terrain view** (`frontend/src/components/terrain/TerrainView3D.tsx`, mesh construction in `terrainMesh.ts`): fetches real terrain metadata + the binary height grid, builds a `THREE.BufferGeometry` with one vertex per grid cell (real elevation on Y, real local X/Z from `cell_size_x`/`cell_size_y`, vertex colors from the same ramp as the 2D preview), and computes real normals — **never a mathematically generated surface, never sine waves, never random/placeholder heights**. Vertical exaggeration only rescales the Y axis of already-fetched real data (no refetch, no change to any stored value) and is always labeled with its current multiplier. An RGB texture is applied **only** when the terrain grid's pixels are the source image's pixels — decided by the backend from raster provenance (`geospatial.terrain_grid.rgb_texture_compatibility`: 8-bit RGB source, same dimensions, same georeferencing/CRS/transform, and a terrain grid that is not reprojected from a geographic CRS), reported as `terrain.texture_compatible` / `texture_unavailable_code` in the visualization context and shared with the GLB export (D2; equal dimensions alone are not enough) — otherwise the terrain renders with its real elevation-driven vertex colors instead of stretching an unrelated or unverified image over it. Controls: `OrbitControls` for orbit/pan/zoom, `PointerLockControls` for WASD + mouse-look flythrough (a cheap "don't sink below the real observed minimum elevation" clamp, not per-pixel ground collision), a grid toggle, a "reset/fit camera" action that frames the real mesh bounds (derived from its actual half-width/half-height/elevation-range, never hardcoded coordinates), and full resource disposal (geometry/material/texture/renderer) on unmount or when switching datasets.

**WebGL fallback** (`frontend/src/hooks/useWebGLSupport.ts`): a real feature-detection probe (creates a throwaway canvas, requests a `webgl2`/`webgl` context) gates the "3D Terrain" mode button *before* any Three.js renderer is constructed — an unsupported browser/device sees a clear message and the 2D map remains fully usable, rather than the workspace crashing on a failed `WebGLRenderer` construction.

**Authenticated raster access** (`frontend/src/hooks/useObjectUrlBlob.ts`, `api/client.ts::fetchBlob`): every preview/window image is fetched with `fetch()` carrying the real `Authorization: Bearer` header (a plain `<img src="...">` cannot attach one), turned into a `Blob`, then a browser object URL — never a token in a query string, never a relaxed/unauthenticated image route. Object URLs are revoked when a layer/dataset changes and on unmount, so switching between datasets doesn't leak blob URLs.

**Performance**: the backend never loads a full-resolution raster into memory for preview/terrain purposes — `out_shape` decimated reads throughout (`raster_preview.py`, `terrain_grid.py`) push the downsampling work into GDAL rather than reading-then-resizing in Python. `PREVIEW_MAX_DIMENSION` (default 1024) and `MAX_TERRAIN_DIMENSION` (default 256) are both configurable via `app/core/config.py`/`.env`, never hardcoded past the settings layer.

**Known Phase 5 limitations** (see also §7):
1. The `dsm` artifact visualized here is exactly Phase 4's DSM output — numerically identical to `metric_elevation` (no hydro-flattening/terrain-object separation exists yet); the 3D view renders that same surface, not a separate terrain model.
2. Terrain/object-top separation is not implemented — a building or treetop in the source image appears in the 3D view exactly as it appears in the DSM, with no attempt to classify or remove it.
3. Visualization is not accuracy validation — rendering a smooth, plausible-looking 3D surface is not evidence the underlying calibration is correct; that's what Phase 4's MAE/RMSE/bias figures are for.
4. Vertical exaggeration changes only the rendered mesh; it is never applied to the terrain-grid API response or any stored artifact.
5. A non-georeferenced dataset has no geographic positioning anywhere in this phase's UI — local pixel coordinates only, in both 2D and 3D.
6. A raster larger than `PREVIEW_MAX_DIMENSION`/`MAX_TERRAIN_DIMENSION` is downsampled for interactive rendering (never silently cropped — the full extent is always covered, just at lower resolution) — the original file is unaffected and remains downloadable at full resolution via the existing Phase 3/4 artifact-download endpoint.
7. The 2D map's click-to-pixel mapping is a linear approximation within the reprojected bounding box, not a true inverse CRS transform — adequate for this project's small, non-rotated footprints, not guaranteed pixel-exact for a large or rotated one. **Fixed in P1-6 (§3.14).**

### 3.6 Class-agnostic region segmentation + quality metrics (implemented, Phase 6)

**The critical scientific rule this phase exists to enforce**: the segmentation model used here has **no notion of semantic classes**. It finds visually coherent regions in an image; it does not know "building" from "road" from "shadow." Every detected region is surfaced only as an opaque, arbitrary `region_id` — never a class label, never a confidence percentage standing in for classification accuracy. Anywhere this phase reports a quality number (image sharpness/exposure, or the model's own mask-stability score), it is labeled for exactly what it measures and never blended into a single fabricated "AI confidence" figure. **IMAGE QUALITY ≠ SEGMENTATION MASK STABILITY ≠ ELEVATION/CALIBRATION ACCURACY** — these are three independent, differently-scoped signals, computed by different code, over different data, and are never combined.

The checkpoint is downloaded on first use from the pinned commit's raw GitHub URL (never a "latest"/branch reference) directly into a `mobile_sam/` subdirectory of the same persistent `HF_HOME` bind mount Depth Anything V2's weights already use (§3.3, §4.7) — a sibling directory, not inside `huggingface_hub`'s own cache layout, since this checkpoint isn't fetched through that library. Every cached-or-downloaded file is verified against the pinned checkpoint's real byte size **and** real git blob SHA-1 (`_git_blob_sha1` — `sha1("blob " + len + "\0" + content)`, the actual formula `git hash-object` uses, not a plain file hash) before being trusted; a mismatch (corrupt cache, tampered file, wrong checkpoint) is rejected outright, never silently accepted. If the checkpoint cannot be obtained (no cached copy and no reachable network) or fails verification, `load()` raises a real `ModelLoadError`, which `app/services/semantic_pipeline.py` turns into `semantic_status=failed` with the real error message — **never** a fabricated result, and the stage is never marked completed.

**Real measured performance finding**: benchmarking MobileSAM's automatic mask generator at 256×256 and 512×512 input resolutions on CPU produced **roughly the same** (~45s) inference time at `points_per_side=16` — the model's own internal encoder preprocessing resizes to a fixed working resolution regardless of input size, so wall-clock cost is dominated by the fixed encoder pass and the number of point prompts, not by pixel count. This is why `MAX_SEMANTIC_INPUT_DIMENSION_PX` (default 2048, `app/core/config.py`) is documented and used strictly as a **memory/array-size safety bound** for very large source images, never claimed as a speed optimization — downsampling a merely-large-but-not-huge image would not measurably speed up this specific model as configured.

**Input policy**: reuses Phase 3's `extract_rgb_uint8` output (the same real, already-validated `(H, W, 3)` uint8 RGB array used for depth inference) — a DEM/depth/DSM raster is never processed as if it were RGB imagery.

**Real inference** (`ai/mobile_sam.py::MobileSAMEstimator.predict`): a genuine forward pass under `torch.inference_mode()` (no gradients — this is inference), timed with `time.monotonic()` and persisted verbatim, exactly like Phase 3's depth inference. **Deterministic overlap/rasterization policy** (fully documented in the method's own docstring, since "how are overlapping masks resolved" was an explicit open design question this phase had to answer, not something the library decides for you):
1. Run the automatic mask generator once — a fixed, deterministic grid of `points_per_side²` point prompts, no randomness.
2. Drop any real detected mask whose pixel area is below `MIN_SEMANTIC_REGION_AREA_PX` (default 64, `app/core/config.py`) — a real, documented filter against noise-sized fragments, never a fabricated omission.
3. Sort surviving masks by real pixel area, **largest first** (a stable sort — equal-area ties keep the model's own original output order), so results are fully deterministic for fixed input and fixed weights.
4. Assign region IDs `1..N` in that sorted order (ID 1 = the largest surviving region), then paint each mask's pixels into the label map **in that same order** — meaning a smaller region painted later **overwrites** a larger one wherever they overlap. This deliberately keeps visually smaller, more specific regions visible rather than letting them disappear under a large enclosing mask.
5. Each region's reported `pixel_area` is the **real, final, post-overlap** count from the actual rasterized array — never each mask's raw pre-overlap area — an honest count of what ended up in the output raster. `bbox_*` still describes each mask's own original extent, which may exceed its final visible area.

**Segmentation output — a categorical raster, never a continuous one**: a single-band `uint32` GeoTIFF (`geospatial/raster_io.py::write_single_band_categorical`) where `0` = background/unassigned (written into the file's own NoData tag) and each positive integer is one real detected region's arbitrary ID — **never** `float32` (region IDs are not interpolatable quantities). If the source image was downsampled for inference (per the memory-safety bound above), the resulting label map is mapped back to the source's real resolution via **nearest-neighbor only** (`PIL.Image.NEAREST`) — bilinear/bicubic would blend distinct, meaningless intermediate ID values, exactly the same rule already applied to categorical raster *reads* below.

**Region metadata** (`app/services/semantic_pipeline.py::run_semantic_segmentation`, persisted to both the artifact's `artifact_metadata` and the job's `semantic_metadata`): model name/task/repository/revision/checkpoint/license/device, `points_per_side`, `min_region_area_px`, real `inference_seconds`, output dimensions, `region_count`, and a full per-region list (`region_id`, real `pixel_area`, `bbox_row_min/col_min/row_max/col_max`, `mask_score`, `predicted_iou`). `mask_score` is SAM's own reported `stability_score` — labeled explicitly as **"Mask Stability"**, never "accuracy" or "probability of correctness" — and is `None` (not a fabricated number) for any region the model didn't score. Aggregate `mask_stability_mean/min/max` and `predicted_iou_mean` are computed only from regions that actually reported a value. A verbatim `value_semantics` disclaimer string (`REGION_VALUE_SEMANTICS`) is persisted into every successful artifact's own metadata, so a consumer reading only the artifact — without this document — still sees the class-agnostic caveat.

**Job integration** (`app/services/analysis_execution.py`) — soft-failure, exactly mirroring Phase 4's calibration pattern: `run_semantic_segmentation` **never raises**; a failed attempt (missing weights, unsupported input, inference error, unexpected exception) becomes `semantic_status=failed` with a real error message and does **not** fail the job — the real depth (and, if requested, calibrated) result already exists and remains a valid result on its own. Only opted into if `AnalysisParametersV1.enable_semantic_segmentation=true` (default `false` — an omitted field reproduces pre-Phase-6 behavior exactly, no calibration reference is required for this, unlike DEM/GCP calibration). Cancellation checkpoints sit both before semantic preprocessing/inference and immediately after inference, before the artifact is ever persisted — mirroring Phase 3's exact pattern (§3.3): in-flight inference itself cannot be forcibly interrupted (same documented limitation, §7), but a cancelled job's segmentation result is never written to storage or the database.

**Image-quality metrics** (`geospatial/image_quality.py::compute_image_quality`) — computed **unconditionally for every job**, regardless of whether segmentation was requested (pure numpy over the array already read for depth inference; sub-second on CPU): sharpness (a discrete-Laplacian-variance blur *proxy*, explicitly documented as a heuristic, not a calibrated measurement — real 4-neighbor kernel `[[0,1,0],[1,-4,1],[0,1,0]]`, reflect-padded), underexposed/overexposed pixel fractions (real thresholds on ITU-R BT.601 luminance, ≤10 and ≥245 on a 0-255 scale), real luminance min/max/mean, and a valid-pixel fraction. These are persisted into the job's `execution_summary.image_quality`, explicitly documented (both there and in the module's own docstring) as measuring **properties of the uploaded image itself only** — never model confidence, never segmentation accuracy, never elevation accuracy. They are computed the same way whether or not segmentation succeeds, and are never combined with `mask_score`/calibration residuals into any single derived number.

**Depth uncertainty — explicitly unavailable**: Depth Anything V2 (§3.3) has no native per-pixel uncertainty output, and this phase does not infer one from depth magnitude, gradient, color, brightness, or calibration residual — any of those would be a fabricated proxy presented as if it were the model's own uncertainty. Anywhere this is surfaced (job metadata, UI), it is stated as "unavailable for this model," not silently omitted or guessed at. **Calibration residuals** (Phase 4's existing MAE/RMSE/bias, §3.4) are reused completely as-is and still labeled "calibration residuals" — never relabeled "confidence" or "accuracy %" anywhere in Phase 6's own code or UI additions.

**Artifact + provenance** (`app/services/analysis_execution.py`): a new `AnalysisArtifact` row, `artifact_type="semantic_segmentation"`, `artifact_metadata.display_label="Distinct Surface Regions"` (the canonical, class-neutral display name used everywhere in the UI — never "Land Cover," "Object Detection," or any classification-implying label). Provenance is traceable via existing conventions, no fake foreign keys: `artifact_metadata.source_dataset_id` (the original source image) and `artifact_metadata.depth_artifact_id` (this same job's `relative_depth` artifact) — combined with the job's own `semantic_metadata.semantic_artifact_id`, a consumer can reconstruct source → depth → segmentation without a new schema concept.

**Visualization** (`app/services/visualization.py`, `geospatial/raster_preview.py`) — extends the existing Phase 5 system rather than a parallel one. `CATEGORICAL_ARTIFACT_TYPES = {"semantic_segmentation"}` is checked at every relevant point: the layer-context builder reports `is_categorical=true` and a real `region_count` instead of a continuous min/max (a region-ID raster has no meaningful "minimum" or "maximum"); `get_artifact_metadata`/`get_artifact_preview`/`get_artifact_window` all dispatch to dedicated categorical renderers (`generate_categorical_preview_png`/`generate_categorical_window_png`) that use **`Resampling.nearest` exclusively**, at both the GDAL-decimation and any PIL-upsampling level — never `Resampling.average`/bilinear/bicubic, which would blend meaningless intermediate region-ID values into fabricated new "regions." Each region ID gets a deterministic, real (not random-per-call) color via **golden-angle hue rotation** (`hue = region_id * 0.618033988749895 % 1.0`, HSV→RGB) — the same ID always renders the same color, and the colors carry no meaning themselves (they never signal "building" or "road"); background/NoData renders fully transparent (`alpha=0`), exactly like every other NoData convention in this project. The pixel-value endpoint (`/value`) needs no categorical-specific code — it already returns `None` for the real NoData value (0) and the real stored integer otherwise, exactly like any other single-band raster.

**Frontend** (`frontend/src/components/terrain/`) — extends, never redesigns, the existing Phase 5 workspace: `LayerType` gained `"semantic_segmentation"`; `LayerPanel` renders a new `CategoricalLegend` (deterministic per-region-ID swatches matching the backend's own golden-angle colors, bounded to 12 shown swatches plus a real "+N more" summary — never thousands of DOM nodes for a heavily-segmented image) instead of the continuous ramp `Legend`, plus an explicit "class-agnostic, not real-world categories" disclaimer line; `MapView2D` adds the layer to its existing stacking order (drawn topmost, as an optional overlay); `inspection.ts`'s `pickInspectableLayer`/`formatSample` gained a `semantic_segmentation` case that reports a real `Region ID: N` (or `Background / no region`) — **never** a class name — and `findSemanticRegion` looks up the already-persisted real `pixel_area`/`mask_score` for the inspected region ID from the job's own `semantic_metadata.regions`. This entire lookup sits *behind* the same `pickInspectableLayer` active-vs-visible-layer logic fixed in Phase 5 (§3.5) — Phase 6 adds a new case to that function's priority list, it does not touch or regress its existing behavior for `dsm`/`metric_elevation`/`relative_depth`. `AnalysisPanel` gained an opt-in "Detect distinct surface regions (experimental)" checkbox plus two new table columns (`Image quality`, `Segmentation`) surfacing the real backend values above — no unjustified "AI confidence: NN%" anywhere.

**3D terrain**: unchanged and untouched by this phase. DSM/metric elevation remains the *only* height source (§3.5) — semantic region IDs are never turned into terrain height, and no semantic overlay was added to the 3D view in this phase (left as a documented future option, §6, since it would require verifying spatial compatibility the same way RGB texturing already does).

**Configuration** (`app/core/config.py`): `MAX_SEMANTIC_INPUT_DIMENSION_PX` (default 2048, memory-safety bound — see the measured-performance note above), `MIN_SEMANTIC_REGION_AREA_PX` (default 64, real filter against noise-sized mask fragments).

**Database**: no new table — `semantic_segmentation` reuses the existing `analysis_artifacts` table exactly like `relative_depth`/`metric_elevation`/`dsm` (`artifact_type` is a plain `String(50)`, so no enum/migration was needed for the artifact type itself). Two new columns on `analysis_jobs` — `semantic_status` (new Postgres enum type) and `semantic_metadata` (JSONB) — plus four new `analysis_stage` enum values, added via a hand-written Alembic migration (`c0b7e6dffad9_add_semantic_segmentation_support.py`) rather than relying on autogenerate: Postgres enum types are append-only and autogenerate cannot diff new enum *members* on an existing type, so the four new `analysis_stage` values are added with explicit `ALTER TYPE ... ADD VALUE IF NOT EXISTS ... AFTER ...` statements, and the new `semantic_status` enum type is explicitly created (`sa.Enum(...).create(checkfirst=True)`) before the column referencing it is added.

**Scientific honesty summary (verbatim, read before using any Phase 6 output)**:
- MobileSAM provides real, class-agnostic region segmentation — region IDs are **not** semantic land-cover or object-classification labels.
- Image-quality metrics (sharpness/exposure/valid-pixel-ratio) are indicators of the uploaded image's own pixel properties, **not** a guarantee or measurement of model uncertainty, segmentation correctness, or elevation accuracy.
- Mask scores (`mask_score`/`predicted_iou`) are reported **only** when the model itself provides one — never invented when absent.
- Segmentation region quality/boundaries have **not** been independently validated against any real-world ground truth in this project.
- DSM/metric-elevation accuracy remains governed entirely by Phase 4's documented calibration limitations (§3.4) — Phase 6 changes nothing about elevation accuracy.
- Rendering a segmentation overlay does not imply, and must never be presented as implying, scientific accuracy of the underlying regions.
- For non-georeferenced imagery, segmentation results (like every other layer) remain spatially local/pixel-coordinate based — no geographic coordinates are fabricated.

### 3.7 Measurements & terrain analysis (implemented, Phase 7)

**What this phase adds, and what it deliberately doesn't**: real point elevation lookup, planimetric distance, full-resolution terrain profiles, and authoritative coordinate inspection over the actual Phase 3/4/6 artifacts — plus a real, persisted measurement history (`measurements` table). It does not add polygon/area drawing tools, building/object height estimation, or any UI/UX redesign — the Measurements tab reuses the existing Terrain workspace component directly rather than a parallel implementation (§4.1).

**The critical scientific rule this phase exists to enforce**: a measurement is only ever as trustworthy as its source raster. `relative_depth` is never presented as elevation (§3.3); a job that never calibrated has no `metric_elevation`/`dsm` artifact to measure elevation from at all (the artifact type itself is the gate — see §3.4); a distance is never claimed in metres unless the raster's own real CRS says so; and a calibrated elevation's real-world unit is reported as genuinely **unspecified** (whatever the reference data used), never assumed to be metres — the exact same honesty rule already applied to `metric_elevation`/`dsm` display (`frontend/src/components/terrain/LayerPanel.tsx`'s `LAYER_UNIT`), now also applied to every Phase 7 measurement result.

**Architecture**: synchronous REST endpoints extending the Phase 5 visualization API pattern — **not** a new `AnalysisJob`/RQ pipeline. Point/line sampling over an already-stored raster is cheap (a real windowed read, sub-second even for a full terrain profile), matching Phase 5's own "read-only, on-demand" precedent rather than Phase 3/4/6's heavy-compute job pattern. No new AI model, no new Docker service.

**Pure geospatial math** (`geospatial/measurements.py`, independent of the backend by design like the rest of `geospatial/`):
- `sample_point_elevation` — the exact real value at one pixel (`None` for a real out-of-bounds request or an in-bounds real NoData/NaN/Inf pixel, distinguished by an `in_bounds` flag) — a real single-pixel windowed read, same convention as `raster_preview.py::sample_pixel_value`.
- `pixel_to_coordinate` — the real map coordinate of a pixel, computed directly from the raster's own actual affine transform (`transform * (col + 0.5, row + 0.5)`, the exact pixel-center convention already established in `geospatial/calibration.py`), plus a real WGS84 reprojection via `rasterio.warp.transform` for universal display regardless of the raster's native CRS.
- `compute_distance` — real planimetric distance between two pixel coordinates. Not georeferenced → pixel distance only (`units="pixels"`, `distance=None`). Projected CRS → both points' real map coordinates, Euclidean distance in the CRS's own real linear unit (read from `rasterio`/PROJ, e.g. `"metre"` for UTM — never assumed). Geographic CRS → both points are reprojected into a real local UTM CRS first (`geospatial.terrain_grid.select_utm_crs` — the exact same technique the Phase 5 3D terrain viewer already uses, made a shared public function for this reuse) before computing distance — **longitude/latitude degrees are never treated as Cartesian metres** (independently verified in tests against a real haversine calculation).
- `sample_profile` — real elevation/value samples along the straight pixel-space line between two points, read via **one real windowed read of the FULL-RESOLUTION raster** covering the line's bounding box — **never** the display-only, `MAX_TERRAIN_DIMENSION`-capped 3D terrain grid (§3.5), which remains rendering-only. Value lookup uses nearest-pixel indexing on real, sub-pixel-precise interpolated line positions (a documented simplification, consistent with `geospatial/calibration.py`'s existing nearest-pixel GCP correspondence). Each sample's `distance_along` is a real cumulative sum of actual consecutive-sample real-world distances (reprojected per-sample for a geographic source) — **not** assumed proportional to the sample's fractional position along the line, since reprojecting a geographic CRS to a local UTM CRS is not perfectly linear.
- `coordinate_to_pixel` — the real, authoritative inverse of `pixel_to_coordinate`: converts a real map coordinate (reprojecting first via real GDAL/PROJ if given in a different CRS) back to the exact full-resolution `(row, col)` pixel it falls in, via `floor(inv_transform * (x, y))` (mirroring `geospatial/calibration.py`'s own inverse-transform convention exactly). This is the fix for item **F** below.
- Every out-of-bounds distance/profile request raises a real, explicit `MeasurementInputError` (a new exception, `geospatial/exceptions.py`) rather than being silently clamped or answered with a fabricated value — converted to a 422 at the API layer.

**Scientific-honesty layer** (`app/services/measurement_service.py` — the *only* place that decides what a raster's values mean; `geospatial/measurements.py` has no opinion on this):
- `relative_depth` artifacts → `value_kind="relative_depth"`, `units="relative units (unitless inverse depth — NOT elevation)"`, and the artifact's own real `value_semantics` disclaimer (`app/services/depth_pipeline.py::RELATIVE_DEPTH_VALUE_SEMANTICS` — extracted into a shared, named constant in this phase so both the depth pipeline and the measurement service reference the exact same string, never a re-worded copy).
- `metric_elevation`/`dsm` artifacts → `value_kind="elevation"`, `units="unspecified — same unit as the calibration reference used for this job ...; not independently verified as metres"`, and the artifact's own real `value_semantics`/`limitations` string (Phase 4's calibration disclaimer, reused verbatim).
- `semantic_segmentation` (or any other categorical type) → point-elevation/profile requests are rejected outright with a real `ValidationAppError` ("this is a categorical region-ID raster, not a continuous scientific field") — **distance** and **coordinate** measurements still work on it, since those are purely geometric (position only, never a pixel value) and every artifact of a job shares the source's exact CRS/transform by construction (Phase 3/4/6 all carry it through unchanged).
- `calibration_state` (the job's real `calibration_status` at measurement time) is included in every value-bearing result for provenance — never omitted, never inferred.

**API** (`app/api/v1/endpoints/measurements.py`), two routers mirroring the Phase 5 visualization split:
```
GET  .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/measurements/point        live point elevation
GET  .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/measurements/distance     live distance
GET  .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/measurements/profile      live terrain profile
GET  .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/measurements/coordinate   live coordinate lookup
GET  .../projects/{project_id}/analysis/{job_id}/artifacts/{artifact_id}/measurements/pixel        real map coordinate -> pixel (item F)
POST .../projects/{project_id}/measurements     save (recomputes server-side; never trusts a client-supplied result)
GET  .../projects/{project_id}/measurements     list (real project ownership, optional ?analysis_job_id= filter)
GET  .../projects/{project_id}/measurements/{measurement_id}    retrieve
DELETE .../projects/{project_id}/measurements/{measurement_id}  delete
```
The four `.../measurements/{point,distance,profile,coordinate}` endpoints are live, **unsaved** computation — the real-time "click a point, see the real value" interaction, exactly like Phase 5's `/value` endpoint. Saving is a deliberate, separate action (`POST .../measurements`): the server always **recomputes** the result from the request's real input coordinates against the real stored raster — a client can never persist a fabricated result by supplying one directly (the request schema doesn't even accept a `result` field). Every route reuses the exact existing ownership chain (`get_owned_project`/`get_owned_analysis_job`/`get_owned_artifact`, plus a new `get_owned_measurement` following the identical 404-never-403 IDOR-prevention shape) — no ownership logic was weakened or bypassed.

**Persistence** (`app/models/measurement.py`, migration `45fde3a116eb_add_measurements_table.py`): a real `measurements` table — `project_id`/`analysis_job_id`/`artifact_id`/`user_id` (all `ON DELETE CASCADE`, exactly like every other child row in this project), a real `measurement_type` enum (`point_elevation`/`distance`/`profile`/`coordinate` — a fixed, small, real category set, mirroring the `CalibrationStatus`/`SemanticStatus` precedent, never a free-text column), and `input_data`/`result_data` JSONB columns. JSONB was chosen deliberately over a PostGIS geometry column: this codebase has PostGIS enabled at the database level (§4.5) but **no ORM model anywhere uses a geometry column**, and Phase 7 doesn't introduce that as a first — `input_data`/`result_data` follow the exact same pattern already used for `AnalysisJob.parameters`/`execution_summary`/`calibration_metadata`/`semantic_metadata`. `result_data` always includes real `units`/`calibration_state`/`disclaimer` keys inline, so a saved record's provenance is fully inspectable from the stored JSON alone. `user_id` is provenance-only, not a second authorization dimension — projects in this codebase are single-owner (no sharing/collaborator feature exists), so `get_owned_project` already fully gates access.

**Frontend** (`frontend/src/components/terrain/`) — extends, never duplicates, the existing Phase 5/6 Terrain workspace: the previously-disabled "Measurements" tab (`pages/ProjectWorkspace.tsx`) now renders the *same* `TerrainWorkspace` component the "Terrain" tab does (no parallel map/3D implementation). A new `measurementMode` state (`"off" | "point" | "distance" | "profile" | "coordinate"`) is `"off"` by default, which reproduces the exact pre-Phase-7 inspection behavior unchanged; any other mode is only ever entered by an explicit mode-selector click, and the current mode is always visibly labeled next to the map/terrain (so a plain click is never mistaken for a measurement). Real measurement computation is dispatched against the exact same `inspectableLayer` plain inspection already uses (`components/terrain/inspection.ts::pickInspectableLayer`, untouched) — a measurement is only ever computed against a real, currently-visible scientific layer, and the Phase 5 active-vs-visible-layer inspection fix is preserved unmodified (measurement mode adds a new branch in the click handler, it does not alter the existing "off" path at all). Results render in a new `MeasurementResultPanel.tsx` (per-mode real value/distance/profile/coordinate display, including the exact real disclaimer/units/calibration-state strings from the API — never a re-derived or shortened claim), a real Recharts (`recharts`, newly added dependency) `ProfileChart.tsx` for terrain profiles (X = real distance-along-line, Y = real elevation/relative-depth value, `connectNulls={false}` so a real NoData run in the profile renders as a genuine gap, never bridged over), and a `MeasurementHistory.tsx` panel (real list/delete against the persisted API, refetched after every save).

**Item F — the Phase 5/6 3D-terrain coordinate-space bug, fixed**: `TerrainView3D.tsx`'s raycasting previously converted a 3D click directly into `(row, col)` in the **downsampled display terrain grid's own coordinate space** (`geospatial/terrain_grid.py`, capped at `MAX_TERRAIN_DIMENSION`, default 256px) and passed that value straight to the full-resolution `/visualization/value` endpoint as if it were a full-resolution pixel index — for any DSM larger than the display cap (the common case), this silently sampled the **wrong** pixel (a real, in-bounds, but mislocated value, not a crash). The fix: a 3D click's raycast hit point is a genuine real-world coordinate in the display grid's own real local coordinate frame (`origin_x`/`origin_y`/`cell_size_x`/`cell_size_y`/`local_crs`, already returned by `/terrain/metadata`) — for a georeferenced dataset, that real coordinate is now resolved against the artifact's own real full-resolution transform via the new backend-authoritative `.../measurements/pixel` endpoint (`geospatial.measurements.coordinate_to_pixel`), never a client-side index rescale; for a non-georeferenced dataset (no real map coordinate exists), the display grid's decimation uses the same uniform scale factor in both directions, so a client-side proportional rescale by the real `source_width`/`width` and `source_height`/`height` ratios (both already reported by `/terrain/metadata`) is exact, not approximate. Verified by dedicated regression tests (`backend/tests/test_measurements.py`) covering a 2048×2048 source downsampled to a 256×256 grid, all four corners, the center point, a non-square (2048×1024) raster, and out-of-bounds map coordinates.

**Configuration** (`app/core/config.py`): `MAX_PROFILE_SAMPLES` (default 512) caps a terrain profile's `samples` request parameter — a real, cheap windowed read either way, but bounds the response size.

**Known limitations**:
- No polygon/area-drawing tool — only point/two-point measurements (elevation, distance, profile, coordinate).
- Building/object height estimation is **not implemented** — a DSM surface-elevation difference between two points is a real number, but it is never automatically presented as a building or object height (no ground/object-top separation exists in the DSM, §3.4's known limitation #2 — a "height" reading between two DSM points is a surface-elevation difference only).
- A calibrated elevation's real-world unit remains genuinely unspecified (§3.4) — Phase 7 reports this honestly rather than resolving it; it is not a Phase 7 regression, it is Phase 4's own unresolved limitation surfaced consistently here too.
- Terrain-profile nearest-pixel value lookup (not sub-pixel/bilinear interpolation) is a documented simplification, consistent with this project's existing nearest-pixel GCP correspondence (§3.4) — adds unquantified positional error at coarse resolutions, same caveat as that existing precedent.
- No measurement result is ever labeled survey-grade or ground-truth accurate — every disclaimer inherits Phase 4's own calibration-accuracy caveats where relevant.

### 3.8 Disaster intelligence & terrain-derived hazard screening (implemented, Phase 8)

**What this phase adds, and what it deliberately doesn't**: real slope/aspect terrain derivatives, an elevation-threshold flood **screening** scenario, and a slope-threshold landslide susceptibility **screening index** — all computed directly from an existing, already-calibrated `metric_elevation`/`dsm` artifact (§3.4). It does not add rainfall/hydraulic simulation, ML-based flood/landslide prediction, routing, weather integration, multi-temporal change detection, or any UI/UX redesign — the Terrain workspace's existing `LayerPanel`/`MapView2D`/`Legend`/`inspection.ts` are extended, never duplicated (§4.1).

**The critical scientific rule this phase exists to enforce**: a hazard screening result is only ever as trustworthy as the elevation it was computed from, and inherits every one of Phase 4's own limitations (scale ambiguity, no terrain/object-top separation, reference-dependent accuracy). Flood screening is a real **elevation-threshold screening scenario**, never a hydrological/hydraulic simulation or a "flood prediction" — it does not model rainfall, drainage, rivers, flow routing, infiltration, tides, storm surge, hydraulic connectivity, or temporal flood dynamics, and a "potentially inundated" pixel is never verified to be hydraulically connected to a real water source. Landslide screening is a real, transparent, terrain-derived **susceptibility screening index** based on documented slope thresholds — it is **never** a calibrated or validated probability of landslide occurrence, and must never be presented as a percentage chance. Both carry their real methodology disclaimer verbatim wherever they're displayed, never re-worded or dropped.

**Architecture — always standalone**: unlike calibration/segmentation (§3.4/§3.6, soft-failure add-ons to an otherwise-independently-valid depth-estimation job), a disaster-screening job is its own, separate `AnalysisJob` that cites an already-produced elevation artifact directly via `disaster_source_artifact_id` (`AnalysisParametersV1`, "presence implies intent" — the same pattern already used for `dem_reference_dataset_id`/`gcp_reference_dataset_id`) and **never** re-runs depth estimation, calibration, or segmentation itself; a job cannot request both disaster screening and calibration/segmentation together (enforced by `AnalysisParametersV1._validate_disaster_screening`). Because this job's entire purpose *is* the hazard screening, a real failure anywhere in the pipeline is a real failure of the **whole job** (`disaster_status=failed` and `status=failed` together) — there is no independently-valid fallback result to keep, unlike Phase 4/6's soft-failure siblings.

**Pure geospatial math** (`geospatial/terrain_derivatives.py`, independent of the backend by design like the rest of `geospatial/`):
- `prepare_elevation` — opens the real elevation raster; rejects a non-georeferenced source outright (real-world slope/area cannot be computed without a real horizontal scale — in practice unreachable today since Phase 4 calibration itself already refuses a non-georeferenced source, but kept as a defensive, documented check) and a raster with no valid elevation pixels at all. A geographic CRS is reprojected to a real local UTM CRS first (`geospatial.terrain_grid.select_utm_crs`, the same technique already used by the Phase 5 3D viewer and Phase 7 measurements) so slope is never computed by mixing degrees with the elevation's own z-unit.
- `compute_slope_aspect` — real Horn (1981) 3×3 weighted finite-difference slope/aspect, the same default method ArcGIS/QGIS use for their own Slope/Aspect tools, implemented via manual reflect-padded numpy convolution (consistent with this project's existing manual-convolution precedent, Phase 6's Laplacian-variance sharpness metric). Aspect uses the real ESRI/Horn compass-bearing convention (0°=North, clockwise), independently verified against three directional test cases. NoData: any output pixel whose real 3×3 neighborhood includes an invalid elevation pixel is itself NoData in both outputs (`ELEVATION_ANALYSIS_NODATA = -9999.0`); a real, valid, perfectly flat pixel (slope==0) has a mathematically undefined downslope direction, reported via a distinct, documented sentinel (`ASPECT_FLAT_SENTINEL = -1.0`) rather than conflated with NoData — matching ArcGIS's own Aspect tool convention.
- `compute_terrain_statistics` — real min/max/mean/median elevation and min/max/mean slope, computed only over valid pixels, plus valid/total pixel counts.
- `run_flood_screening` — classifies each valid pixel `elevation <= water_level` as potentially inundated (class 2) vs. not (class 1); NoData stays NoData (class 0). Rejects a non-finite `water_level` outright. Real area is `pixel_area × pixel_count`, in the CRS's own real linear unit (never assumed to be metres).
- `run_landslide_screening` — classifies each valid slope pixel into Low/Moderate/High/Very High (classes 1–4) via configurable degree thresholds (`LandslideThresholds`, defaults `low_max_deg=10.0`/`moderate_max_deg=20.0`/`high_max_deg=30.0`); NoData stays NoData (class 0).

**Backend orchestration** (`app/services/disaster_pipeline.py`) — loads the real elevation artifact and calls into the geospatial layer above, timing each real stage (`timings_seconds`) and building the real metadata persisted to `AnalysisJob.disaster_metadata`: source/analysis CRS, reprojection flag, real pixel dimensions, terrain statistics, and (if requested) the flood/landslide result dicts — each including its own real `class_labels` and verbatim methodology disclaimer. This module raises (`DisasterAnalysisError`) rather than returning a soft-failure sentinel; `app/services/analysis_execution.py::_run_disaster_only_stages` catches this (and `RasterValidationError`) and converts it into a real `AnalysisExecutionError`, exactly like a depth-inference failure already does. `ELEVATION_ARTIFACT_TYPES`/`NOT_ELEVATION_ERROR` live in this module specifically to avoid a circular import (`app/services/analysis_jobs.py` → `app.jobs.tasks` → `analysis_execution.py` would otherwise cycle back if `analysis_execution.py` imported from `analysis_jobs.py` directly) — this module has no backend-side dependents of its own to cycle through.

**Job lifecycle** — 7 new `AnalysisStage` values inserted after Phase 6's `writing_semantic`: `validating_input → loading_terrain_data → computing_slope → computing_aspect → computing_terrain_statistics → running_flood_screening → running_landslide_screening → writing_hazard_artifacts → finalizing → completed` (the last two flood/landslide stages only advance if that screening was actually requested). A new `DisasterStatus` enum (`not_requested`/`processing`/`completed`/`failed`) and `disaster_metadata` JSONB column on `AnalysisJob` mirror the `CalibrationStatus`/`SemanticStatus` precedent exactly, except a real `failed` here also fails the whole job (§ above). The cited elevation artifact is validated twice: once at job-creation time (`app/services/analysis_jobs.py::_validate_disaster_source_artifact` — immediate 422 on an obviously-wrong reference, scoped by *project*, not by this job's own dataset, since a disaster job may screen an elevation artifact produced from any dataset in the same project) and again by the worker at execution time (time passes between creation and execution; the artifact could be deleted or replaced in between).

**Artifacts** — four new `AnalysisArtifact` rows per completed job: `slope`/`aspect` (real float32 GeoTIFFs, `nodata=-9999.0`, degrees) and `flood_screening`/`landslide_screening` (real `uint32` categorical GeoTIFFs via the existing `write_single_band_categorical` — the same pipeline semantic_segmentation already uses, §3.6 — `nodata=0`), each carrying real provenance metadata (`source_artifact_id`, CRS, reprojection flag) plus its own real `class_labels`/disclaimer for the two hazard rasters.

**Visualization API extension** (`app/services/visualization.py`) — `latest_completed_job` (driving the depth-family layers) now filters `disaster_status == NOT_REQUESTED` so a disaster-only job can never be mistaken for "the" job backing `relative_depth`/`metric_elevation`/`dsm`/`semantic_segmentation`; a new, independent `latest_completed_disaster_job` (filters `disaster_status == COMPLETED`) drives the new `slope`/`aspect`/`flood_screening`/`landslide_screening` layers, merged into the same `layers` list the frontend already consumes — a dataset can have both a depth-family job and a disaster job active at once, and both sets of layers appear together. A new `legend` field (`LayerContextOut`/`RasterMetadataOut`) carries real `{"value": int, "label": str}` pairs verbatim from an artifact's own persisted `class_labels` — populated only for `flood_screening`/`landslide_screening` (`LEGEND_ARTIFACT_TYPES`), deliberately **not** for `semantic_segmentation`, whose region IDs are arbitrary per-image labels, not a fixed named class set. Both functions were made public (no leading underscore) in Phase 9 specifically so `app/services/report_execution.py` could reuse them directly rather than re-implementing the same dataset→job lookup a second time.

**Frontend** (`frontend/src/components/terrain/`) — extends, never duplicates, the existing Phase 5/6/7 Terrain workspace: a new `DisasterPanel.tsx` component (elevation-source selector restricted to this dataset's own available `metric_elevation`/`dsm` layers, a water-level input, flood/landslide toggles, a "Run screening" action that POSTs a real `AnalysisJob` and polls it via the existing job-status endpoint) renders real terrain-statistics/flood/landslide results and the real disclaimer from the job's own `disaster_metadata` once complete — the backend remains fully authoritative; no hazard result is ever computed client-side. `LayerPanel.tsx`/`Legend.tsx` gained a `FixedLegend` component rendering a layer's real `legend` value→label pairs (reusing the exact same golden-angle-hue color formula the categorical preview PNG and `CategoricalLegend` already use, §3.6, so swatch colors match). `inspection.ts`'s layer-inspection priority and `formatSample` were extended for the four new layer types — slope/aspect report real degrees (aspect's flat-terrain sentinel displayed as "Flat terrain," never a fabricated bearing), flood/landslide look up the real class label via the layer's own `legend` rather than showing a bare integer.

**Configuration/safety**: the worker re-validates the cited elevation raster's structural dimensions against the existing `MAX_DEPTH_INPUT_DIMENSION_PX` bound before reading pixel data — in practice unreachable today since every `metric_elevation`/`dsm` artifact already inherits this bound from the source image it was derived from, but kept as the same defensive re-check every other phase in this pipeline already applies to its own input.

**Known limitations**:
- Flood screening has no hydraulic connectivity check — an isolated low-elevation depression with no real path to a water body is still classified "potentially inundated" if it's below the water level; this is a deliberate scope boundary of an elevation-threshold screen, not a bug.
- Landslide thresholds are a real, documented, but not site-calibrated methodology choice (steeper terrain assumed more susceptible, all else equal) — they do not incorporate soil type, geology, hydrology, land cover, or any triggering event, and are not derived from any site-specific geotechnical study.
- Both screenings inherit every limitation of the elevation they're computed from (§3.4) — scale ambiguity, no terrain/object-top separation, reference-dependent accuracy.
- No independent validation against real historical flood/landslide event data is performed — "independent validation" in this project's own test suite means cross-checking the API's reported statistics against a separate tool reading the same raster bytes directly (e.g. a standalone GDAL container), not validation against ground-truth hazard outcomes.

### 3.9 Reports & export (implemented, Phase 9)

**What this phase adds, and what it deliberately doesn't**: a real, persisted report/export workflow that assembles whatever real Phase 1-8 results already exist for one dataset into a downloadable PDF, a machine-readable JSON export, a CSV (when genuine tabular data exists), and a ZIP bundle of everything plus the real raster artifacts. It does not add a report *template editor*, scheduled/recurring reports, email delivery, or any UI/UX redesign — the existing project workspace gains one new tab (`ReportsPanel.tsx`) rather than a parallel reporting application.

**The critical scientific rule this phase exists to enforce**: a report is a **presentation** of already-real data, never a second, independent source of truth for it. Every field in a report traces to a real database row or a real on-demand raster read (`app/services/visualization.py::get_artifact_metadata`, reused verbatim) — the report builder (`app/services/report_builder.py`) performs zero computation of its own, only assembly. A missing section (no calibration, no disaster screening, no measurements) is rendered as an explicit, honest "not available"/"not requested" statement, never a blank space or an invented value; relative depth is never re-labeled as elevation inside a report; a calibrated result never gains a "survey-grade" claim it didn't already have; flood/landslide sections carry their exact Phase 8 disclaimers verbatim.

**Architecture — fits the existing job/worker system, not a parallel one**: a `Report` is a new, standalone persisted row (mirroring `AnalysisJob`'s own status-tracking shape) generated by a new task function (`run_report_generation`) enqueued to the SAME RQ `"default"` queue the existing worker container already processes — no new service, no new Docker container, no new queue. The split across modules mirrors the analysis-job domain exactly, for the exact same reason:
- `app/services/report_service.py` (the "create" side, analogous to `analysis_jobs.py`) — validates a completed analysis actually exists for the dataset (immediate 422 otherwise), persists the `Report` row, enqueues generation.
- `app/services/report_execution.py` (the "execute" side, analogous to `analysis_execution.py`) — the real RQ-invoked pipeline. Kept in a separate module from `report_service.py` specifically to avoid a circular import (`report_service.py` → `app.jobs.tasks` → `report_execution.py`; if generation instead lived in `report_service.py`, `app.jobs.tasks` importing it would cycle straight back) — the identical lesson Phase 8's `disaster_pipeline.py` already documents for the analysis-job domain.
- `app/services/report_builder.py` — pure data assembly (`ReportContext` in, one real nested dict out). No I/O, no database session, no rendering — independently unit-testable against plain constructed model instances.
- `app/services/report_render.py` — pure rendering: `render_pdf`, `render_csv`, `build_bundle_zip`. Each is a pure function of the data dict (and, for the bundle, real artifact file paths already on disk) — independently unit-testable without a database at all.

**Which analysis a report covers**: a report is scoped to one **dataset**, not one `AnalysisJob` — because, since Phase 8, a single dataset can genuinely have two independent completed jobs (a depth/calibration job and a separately-run disaster-screening job, §3.8). `report_execution.py` reuses `app/services/visualization.py`'s own `latest_completed_job`/`latest_completed_disaster_job` dataset→job lookups directly (both made public in this phase for exactly this reuse) rather than re-implementing the same "which job actually backs this dataset's current results" logic a second time — the report always agrees with whatever the Terrain workspace itself would currently display for that dataset.

**Real report data snapshot** (`report_metadata`, JSONB on `Report`, and the exact body served by `GET .../reports/{id}/json`): project/dataset identity and georeferencing; the depth job's real model name/revision/device/inference time and the exact `RELATIVE_DEPTH_VALUE_SEMANTICS` disclaimer (reused verbatim from `app/services/depth_pipeline.py`, never re-worded); real calibration fields (method, scale/offset, sample/inlier/outlier counts, validation MAE/RMSE/bias, the cited reference dataset's own real filename/CRS) when calibrated, or an honest "no reference was provided" note when not; real semantic-segmentation region count/mask-stability when requested; the disaster job's real terrain statistics and flood/landslide summaries (their own `class_labels`/disclaimers included verbatim) when a disaster job exists; a real artifact inventory (one entry per `AnalysisArtifact` across both jobs, via `get_artifact_metadata`); every measurement taken against either job's artifacts; a `provenance` block naming the exact source dataset/job IDs and the generating user; and a `limitations` list built by collecting every disclaimer actually applicable to what's present (never a fixed list unrelated to the real content). This one dict is the single source of truth the PDF, JSON endpoint, and CSV/bundle all render from — never independently recomputed per output format, so they can never drift apart from each other.

**PDF rendering** (`reportlab`, pure Python — no system libraries like Cairo/Pango needed, unlike e.g. WeasyPrint): built directly from the data dict with `SimpleDocTemplate`/`Table`/`Paragraph` — there is no static template file with placeholder values anywhere in this pipeline. A `None`/absent field renders as a plain "Not available" table cell; a genuinely-not-requested section (uncalibrated, no semantic segmentation, no disaster job) renders its own honest one-line explanation instead of an empty section.

**CSV export**: one real CSV combining every genuinely-available tabular section (measurements, terrain statistics, hazard class pixel counts/areas/percentages) as blank-line-separated labeled sections — chosen over several separate per-section CSV files to keep the API/UI surface small while still real and complete. Returns nothing (a real 404, not an empty file) when none of those sections have any data at all — e.g. a dataset with only an uncalibrated depth job and no measurements has no real tabular data to export.

**ZIP bundle**: `report.pdf` + `analysis.json` (the exact `report_metadata` dict, `json.dumps`'d) + `report.csv` (only if it exists) + every real generated raster artifact from both jobs, archived directly from its existing storage location under `artifacts/` — the bundle builder never regenerates or copies raster data ahead of time, it reads each artifact's real, already-written file at bundle-build time. A referenced artifact file that's gone missing from storage is noted in a real `artifacts/MISSING.txt` manifest entry rather than silently producing a shorter, unexplained archive.

**Persistence & failure semantics**: `reports` table (`Report` model, migration `a0d3ac929883`) — `project_id`/`dataset_id`/`user_id` FKs (all `ON DELETE CASCADE`, the same convention as every other child row), a `ReportStatus` enum (`pending`/`generating`/`completed`/`failed`, mirroring `CalibrationStatus`/`SemanticStatus`/`DisasterStatus`), and nullable `pdf_storage_key`/`csv_storage_key`/`bundle_storage_key` columns (through the existing storage backend, same convention as `AnalysisArtifact.storage_key`). Like Phase 8's disaster jobs (and unlike Phase 4/6's soft-failure calibration/segmentation add-ons), a report has no partially-valid fallback — its entire purpose is the report itself, so a real failure (the dataset's analysis was deleted or changed between report creation and generation, a render error, ...) marks the WHOLE report `failed` with the real reason, and any partially-written files for that report are deleted from storage rather than left as a broken half-generated set.

**API** (`app/api/v1/endpoints/reports.py`, ownership via a new `get_owned_report` following the exact same project-scoped, 404-never-403 IDOR-prevention shape as `get_owned_measurement`):
```
POST   .../projects/{project_id}/datasets/{dataset_id}/reports   create + enqueue generation
GET    .../projects/{project_id}/reports                          list (optional ?dataset_id=)
GET    .../projects/{project_id}/reports/{report_id}               status + availability flags
GET    .../projects/{project_id}/reports/{report_id}/json          the real, full data snapshot
GET    .../projects/{project_id}/reports/{report_id}/pdf           download the real PDF
GET    .../projects/{project_id}/reports/{report_id}/csv           download the real CSV (404 if none exists)
GET    .../projects/{project_id}/reports/{report_id}/bundle        download the real ZIP bundle
```
Every download endpoint returns a real 422 ("not ready yet") for a report that hasn't reached `completed`, rather than a confusing 404 or an empty file.

**Frontend** (`frontend/src/components/ReportsPanel.tsx`, wired into `pages/ProjectWorkspace.tsx`'s previously-disabled "Reports" tab) — a dataset picker, a real "Generate report" action, and a report-history table that polls (same pattern as `AnalysisPanel.tsx`) while any report is `pending`/`generating` and stops once none are. Download buttons for PDF/CSV/ZIP bundle are disabled based on the report's own real `pdf_available`/`csv_available`/`bundle_available` flags — never a button that claims a file exists when it doesn't. `components/reportFormat.ts` holds the small amount of pure status-label logic, kept network-free specifically so it's unit-testable in isolation (same pattern as `measurementFormat.ts`).

**Known limitations**:
- No report template customization — one fixed layout/section order for every report.
- No scheduled/recurring report generation, and no email/external delivery — every report is generated on explicit user request and downloaded manually.
- A report's `report_metadata` is a frozen snapshot taken at generation time — if the underlying dataset's analysis is re-run afterward, the existing report is NOT automatically regenerated; a new report must be requested to reflect the new results.
- CSV export is one combined file with labeled sections rather than separate per-concern files (e.g. a dedicated GCP-sample CSV) — a deliberate scope choice to keep the export surface small; the same real numbers are all present, just not split across multiple files.

### 3.10 Relative terrain for uncalibrated/non-georeferenced imagery (implemented, Phase 10)

**What this phase adds, and what it deliberately doesn't**: a real 3D terrain view for a dataset that has produced `relative_depth` but never successfully calibrated (no DEM/GCP reference, or a reference that failed) — closing the gap where the single most basic case this project is named for (a single uncalibrated photo) previously had NO 3D flythrough at all, only a flat 2D relative-depth layer. It does not add metric elevation, a DSM, georeferencing, or any accuracy claim to `relative_depth` itself — the raster and its scientific meaning are completely unchanged (§3.3); this phase only extends WHERE that same real data can be visualized, reusing the entire existing 3D pipeline unmodified.

**The critical scientific rule this phase exists to enforce**: a terrain mesh built from `relative_depth` values is real geometry over real (if unitless, relative) numbers, but it is never elevation, never a DSM, never georeferenced terrain, and never assigned a physical unit. Every surface exposed by this feature — API schema, visualization context, frontend UI — carries an explicit `height_kind` discriminator (`"elevation"` | `"relative_depth"`, reusing the exact naming convention Phase 7's `PointElevationOut.value_kind` already established) so no consumer can mistake one for the other by field name alone.

**Architecture — no duplicate system, one relaxed gate**: `geospatial/terrain_grid.py::extract_terrain_grid` was already fully artifact-type-agnostic (reads band 1 of whatever single-band raster path it's given — it has no dependency on the file being a calibrated DSM) — confirmed by inspection before this phase touched anything, and left completely unmodified except for one clarifying docstring sentence. The only real gate was in `app/services/visualization.py::build_visualization_context` (which previously required a `dsm` artifact specifically to report `terrain.available=True`) and the two `.../terrain/metadata`/`.../terrain/grid` API endpoints (which previously rejected any artifact type other than `"dsm"`, via `_require_dsm`). Both were relaxed to also accept a job's own `relative_depth` artifact when no `dsm` exists — `TERRAIN_SOURCE_ARTIFACT_TYPES = {"dsm", "relative_depth"}` is now the single, real, shared list both the service layer and the API layer check against (never two independently-drifting lists). No new artifact type, no new database table, no new frontend component family, no new camera/texture system — the exact same Three.js scene, `PointerLockControls` WASD+mouse-look flythrough, UV-mapped RGB texture projection, and orbit controls already built for the calibrated DSM case now also render a relative-depth-backed terrain, unmodified.

**Real fallback logic** (`build_visualization_context`): if a real `dsm` artifact exists, `terrain.height_kind="elevation"` (unchanged calibrated-path behavior — verified via regression tests that this path's numbers and shape are byte-for-byte the same as before this phase). Else, if a real `relative_depth` artifact exists, `terrain.height_kind="relative_depth"`, `terrain.artifact_id`/`analysis_job_id` reference that real artifact, `min_elevation`/`max_elevation` are left `None` (never populated for a relative-depth-backed terrain — the field names themselves imply a physical quantity this data doesn't have), and `min_height_value`/`max_height_value` (new, scientifically-neutral field names, populated for BOTH cases) carry the real min/max of whatever the actual height values are. Else — neither artifact exists yet (e.g. the job is still running) — `terrain.available=False` with a real reason, exactly as before. This fallback is deliberately indifferent to *why* no DSM exists (calibration never requested vs. calibration attempted and failed): both leave `dsm_artifact` `None`, and both correctly fall back to the real `relative_depth` artifact the job still has — regression-tested explicitly for the calibration-failed case, since "calibration failed" must never be conflated with "no real data exists to show."

**Coordinate/CRS semantics — no fabrication, unchanged from the existing generic machinery**: `extract_terrain_grid` already handles all three real cases identically regardless of which artifact type it's given — a non-georeferenced source yields `crs=None`, `is_georeferenced=False`, `origin=(0,0)`, `cell_size=1` (never a fabricated CRS); a projected-CRS source uses its real transform directly; a geographic (lat/lon) CRS is reprojected to a real local UTM CRS first (`select_utm_crs`, shared with Phase 7 measurements). Since `relative_depth` genuinely can be georeferenced (Phase 3 preserves the source's real CRS/transform when the source image itself was georeferenced, even though no calibration ever ran), a relative-depth-backed terrain for a georeferenced-but-uncalibrated source is rendered in its own real local coordinate frame exactly like the calibrated case — it is simply never called elevation.

**RGB texture projection and first-person flythrough — verified still fully generic**: `frontend/src/components/terrain/TerrainView3D.tsx` builds its mesh from an abstract `(TerrainMetadata, height-grid buffer)` pair and has no awareness of which artifact type backed either — zero changes were needed there. Texture-compatibility (`rgbLayer.width === terrain.width`) already holds for both cases because every scientific artifact type (`relative_depth`, `metric_elevation`, `dsm`, `semantic_segmentation`) is unconditionally resized back to the exact source RGB dimensions during the depth/calibration/semantic pipeline (verified in `ai/depth_anything.py` and `app/services/analysis_execution.py` before this phase began) — texture projection and first-person WASD+mouse-look flythrough work identically in relative mode, never re-labeled as an orthomosaic/orthophoto/georeferenced texture (`components/terrain/terrainAvailability.ts::textureLabel` calls it "RGB texture on relative terrain" instead).

**Frontend honesty** (`components/terrain/terrainAvailability.ts`, a small pure module mirroring `inspection.ts`'s/`reportFormat.ts`'s "extract pure logic for unit-testability" precedent — Three.js/React components themselves stay untested per this project's existing documented convention): `isRelativeTerrain`/`isElevationTerrain` classify a real `TerrainContext` (never re-derive `height_kind` from anything else), and `RELATIVE_TERRAIN_NOTICE` is the exact persistent banner text (rendered in both the terrain-controls panel and as an overlay on the 3D canvas itself in `TerrainWorkspace.tsx`) whenever relative mode is active — never shown for the calibrated case, verified in tests.

**Measurement safety — verified unaffected by construction, not merely by re-testing**: the pixel-inspection/measurement code path (`inspection.ts::pickInspectableLayer`, the point/distance/profile/coordinate endpoints) operates entirely on `VisualizationContext.layers` and `AnalysisArtifact`/`analysis_job_id`, never on `VisualizationContext.terrain` — the 3D view's own click handler (`TerrainView3D.tsx::onClick`) resolves a click to a `(row, col)` and hands it to the exact same `handleMapClick`/inspection pipeline the 2D map already uses, regardless of which artifact backs the terrain mesh. Phase 7's existing `relative_depth`-vs-elevation labeling (`value_kind`, disclaimers) was therefore never touched by this phase and needed no changes — confirmed via the full existing measurement test suite passing unmodified.

**Report/export safety**: `app/services/report_builder.py` already builds its `depth_analysis`/`disaster_screening` sections directly from `AnalysisJob` fields, entirely independent of `VisualizationContextOut`/`TerrainContextOut` — it already correctly describes `relative_depth` as unitless and never as elevation (Phase 9). No change was needed or made.

**Known limitations**:
- A relative-depth-backed mesh's height values are the model's raw relative-depth numbers (larger = closer to camera) — the resulting geometry is a real, if visually inverted-feeling in some scenes, undulation, not a claim about which direction is "up" in any physical sense. No adjustment/inversion is applied; the raw real values are shown as-is, exactly like the calibrated case shows the DSM's raw real values as-is.
- No new accuracy or usefulness claim is made for the relative-depth mesh beyond what Phase 3 already documents about `relative_depth` itself (scale ambiguity, no terrain/object-top separation, not validated for nadir/aerial imagery).

### 3.11 Reliability, recovery & reproducibility hardening (implemented, Phase 11)

**Scope discipline**: this phase followed an explicit readiness audit (Phase 11 readiness report) that found the full SIH26175 pipeline already functionally complete with no remaining requirement gap. The audit evaluated eleven candidate hardening items and authorized only three as genuine core-completeness blockers; everything else (retry policy, rate limiting, audit logging, calibration residual visualization, storage-orphan cleanup, production Docker hardening) was explicitly deferred as real-but-not-blocking. No UI/UX redesign was in scope.

**A — Immutable Depth Anything model revision**: `ai/depth_anything.py`'s `MODEL_REVISION` was a moving `"main"` branch reference — the exact opposite of `ai/mobile_sam.py`'s already-correctly-pinned commit SHA, and unacceptable for reproducible scientific execution (a future upstream update to `main` could silently change model output for every job). Repinned to the exact immutable commit `main` resolved to at pin time, confirmed two independent ways — the commit already present in this project's local Hugging Face cache (i.e. what every prior phase's testing, including Phase 10's real browser acceptance, actually ran against) and a live query against the Hugging Face Hub API — never guessed. A real before/after inference comparison (loading by `revision="main"` vs. the pinned SHA, identical synthetic input, identical `torch.inference_mode()` forward pass) produced bit-for-bit identical output (max absolute difference `0.0`), as expected since both names resolve to the same commit; the change protects reproducibility going forward, it does not alter today's behavior. A fresh, no-cache re-download of the model from only the pinned SHA (local cache deliberately deleted first) was verified to load and run inference successfully.

**B — Explicit job timeout + stale/crashed job reconciliation**: `app/services/analysis_jobs.py`'s `enqueue()` call previously specified no `job_timeout`, so RQ's implicit 180-second default silently applied. A real, empirical measurement (a genuine depth + MobileSAM semantic-segmentation job at the largest input size `MAX_SEMANTIC_INPUT_DIMENSION_PX` allows, run against this project's own live worker) took 170.7s end-to-end — within roughly 10 seconds of that default, confirming the risk was not theoretical. `Settings.ANALYSIS_JOB_TIMEOUT_SECONDS=900` (`app/core/config.py`) is now passed explicitly, generously above the measured worst case.

If a job is ever killed by that timeout, or the worker process/container crashes outright, neither path reaches `execute_analysis_job`'s own exception handling (the work-horse process is torn down directly) — the job's row is left `running` forever with no automatic recovery, a limitation this project had honestly self-documented since Phase 2/3 (see the "Known limitations" note this section supersedes). `app/services/job_reconciliation.py::reconcile_stale_running_jobs` closes this: it reconciles any `running` job whose `updated_at` has not advanced for longer than `Settings.STALE_JOB_AFTER_SECONDS=1200` to `failed`, with an honest, real error message. Deliberately zero new columns: `AnalysisJob.updated_at` already advances via `onupdate=func.now()` on every one of the many real stage-transition commits already scattered throughout `analysis_execution.py` — it was already exactly the "worker heartbeat" a staleness check needs. The reconciling UPDATE is a single atomic, conditional statement (`WHERE status='running' AND updated_at < threshold`) — a job that has since completed, failed, or been cancelled is never touched, and a genuinely active job (its longest real observed single inference call is 145.7s, versus a 1200s threshold) is never falsely reaped.

This sweep runs as a periodic background `asyncio` task started from the backend's own FastAPI lifespan (`app/main.py`) — inside the backend process, not the worker — specifically so it does not depend on the worker (the thing that crashed) ever coming back. It runs once immediately on backend startup (catching anything orphaned by a prior crash right away) and every `Settings.STALE_JOB_SWEEP_INTERVAL_SECONDS=60` seconds thereafter.

**Real Docker crash verification performed**: a real analysis job (depth + semantic segmentation) was started against the live stack and confirmed `running` in the `semantic_inference` stage; the worker container was then killed with `docker kill --signal=SIGKILL` mid-inference. The job row was confirmed to remain `running` forever — even after the worker container was manually restarted and became healthy again, since a fresh worker process only pulls new jobs from the queue and has no awareness of a previous process's orphaned claim. The job's `updated_at` was then backdated past the staleness threshold (to make the verification practical within a single session rather than waiting the real 20-minute window) and the backend container was restarted to load the current code; its lifespan's immediate startup sweep — the real, unmodified production mechanism, not a test harness — reconciled the job to `failed` with the honest error message within seconds, and the dataset's active-job lock was confirmed released (a new job could be submitted immediately). One incidental, honestly-reported finding from this exercise: this environment's backend `--reload` (`uvicorn --reload`) did not reliably pick up file changes over its Windows/Docker Desktop bind mount, unlike the frontend's Vite dev server (which is explicitly configured with polling for the same class of issue) — a manual container restart was needed to load new code for live (non-pytest) verification. This is an environment/tooling observation, not a Phase 11 defect, and was out of the authorized scope to fix.

**C — Running-job cooperative cancellation**: Phase 2 had already built full cooperative-cancellation checkpoint infrastructure (`_raise_if_cancelled`, re-reading the job's real DB status at roughly ten points spread across every pipeline branch — depth, calibration, semantic, and standalone disaster-screening stages) explicitly anticipating this exact future need — its own docstring said so. The only blocker was that `cancel_job`'s atomic compare-and-swap UPDATE matched only `status='queued'`. Widened to `status IN ('queued', 'running')` — the existing checkpoints needed zero changes, since they already act on `job.status == CANCELLED` however it got set. This closed the gap with no new column, no new pipeline engineering, and no schema migration.

Widening cancellation surfaced one real symmetric race the queued-only design never had to consider: a job's *own* completion and failure write-paths in `execute_analysis_job`/`_mark_failed` were previously unconditional ORM commits, so a cancellation landing in the narrow window between a job's last checkpoint and its final commit could be silently clobbered back to `completed` (or a failure could silently overwrite a `cancelled` row back to `failed`). Both paths were made conditional (`WHERE status='running'`) — exactly mirroring the claim step's own existing atomic-UPDATE pattern — so whichever of a completion, a failure, or a cancellation commits first wins, and the loser's WHERE clause simply matches no rows. Verified with a real forced race test (a stubbed, deliberately slow `_run_stages` racing a genuine HTTP cancel request against the real, unmodified claim/completion code).

Cancellation of a running job is honestly cooperative: the API response and a new frontend tooltip both say cancellation is *requested* and takes effect at the next safe checkpoint, never claiming to interrupt an in-flight model inference call — verified end-to-end by running the real claim/checkpoint pipeline in a genuinely separate OS thread (so a real blocking `predict()`-style call cannot starve the same event loop a concurrent HTTP cancel request needs) and confirming inference was allowed to finish, not interrupted mid-call, before the checkpoint immediately after it observed the cancellation and stopped. A second test confirmed that an artifact from an earlier, already-committed pipeline stage (e.g. a real depth raster) is never deleted just because cancellation is observed at a later checkpoint — checkpoints sit only at safe stage boundaries, never mid-write, so anything already committed is a real, valid, complete result regardless of the job's final overall outcome.

`frontend/src/components/AnalysisPanel.tsx`'s existing Cancel button (previously shown only for `queued` jobs) now also appears for `running` jobs, with a `title` tooltip distinguishing immediate (queued) from cooperative, checkpoint-bounded (running) cancellation — the only frontend change this phase made; no other UI/UX change was in scope.

**Testing**: 15 new backend tests (`tests/test_depth_pipeline.py`, `tests/test_analysis.py`, `tests/test_job_reconciliation.py`), all real integration tests against the actual database and pipeline code — no mocking of the cancellation/reconciliation logic itself. Final count 229/229 (up from 214/214), reconfirmed against a fresh, no-cache Docker rebuild of the backend/worker images. Frontend 57/57 unchanged; `tsc`/`eslint`/`npm run build` all clean.

### 3.12 Bare-earth estimate (DTM) and nDSM (implemented, P1-3)

**What these are, and are not.** TERRAIN-X's only elevation input is one calibrated monocular surface raster (`dsm`, bitwise identical to `metric_elevation`). There is no point cloud, no multiple returns, no stereo, and no classified ground, so **no true DTM can be measured here**. P1-3 adds two **raster-derived estimates**:
- `dtm`: **estimated** bare-earth elevation, a raster-filter approximation.
- `ndsm = dsm − dtm`: the **estimated** height of the visible surface above that estimated ground.

Neither is a physical measurement or a measured object/building height. The display names ("DTM (estimated bare earth)", "nDSM (estimated height above ground)"), inspection labels ("Estimated bare-earth elevation", "Estimated height above ground"), artifact `value_semantics`, and report sections all say so.

**When it runs.** Automatically inside the depth/calibration job, after `VALIDATING_RESULTS`, **only when calibration ended `CALIBRATED`**, i.e. after the P1-2 quality gate passed and `metric_elevation`/`dsm` were written and re-verified. The new stages are `filtering_ground → writing_dtm → writing_ndsm`.
- An uncalibrated job, a failed calibration, or a gate rejection leaves `ground_filter_status = not_requested`, with no DTM/nDSM.
- `relative_depth` is never ground-filtered: it has no unit, so elevation-difference thresholds would be meaningless.
- The P1-2 gate code is unchanged; the ground filter only reads its outcome.

**Algorithm** (`geospatial/ground_filter.py`, pure numpy): a raster progressive morphological filter (Zhang et al. 2003).
1. Valid cells are finite (and not the source NoData). Invalid cells are **excluded** from every window: +∞ for erosion, −∞ for dilation. They are never fed in as the −9999 sentinel.
2. The metric cell size is measured on the DSM's own grid, with no reprojection, so outputs stay cell-aligned:
   - projected CRS: pixel size × the CRS linear-unit factor (US-foot CRSs are converted);
   - geographic CRS: the centre pixel's offsets measured in local UTM;
   - rotated or non-georeferenced grids are rejected.
3. Windows grow over half-widths of 1, 2, 4, 8, … cells of the coarser axis, up to `GROUND_FILTER_MAX_WINDOW_M`, and are clamped to the raster.
4. Thresholds are `dh₁ = dh0`, then `dh_k = min(s·(size_k − size_{k−1}) + dh0, dh_max)`. Because the threshold depends on the window-size increment, a short final (clamped) step can have a lower threshold than the step before it.
5. Each level applies a square, separable, NaN-aware van Herk/Gil-Werman opening (O(n) per pass). A cell becomes non-ground once `S_{k−1} − O_k > dh_k`.
6. `DTM = DSM` on ground cells and the final opened surface on non-ground cells.

**Invariants.**
- Opening never exceeds its input, and the openings are chained, so **DTM ≤ DSM** everywhere by construction.
- Every DTM value is a value the DSM contains, so `ndsm = dsm − dtm` is exact in float32.
- `nDSM ≥ 0`, and `nDSM == 0` exactly on cells classified as ground.
- nDSM is **never clipped**. A value below −1e-6 fails the ground-filter stage instead of being hidden.

**Outputs.** `dtm.tif` and `ndsm.tif`: float32, NoData −9999, on the DSM's exact grid, CRS and transform, each re-opened and verified after writing. Artifact metadata carries provenance (source dataset, depth, metric elevation, DSM and DTM artifact IDs, `calibration_quality_gate_passed`) plus min/max/mean statistics. `ground_filter_metadata` holds:
- the method and the applied policy (version, parameters, and the "not tuned/validated" statement);
- the cell size and the window/threshold schedule;
- statistics (valid and ground counts, ground share, DTM and nDSM min/max/mean, nDSM p95);
- the artifact IDs, value semantics and limitations — or the real failure reason.

**Soft failure.** `ground_filter_status` (`not_requested`/`processing`/`completed`/`failed`) mirrors `semantic_status`. A filter error, an invariant violation or a write failure sets `failed` with the reason. Partial files are removed and no DTM/nDSM rows are written. The job still completes, and `metric_elevation`/`dsm` survive.

**Consumers.**
- The 2D layers and pixel inspection show DTM and nDSM, with distinct unavailable reasons for "no gate-passed calibration", "ground filtering failed" and "job predates P1-3".
- Measurements accept `dtm` as elevation.
- `ndsm` is **explicitly rejected** by point, distance and profile measurements (nDSM measurements are future object-height work).
- Reports include a DTM/nDSM section and CSV statistics, and the bundles include `dtm.tif`/`ndsm.tif`.
- **Unchanged:** disaster screening still accepts only `metric_elevation`/`dsm`, and 3D terrain still uses `dsm`/`relative_depth` (`TERRAIN_SOURCE_ARTIFACT_TYPES`).

**Configuration** (literature starting values, not tuned or validated for monocular surfaces; persisted with every result):
- `GROUND_FILTER_MAX_WINDOW_M = 20`
- `GROUND_FILTER_SLOPE = 0.15`
- `GROUND_FILTER_INITIAL_THRESHOLD = 0.5`
- `GROUND_FILTER_MAX_THRESHOLD = 3.0`
- `GROUND_FILTER_POLICY_VERSION = "v1"`

**Limitations.**
- Objects wider than the max window stay "ground".
- Terrain steeper than `s` can be cut down and appear as objects.
- Objects lower than `dh0` stay "ground".
- Under objects on sloping ground the fill is flat, so nDSM is overestimated on the downhill side.
- The thresholds assume the elevation unit equals the horizontal unit (metres).
- The monocular surface represents objects only approximately, and nothing validates nDSM heights. The P1-2 gate measures overall agreement with the reference, not object heights.

### 3.13 Calibration residuals at sample locations (implemented, P1-5)

**Definition.** `residual = predicted calibrated elevation − reference elevation`, the convention P1-2 already uses for `bias`. Units are the calibration reference's own units; the system never claims metres. Positive means the calibrated surface is higher than the reference at that sample.

**Points only.** Residuals exist only at the valid P1-2 calibration samples: the stride-grid pixel centres for a DEM, the surveyed points for GCPs. Nothing is interpolated, and there is no residual raster. Pixels between samples have no reference value that P1-2 aligned to them, and they are neither in-sample nor independent of their neighbours.

**Two kinds, never conflated.**
- **Held-out (default):** each sample's own prediction from P1-2's cross-validation. That is the fold model fitted without the sample's spatial block (DEM, `leave_one_spatial_block_out`) or without the point itself (GCP, `leave_one_out`). `CrossValidationResult` now exposes the per-sample `heldout_predictions`/`sample_fold_ids` it already computed. They are taken verbatim and never recomputed from the production fit, and `as_dict()` never serializes them.
- **Fit:** the production a/b applied to each sample. This is in-sample, labelled "not validation".

Invariants, all tested bit-exactly:
- The mean, RMSE and MAE of the held-out residuals equal the persisted `cross_validation` values.
- Each fold's sum of squared residuals equals its `heldout_sse`.
- Each held-out prediction equals its fold's persisted a/b applied to the sample's depth.
- Changing the reference inside a block never changes that block's held-out predictions.

**When it runs.** Only for a `CALIBRATED` (gate-passed) job, inside the calibration stage. Uncalibrated, failed, gate-rejected and pre-P1-5 jobs get no artifact and no backfill. P1-2's diagnostics remain the explanation for a rejection. A failure while building residuals is recorded as `calibration_residuals_error` and never changes the P1-2 outcome.

**Artifact.** `calibration_residuals` is an RFC 7946 GeoJSON FeatureCollection (WGS84 lon/lat, `application/geo+json`) with one Point per valid sample. Each carries its row/col, source-CRS x/y, depth, reference, both predictions and residuals, the production inlier flag and `fold_id`. DEM samples also carry `block_id`/`reference_cell_id`, and GCP samples carry `gcp_index`. Its `artifact_metadata` holds the definition, units, disclaimer, per-kind statistics, per-block held-out summaries and provenance. The job's `calibration_metadata` gains only `calibration_residuals_artifact_id`. There is no migration.

**Consumers.**
- **API:** `GET …/artifacts/{id}/calibration-residuals` returns it; downloads are named `.geojson`.
- **Kept out of raster paths:** the residuals are not in `layers`. `artifact_raster_path` rejects the artifact, so preview, value, terrain and measurement routes return 422.
- **Visualization context:** a separate `calibration_residuals` entry gives availability or the real reason.
- **Map:** a Terrain-sidebar card and 2D circle markers. The diverging colour scale is centred on 0 and symmetric at max |r| of the kind shown; it is display-only, not a threshold. A black ring marks production-fit outliers. Clicking a marker in inspection mode shows its values; markers are non-interactive in measurement modes.
- **Reports:** a JSON summary plus per-block (DEM) or per-point (GCP) tables, a PDF section and disclaimer, and a separate CSV section. The bundle file keeps the name `measurements.csv`, and `artifacts/calibration_residuals.geojson` is added to the ZIP.

**Limitations.** Residuals describe agreement with the supplied reference at sample locations only, not absolute accuracy. Held-out values come from fold models, not the production surface. DEM residuals include DEM resolution and cell-reuse effects. There is no 3D display.

### 3.14 2D georegistration and backend-authoritative 2D pixel resolution (implemented, P1-6)

**The defect.** Before P1-6, the 2D map stretched each layer's source-grid preview PNG over the dataset's axis-aligned WGS84 envelope. It also turned a click into a row/col by interpolating linearly inside that envelope. A projected raster is rotated relative to Web Mercator away from its UTM zone's central meridian, so both were wrong. For a 5 km scene 2.4° off the central meridian, the overlay was up to 140 m off and clicks read the wrong pixel by up to 14 px. Every earlier fixture sat on the central meridian, where the error is exactly zero.

**Overlays.** `geospatial/map_overlay.py` draws each layer onto its **own** axis-aligned EPSG:3857 grid and reports the grid's exact WGS84 corners. Leaflet's linear stretch is then exact.
- The grid uses GDAL's suggested resolution and is sized to cover the layer's densified footprint envelope.
- Each overlay pixel takes the source pixel its centre falls in. That is nearest neighbour through an exact PROJ transform and the layer's own inverse affine, the same path `coordinate_to_pixel` uses.
- `rasterio.warp.reproject` is not used here. In the pinned rasterio 1.4.x it always applies GDAL's approximate transformer (0.125 px), which picks neighbouring pixels at boundaries.
- Outside the footprint and at NoData the overlay is transparent. Categorical IDs, RGB and the continuous ramp render as in the source-grid preview.
- **API:** `GET …/visualization/map-preview` for artifacts and datasets. Each layer's `LayerContextOut.map_overlay_bounds` gives its placement. It is null when the layer is not georeferenced; the endpoint then returns 422, and a residual (GeoJSON) artifact also gets 422.
- **No fallback.** A layer without bounds, or whose overlay fails, is reported on the map and never drawn over another box.
- **Unchanged:** the source-grid `/preview` (still used for the 3D texture), the 3D view, and the CRS.Simple path for non-georeferenced sources.

**Clicks.** A georeferenced 2D click carries only its lng/lat, and the frontend never derives a row/col from it (`frontend/src/components/terrain/mapClick.ts`). Inspection and point/coordinate/distance/profile resolve it with `/measurements/pixel` (`coordinate_to_pixel`) against the authoritative raster of the exact layer being sampled. Slope-at-point already resolved on the backend and is unchanged. A point outside that raster reports "outside" and never picks a guessed pixel. New saved measurements store the backend-resolved pixels.

**Scope.** The overlay PNG is a display derivative only and never a source of any value. Measurement algorithms, stored artifacts and historical measurement records are unchanged; measurements saved before P1-6 were not rewritten, flagged or migrated. There is no migration.

**Verified.**
- On an off-meridian UTM 33N fixture (128×128 px at 40 m, ~60°N, 2.9° east of the central meridian), every overlay pixel centre shows exactly the source pixel under it: continuous, categorical, RGB, NoData, and a geographic source with a UTM derivative.
- The old envelope mapping is shown to miss by up to 5 px there, while backend resolution is exact.
- In the browser, a click on a P1-5 residual marker resolves the residual's own row/col. The displayed elevation equals the independently read DSM value, and slope-at-point resolves the same pixel.

### 3.15 Terrain-aware first-person flythrough (implemented, P1-7)

**Before.** First-person used `PointerLockControls` with WASD only. `moveForward` and `moveRight` move parallel to the XZ plane, so altitude was fixed at the orbit camera's height on entry. The only floor was a clamp at the grid's global minimum, so the camera could pass through any higher terrain.

**Flight surface = rendered surface** (`frontend/src/components/terrain/flythrough.ts`, pure and unit-tested). World Y is taken from the mesh's own position buffer (`buildTerrainGeometry`), so exaggeration and the relative-depth gamma are whatever the mesh already applied; no second height formula exists.
- Height is interpolated on the mesh's own triangles: each quad is split along the (r, c+1)–(r+1, c) diagonal and exists only when all four corners are finite.
- The Vitest suite checks this against a Three.js raycast on the real mesh.
- The flight surface is rebuilt whenever the geometry is.

**Flight step (`stepFlight`).**
- **Controls:** WASD moves relative to the camera heading, Space/Shift move vertically, and +/- scale speed by 1.5 (limited to 1/32–32× the default).
- **Horizontal limit:** the footprint plus 10% of its extent on each side.
- **Clearance on the whole path:** the camera is constrained at every point where the straight horizontal path crosses a mesh triangle edge (col, row or col + row = integer), and at both ends. Between those points both the surface and the path are linear, so the whole step stays at or above ground + minimum clearance.
- **No tunnelling:** a lift over terrain is kept, so the camera climbs over a ridge and stays on it rather than reappearing beyond it. One large step gives exactly the result of many small ones.
- **No surface:** over NoData, sky or outside the grid nothing is imposed and no height is invented.
- **Terrain-follow (F, off by default):** holds exactly ground + the clearance it was switched on at. Space/Shift adjust that clearance, never below the minimum.

**Entry pose (deterministic):** the centre of the south (image-bottom) footprint edge, at the entry clearance above the surface there (or above the highest rendered vertex if that point has no surface), looking level toward the footprint centre. Exiting restores the orbit view the user had before entering.

**Clearance, speed and HUD.**
- **Minimum clearance:** DSM, 2 reference units (× exaggeration in world units). Relative depth, 1% of the larger horizontal extent, in visual units.
- **Entry clearance:** 10× the minimum, or 5% of the extent if that is larger.
- **HUD (updated about 10×/s):** map coordinate in the grid's local CRS (the frame the 3D click path already sends to `/measurements/pixel`), or the source pixel when not georeferenced; the display-grid ground value; height above ground; heading (clockwise from north, where north is the image top); speed; and the follow state. For a DSM, ground and clearance have exaggeration removed. Relative depth is labelled "relative/unitless" and "visual units" and is never called elevation.

**Scope.** Ground values are display-grid values (at most 256 px, block-averaged), used for flight and the HUD only. Authoritative values stay with inspection and measurement on the full-resolution raster. No backend, API, database or migration change. The mesh formulas, exaggeration, terrain grid, 3D texture, click-to-pixel path, orbit and top-down cameras are unchanged.

### 3.16 Waypoint flythrough with playback and recording (implemented, P1-8)

**Waypoints** (`frontend/src/components/terrain/flythroughPath.ts`) are stored in the terrain grid's local frame (world = local − half-extent), the frame P1-7 flight uses.
- **3D click:** the raycast hit's exact grid-local (x, z).
- **Georeferenced 2D click:** lng/lat is converted by `GET …/visualization/terrain/local-coordinate?lng=&lat=`.
  - The endpoint is read-only and owner-scoped. It calls the same `extract_terrain_grid` the 3D terrain is built from, so the local CRS and origin are identical.
  - It returns `local_crs`, `map_x`, `map_y` and `in_footprint` (inside the mesh's vertex extent). Nothing is adjusted.
  - It returns 422 for a non-terrain artifact, a non-georeferenced terrain or an invalid coordinate.
- **Non-georeferenced 2D click:** the source pixel is scaled onto the grid.
- **Validation:** a waypoint must be in the footprint, on rendered surface, and at least one cell from the previous waypoint. An invalid waypoint is rejected with the reason and never moved.

**Path.** A centripetal Catmull-Rom curve (α = 0.5, mirrored phantom end points, through every waypoint) is sampled once into a polyline with chords of at most 0.25 cell. **That polyline is the authoritative flown path:** clearance, arc length, playback position and heading all use it, and the spline is never re-evaluated.
- Overshoot beyond P1-7's flight bounds is clamped and counted.
- Every point where the polyline crosses a rendered-mesh triangle edge (P1-7's exported `triangleEdgeCrossings`) is inserted on the polyline, so its shape is unchanged.
- **Height:** a sliding-window maximum (±2 cells) of ground + target clearance over those points.
- **Why that's sufficient:** between consecutive points both the surface and the path are linear, so the whole path stays at least the target clearance above the rendered surface.
- **No surface in the window:** height is interpolated between constrained neighbours; no ground is invented.
- **Target clearance:** P1-7's entry clearance.
- **Where the path is built:** `TerrainView3D` builds it from its own rendered flight surface, so path and render cannot disagree. It is rebuilt when the waypoints or the exaggeration change.

**Playback** is deterministic by time: position = `pathStateAt(path, speed × t)`, linear between flown vertices.
- Heading and pitch look ahead max(3 cells, 1 s of travel) along the polyline. Pitch is limited to ±30°, and the final direction is kept at the end.
- **Controls:** Play, Pause, Resume, Restart, Stop or Esc, and speed 0.5–4× P1-7's default.
- **At the end:** the final frame is held with state "finished".
- **Stop:** restores the pre-playback orbit view.
- **While playing:** 3D clicks are ignored, and entering first-person stops playback.
- **HUD:** P1-7's readout, plus progress, path time and target clearance.

**Recording** uses `MediaRecorder` over `canvas.captureStream(30)`, preferring WebM VP9, then VP8, then plain WebM.
- It records one full playback at 1× from the start and downloads `terrainx-flythrough-<artifact>.webm` client-side; nothing is uploaded.
- Stop or Esc discards the partial recording.
- If the browser can't record, the control is disabled with the real reason.
- Frame content follows path time; frame count follows the browser's render rate.

**Scope.** Paths are client-only, with an optional JSON download (terrain artifact, local CRS, origin, waypoints, clearance, speed). There is no database change and no migration.
- Clearance is measured against the display grid (at most 256 px), which the UI states.
- 2D waypoints are listed in the sidebar and not drawn on the 2D map.
- P1-7 flight, the mesh, the terrain grid, the sky mask, texture, click-to-pixel, and orbit/top-down cameras are unchanged; the only P1-7 change is exporting `triangleEdgeCrossings`.

### 3.17 3D terrain mesh export (implemented, P1-9)

**Two different representations.** The browser mesh (`terrainMesh.ts`) is a *display/flythrough* representation: vertices at the same cell centres (since D1), display exaggeration, relative-depth gamma, centred. The exported GLB is a *physical / unitless terrain-grid* representation: vertices at **cell centres** with the **raw grid values**, and no baseline, exaggeration, gamma or centring. They are not vertex-for-vertex identical, by design.

**Export** (`GET …/artifacts/{id}/visualization/terrain/mesh.glb?resolution=256|512&texture=true|false`; `geospatial/mesh_export.py`).
- **Source and resolutions:** `dsm` and `relative_depth` terrain sources only, at 256 or 512 px only. Any other resolution returns 422, and 1024 is not offered.
- **Grid:** the same `extract_terrain_grid` (plus the sky mask for relative depth) the 3D view uses, called with the resolution as `max_dimension`. Extraction itself is unchanged.
- **Triangulation:** the renderer's rule. A quad is triangulated only when all four cells are finite, using the same diagonal, counter-clockwise from +Y.
- **No geometry without a surface:** unused vertices are dropped, so NoData and sky have no geometry at all, and disconnected regions stay disconnected.
- **Normals and container:** normals come from the physical geometry. The GLB 2.0 is written with `struct`/`json`/numpy (no new dependency), with accessor min/max and 4-byte alignment.
- **No stored state:** it is built in memory in a worker thread under a semaphore (`MESH_EXPORT_MAX_CONCURRENT = 2`). No temporary files, no persistence, no migration.
- **Ownership:** ownership is checked through the existing chain, and the filename is built from the artifact UUID.

**Coordinates.** glTF is Y-up.
- **Georeferenced:** `x` = east offset and `z` = south offset from the centre of cell (0, 0), in `local_crs` units. `map_x = origin_x + x`, `map_y = origin_y − z`.
- **Not georeferenced:** source-pixel units. `pixel_col = origin_x + x`, `pixel_row = origin_y + z`.
- **Heights:** `y` is the raw grid value.
  - DSM: calibrated surface elevation in the reference's (unverified) vertical units.
  - Relative depth: raw and unitless. The metadata says it is not a physical height and that horizontal and vertical units are not comparable, and never calls it elevation.
- **Precision:** the float64 origin lives in `asset.extras.terrainx`, alongside the CRS (EPSG and WKT), axis mapping, units, `height_kind`, grid/source dimensions, decimation and reprojection flags, whether the sky mask was applied, counts, texture status, and provenance (artifact, job, dataset, calibration status, quality gate). The file is deterministic.

**Texture.** The source RGB is embedded as a PNG (at most 2048 px, block-averaged) only when it aligns with the grid pixel-for-pixel: the source is RGB uint8, the grid isn't reprojected, and the dimensions match. UVs are the cell centres, `((c + 0.5)/w, (r + 0.5)/h)`. Otherwise the texture is omitted with the reason in `extras` and in the `X-TerrainX-Texture` header.

**Verified.**
- An independent test GLB reader (`backend/tests/glb_reader.py`) and three.js `GLTFLoader` (Playwright).
- Every vertex's map coordinate equals its raster cell centre, including an off-meridian UTM round trip back to the same pixel through `/measurements/pixel`.
- Heights equal the grid/raster values bit-exactly. Triangles = 2 × valid quads, and nothing is placed over NoData.
- Texture pixels equal the source pixels, and the bytes are identical after changing the on-screen exaggeration.
- **Limitation:** the E2E fixtures contain no NoData in their terrain grids (the sky mask does not trigger on them), so real NoData holes are verified in the backend API tests on stored rasters with NoData. Playwright checks the same invariants on real data.

### 4.2 Backend API (`backend/`)
FastAPI, versioned REST routes under `/api/v1`. Responsibilities:
- JWT-based auth (access token; role-based route protection).
- CRUD for `projects`, `datasets`.
- Dataset upload handling: streams to `storage/`, triggers metadata extraction, records `datasets` row with status (`uploaded` → `validating` → `valid`/`invalid`/`failed`) — see §3.1 for the implemented flow.
- Analysis job lifecycle (implemented, §3.2): create job with versioned, validated parameters, enqueue to RQ, expose status/stage polling, store the job's own execution summary.
- Visualization endpoints (implemented, Phase 5 §3.5, extended Phase 6 §3.6): real context/metadata/preview/window/terrain-grid routes over existing dataset/artifact rows — read-only, no new persisted state; Phase 6 added categorical (region-ID) rendering to the same routes rather than new ones.
- Measurement endpoints (implemented, Phase 7, §3.7): real point/distance/profile/coordinate computation (live, unsaved) plus persisted CRUD (`measurements` table) — the first Phase 5-style read-only pattern extended with real backend-side persistence.
- Structured logging (JSON, request-scoped correlation IDs) and centralized error handling (typed exceptions → consistent error envelope).
- Pydantic models for request/response validation.

### 4.3 AI (`ai/`)
- `depth_estimator.py` (implemented): the model-agnostic `DepthEstimator` ABC (`load()`/`predict()`/`info()`) plus the `DepthPrediction`/`DepthModelInfo` dataclasses every implementation returns.
- `depth_anything.py` (implemented): the concrete `DepthAnythingV2Estimator` — see §3.3 for the full model card and behavior.
- `device.py` (implemented): runtime CUDA-availability detection, CPU fallback — never assumes a GPU.
- `registry.py` (implemented): the process-local singleton that avoids reloading the model per job (§3.3); Phase 6 added a second, independent singleton (`get_semantic_estimator`) rather than unifying the two behind one dispatcher (§3.6).
- `semantic_estimator.py` (implemented, Phase 6): the model-agnostic `SemanticEstimator` ABC (`load()`/`predict()`/`info()`) plus the `SemanticPrediction`/`RegionInfo`/`SemanticModelInfo` dataclasses — deliberately a separate interface from `DepthEstimator`/`DepthPrediction`, never a generic "prediction" object shared between the two, since a categorical label map + per-region metadata is a fundamentally different shape from one continuous float array (§3.6).
- `mobile_sam.py` (implemented, Phase 6): the concrete `MobileSAMEstimator` — real class-agnostic automatic mask generation, checkpoint download/verification, deterministic overlap-resolution policy. See §3.6 for the full model card and behavior.
- Uncertainty estimation derived from actual model output statistics, never a fabricated constant — still not implemented for depth (Depth Anything V2 has no native per-pixel uncertainty, and §3.6 deliberately does not infer one); Phase 6 instead adds real image-quality indicators and exposes the segmentation model's own mask-stability score where available — both explicitly distinguished from "uncertainty"/"confidence" (§3.6).

### 4.4 Geospatial (`geospatial/`)
- `raster_metadata.py` (implemented): opens any uploaded raster with rasterio/GDAL and reports real width/height/band count, and — only when GDAL actually reports a CRS — the EPSG code (or WKT fallback) and true geographic bounding box. Raises `RasterValidationError` for anything GDAL can't read; never guesses.
- `raster_io.py` (implemented, Phase 3; extended Phase 6): `read_raster_array()` reads real pixel data plus real CRS/transform (companion to `raster_metadata.py`, which is structural-metadata-only); `write_single_band_float32()` writes a real single-band float32 GeoTIFF, carrying CRS/transform only when both are given — never fabricating georeferencing for a non-georeferenced source. Phase 6 added `write_single_band_categorical()` — a real single-band `uint32` GeoTIFF with an explicit NoData tag, for region-ID rasters that must never be treated as continuous/interpolatable (§3.6). Used by the depth pipeline (§3.3), calibration (§3.4), and semantic segmentation (§3.6); general-purpose enough for future terrain-derivative outputs too.
- `calibration.py` (implemented, Phase 4): the pure scientific core of metric calibration — `sample_dem_pairs`/`sample_gcp_pairs` (CRS-aware reference sampling), `fit_robust_affine` (OLS + iterative sigma-clipping), `compute_validation_metrics` (real MAE/RMSE/bias/residuals). Independent of the backend/FastAPI layer by design — imported by `app/services/calibration_pipeline.py`, never the reverse. See §3.4 for the full scientific rationale and limitations.
- `raster_preview.py` (implemented, Phase 5; extended Phase 6): real raster statistics (`compute_raster_statistics`) and presentation-only PNG generation (`generate_preview_png`/`generate_window_png`/`sample_pixel_value`) for the visualization workspace — see §3.5. Phase 6 added a fully separate categorical rendering path (`generate_categorical_preview_png`/`generate_categorical_window_png`/`_region_color`) for region-ID rasters — deterministic golden-angle-hue colors, `Resampling.nearest` exclusively, never reusing the continuous viridis-like ramp (§3.6).
- `terrain_grid.py` (implemented, Phase 5; reused Phase 7): real, downsampled DSM height-grid extraction plus the local metric coordinate frame used by the 3D viewer — see §3.5. Untouched by Phase 6 — semantic regions are never a height source (§3.6). `select_utm_crs` (formerly module-private `_select_utm_crs`) was made a public, shared function in Phase 7 so `geospatial/measurements.py` reuses the exact same real UTM-zone-selection rule for geographic-CRS distance/profile reprojection, rather than a second, divergent implementation.
- `image_quality.py` (implemented, Phase 6): real, model-independent image-quality indicators (`compute_image_quality`) computed directly from RGB pixel data — sharpness proxy, exposure fractions, luminance range, valid-pixel ratio. Explicitly documented as measuring the uploaded image's own properties only, never model confidence or segmentation/elevation accuracy — see §3.6.
- `measurements.py` (implemented, Phase 7): real point elevation, distance, terrain-profile, and coordinate/pixel conversion primitives — `sample_point_elevation`, `pixel_to_coordinate`, `compute_distance`, `sample_profile`, `coordinate_to_pixel`. See §3.7 for the full scientific rationale, the deterministic profile-sampling policy, and the 3D-terrain coordinate-space bug fix.
- GDAL/rasterio reprojection (`rasterio.warp.transform`/`reproject`) used for cross-CRS DEM/GCP alignment (§3.4), the Phase 5 visualization workspace's WGS84 bounds/local-UTM terrain frame (§3.5), and Phase 7's geographic-CRS distance/profile/coordinate reprojection (§3.7) — broader reprojection use (e.g. resampling a whole raster to a target CRS/resolution as a persisted artifact) remains future work.
- GeoPandas for vector reference data (boundaries, complex AOIs) — not yet used; Phase 4's GCP references are plain CSV, not a GeoPandas-backed format.
- Slope/aspect terrain derivatives — not yet implemented (from a later phase).
- Flood/inundation modeling: user-specified water level → real hydrological fill/connectivity computation over the DSM, not a pre-baked overlay. Not yet implemented (from Phase 8).

### 4.5 Database (`database/`)
PostgreSQL + PostGIS. Alembic migrations. Core entities:

- `users` — credentials (hashed), role.
- `projects` — owned by a user, groups datasets/analyses.
- `datasets` (implemented) — one row per uploaded file: `original_filename` (display only, never used for paths), `storage_key`, server-detected `file_type`/`mime_type`, `file_size_bytes`, `status` (`uploaded`/`validating`/`valid`/`invalid`/`failed`) + `validation_error`, and — populated only for files GDAL actually reads — `width`/`height`/`bands`/`is_georeferenced`/`crs`/`bbox_min_x..bbox_max_y`. Phase 4 added `role` (`source_image`/`dem_reference`/`gcp_reference` — see §3.4; existing rows backfill to `source_image` via `server_default`, so Phase 1 data keeps working unchanged) and `gcp_crs`/`gcp_points` (populated only for `role=gcp_reference`). FK to `projects.id` with `ON DELETE CASCADE`.
- `analysis_jobs` (implemented) — FKs to `projects`/`datasets`/`users` (all `ON DELETE CASCADE`), `status` + `current_stage` enums, `error_message`, versioned `parameters` (JSONB, exactly what the job was created with — from Phase 4, may include a `dem_reference_dataset_id`/`gcp_reference_dataset_id`; from Phase 6, may include `enable_semantic_segmentation`), `execution_summary` (JSONB, what the job's own run actually verified/computed, plus — from Phase 6 — a real `image_quality` sub-object computed for every job), `created_at`/`started_at`/`completed_at`/`updated_at`. Phase 4 added `calibration_status` (enum, default `uncalibrated`) and `calibration_metadata` (JSONB) — see §3.4. Phase 6 added `semantic_status` (enum, default `not_requested`) and `semantic_metadata` (JSONB) — see §3.6 — plus four new `current_stage` enum values. Indexed on `project_id`, `dataset_id`, `user_id`, `status`, `created_at`; a partial unique index on `dataset_id` (`WHERE status IN ('queued','running')`) enforces at most one active job per dataset. See §3.2.
- `analysis_artifacts` (implemented; populated from Phase 3) — real scientific/geospatial output files: `analysis_job_id` FK, `artifact_type` (`relative_depth` from Phase 3; `metric_elevation` and `dsm` from Phase 4, see §3.4; `semantic_segmentation` from Phase 6, see §3.6 — a plain `String(50)` column, so a new artifact type needs no migration), `storage_key`, `mime_type`, `file_size_bytes`, `artifact_metadata` (JSONB — for `relative_depth`: model/device/dimensions/timing/real depth min-max-mean/georeferencing/value-semantics disclaimer, see §3.3; for `metric_elevation`/`dsm`: the full calibration metadata, provenance-chain artifact IDs, real elevation min/max/mean, and a limitations string, see §3.4; for `semantic_segmentation`: model/device/timing, real region list with per-region area/bbox/mask-stability, provenance IDs, and the class-agnostic value-semantics disclaimer, see §3.6). Phase 2 inserted zero rows here by design (nothing real to record yet); Phase 3 is the first phase with a real output to put in this table.
- `terrain_results` — DSM/depth/elevation/slope/confidence layer references + summary stats, as a queryable aggregate over `analysis_artifacts`. Not yet implemented — Phase 4's DSM/metric-elevation output lives directly in `analysis_artifacts` (above) without a separate summary table yet.
- `measurements` (implemented, Phase 7) — real, persisted point/distance/profile/coordinate measurements: `project_id`/`analysis_job_id`/`artifact_id`/`user_id` FKs (all `ON DELETE CASCADE`), a `measurement_type` enum, and `input_data`/`result_data` JSONB. See §3.7.
- `hazard_results` — flood/slope-hazard scenario outputs tied to a job + input water level. Not yet implemented (from Phase 8).
- `reports` — generated export bundles (GeoTIFF/GeoJSON/report PDF) with metadata. Not yet implemented (from Phase 9).
- `audit_logs` — auth events, mutating actions, job lifecycle events. Not yet implemented (from Phase 11).

**Phase 5 added no tables and required no migration** — the visualization workspace (§3.5) is entirely read-only over the rows and files described above, computing everything else (statistics, previews, terrain grids) on demand from the real stored rasters.

**Phase 6 added no new table** (the `semantic_segmentation` artifact type reuses `analysis_artifacts` exactly like every other artifact type) but did require one hand-written migration (`c0b7e6dffad9_add_semantic_segmentation_support.py`) for the two new `analysis_jobs` columns and the four new `current_stage` enum values — hand-written rather than autogenerated because Postgres enum types are append-only and Alembic autogenerate cannot diff new enum *members* on an existing type (`ALTER TYPE ... ADD VALUE` was written explicitly), and because `add_column` referencing a brand-new enum type requires that type to be created first (`sa.Enum(...).create(checkfirst=True)`). Verified with `alembic check` (zero drift) and a live enum-order check against Postgres directly.

**Phase 7 added one new table** (`measurements`) via a plain autogenerated migration (`45fde3a116eb_add_measurements_table.py`) — unlike Phase 6's enum-member-addition case, a brand-new table with a brand-new enum type autogenerates cleanly; the only hand-edit needed was adding the same "drop the enum type explicitly in `downgrade()`" line already established in `4d5fb992ace1_add_datasets_table.py` (autogenerate creates the enum type on `upgrade()` but never adds a matching `drop` to its generated `downgrade()`). Verified with `alembic check` (zero drift) and a real downgrade-then-upgrade cycle (confirms the enum-type-drop fix actually prevents a "type already exists" failure).

### 4.6 Storage (`storage/`)
`StorageBackend` interface with one implementation so far, `LocalStorageBackend` (implemented): a directory (`STORAGE_ROOT`, bind-mounted from the host at `../storage` in dev) holding `projects/{project_id}/datasets/{dataset_id}/original.{ext}`. Every key is resolved and checked to stay under the storage root (defense-in-depth path-traversal guard) even though keys are always server-generated from UUIDs, never from client input. Swappable for an S3-compatible backend later without touching calling code in `backend/`.

### 4.7 Docker (`docker/`)
`docker-compose.yml` for local dev: `postgres` (PostGIS image), `redis`, `backend`, `worker`, `frontend` (dev server). Production Dockerfiles built from the same images, differing only in command/env.

`backend/Dockerfile` installs `torch` in its own layer, before `requirements.txt`, from PyTorch's dedicated CPU-only wheel index (`--index-url https://download.pytorch.org/whl/cpu`) rather than mixing it into `requirements.txt` — the two indexes can serve the *same* version string with very different (CUDA-bundled vs. CPU-only) contents, so a dedicated, unambiguous install step is the reliable way to guarantee the CPU build regardless of pip's index-resolution order. No CUDA-specific packages are installed anywhere in this image. Both `backend` and `worker` set `HF_HOME=/app/storage/model_cache`, inside the same persistent `../storage` bind mount already used for dataset storage (§3.1) — one mount, two purposes, both surviving container recreation.

**Phase 6 additions**: the same CPU wheel index install was upgraded from torch-only to `torch==2.5.1` + `torchvision==0.20.1` together (torchvision is a hard dependency of MobileSAM's `SamAutomaticMaskGenerator`, not needed by Phase 3 alone); `git` is installed via apt specifically so pip can install the `mobile_sam` package directly from its pinned GitHub commit (no PyPI release exists for it); `timm==1.0.29` was added to `requirements.txt` after discovering — only by actually attempting the import, not by reading `mobile_sam`'s own declared dependencies, which omit it — that `mobile_sam.modeling.tiny_vit_sam` hard-imports `timm.models.layers.DropPath`. MobileSAM's checkpoint itself is never baked into the image (fetched lazily at runtime into the same `HF_HOME`-rooted persistent mount as Depth Anything V2's weights, §3.6) — consistent with the existing "weights are downloaded, not shipped in the image" convention.

## 5. Security

- Passwords hashed (Argon2id), JWT (HS256) signed with a secret from the environment, short-lived access tokens.
- File upload validation (implemented): real magic-byte sniffing decides the format — client-supplied filename/extension/Content-Type are never trusted for that decision; a configurable max size (`MAX_UPLOAD_SIZE_MB`) is enforced both via an early `Content-Length` check and while streaming; storage keys are always server-generated from a UUID, never from the client filename, and `LocalStorageBackend` independently guards against path traversal.
- Per-project authorization checks on every project/dataset/analysis route: ownership mismatches and non-existent resources both return 404 (never 403 or a data leak), so resource existence is never revealed to a non-owner (no IDOR). Datasets are checked against their claimed `project_id`; analysis jobs are checked against their claimed `project_id`, and creation additionally re-validates that the dataset belongs to that same project — manipulating IDs in the URL cannot reach another user's dataset or job.
- Analysis parameters are a `pydantic` model with `extra="forbid"` (`AnalysisParametersV1`) — arbitrary client JSON is never persisted as trusted job configuration, and the worker re-validates the stored parameters again before using them. A DEM/GCP reference cited in those parameters is checked against the *same* project both at job-creation time and again by the worker at execution time (§3.4) — a reference ID from another project or another user is rejected exactly like a source dataset would be, and a dataset's `role` is a server-validated enum, never a client-chosen label (uploading a plain image and later citing it as a DEM reference is rejected with a clear error, not silently accepted).
- Artifact routes (`.../analysis/{job_id}/artifacts[/…]`) follow the same ownership chain as jobs: project → job → artifact, each checked, 404 (not 403) on any mismatch; storage keys are always server-generated (`projects/{project_id}/analysis/{job_id}/depth.tif`, `.../metric_elevation.tif`, `.../dsm.tif`), never derived from client input.
- Phase 5 visualization routes (`.../visualization/...`, §3.5) enforce the identical ownership chain via two new shared dependencies (`app/api/deps.py::get_owned_analysis_job`/`get_owned_artifact`) — every context/metadata/preview/window/terrain request is checked project → dataset or project → job → artifact before any file is touched; the frontend never has or needs a raw storage path, and no visualization endpoint accepts an arbitrary filesystem path as input (only database-resolved artifact/dataset IDs). Authenticated image/binary access (previews, terrain grids) goes through `fetch()` with a real `Authorization` header, never a token in a query string, and never a bare `<img src>` against an unauthenticated route. Phase 6's `semantic_segmentation` artifact type reuses these exact same dependencies and routes (§3.6) — no new endpoints, no new ownership logic, verified with the same no-token/wrong-user/wrong-project/valid-owner test matrix as every other artifact type.
- No model weights are downloaded from an untrusted or arbitrary source: the Hugging Face repo ID and revision are hardcoded constants in `ai/depth_anything.py`; MobileSAM's repository, pinned commit, and checkpoint filename are likewise hardcoded constants in `ai/mobile_sam.py` (§3.6) — never client- or config-supplied at runtime, and the downloaded checkpoint is verified against a real, pinned git blob SHA-1 before being trusted (a corrupted or substituted file is rejected outright, never silently used).
- Phase 7's measurement routes (`.../measurements/...`, §3.7) — both the live-compute artifact-scoped routes and the persisted project-scoped CRUD routes — reuse the identical ownership-chain dependencies as visualization (`get_owned_project`/`get_owned_analysis_job`/`get_owned_artifact`), plus a new `get_owned_measurement` following the exact same 404-never-403 shape; verified with the same no-token/wrong-user/cross-project/valid-owner test matrix. A `POST .../measurements` request never trusts a client-supplied result — the server always recomputes it server-side from the request's real input coordinates before persisting, so a malicious or buggy client cannot store a fabricated measurement.
- Secrets via environment variables / `.env` (never committed).

## 6. Extensibility points (deliberately left open, not built now)

- Swapping RQ for Celery/K8s Jobs if job volume grows.
- Extracting `ai/` into a standalone GPU inference service behind an internal API — the `DepthEstimator` interface already isolates model mechanics from orchestration, so this would not require touching `analysis_execution.py`'s stage logic.
- Adding new model versions/architectures via the `DepthEstimator` interface (a `DepthAnythingV2Base`, an entirely different model, ...) without touching pipeline orchestration — `ai/registry.py` is the single place that decides which concrete estimator is used.
- Object storage backend swap in `storage/` (would also relocate `HF_HOME`'s persistence story, currently piggybacking on the same local bind mount).
- New `AnalysisStage` values and a new `AnalysisParametersVN` schema version, without redesigning `analysis_jobs` — Phase 3 and Phase 4 each already demonstrated this, adding four new stage values apiece without touching the status model.
- Real rows in `analysis_artifacts` for new artifact types (`slope`, `hazard_extent`, ...) as later phases produce them, alongside the existing `relative_depth`/`metric_elevation`/`dsm`.
- A real DSM-specific processing step (hydro-flattening, void-filling, terrain/object-top separation) that would make the `dsm` artifact genuinely differ from `metric_elevation` rather than being numerically identical to it (§3.4's known limitation) — the artifact type and provenance chain already exist for this to slot into later.
- Sub-pixel (bilinear) GCP-to-pixel correspondence in place of the current nearest-pixel simplification (§3.4), if a future need justifies the added complexity.
- WebSockets/SSE in place of polling for job status, without changing the job model or service layer.
- Persisted (cached) raster statistics/previews if repeated on-demand computation (§3.5) ever shows up as a real bottleneck — deliberately not built now, since every current raster is small enough (≤4096px per Phase 3's own input policy) for on-demand `out_shape` reads to stay cheap.
- Multi-band or true-color-corrected 3D terrain texturing beyond the current "exact-dimension-match" compatibility check (§3.5), if a future phase adds real raster-to-raster reprojection/resampling as a persisted step rather than only at visualization time.
- A true inverse-CRS pixel lookup for 2D map clicks (replacing the current linear-interpolation-within-bounds approximation, §3.5) if a future dataset's footprint is large or rotated enough for the approximation to matter — Phase 7 (§3.7) added a real backend-authoritative inverse transform (`geospatial.measurements.coordinate_to_pixel`) for *measurement* results and the 3D-terrain click fix specifically, but the 2D map's own image-overlay placement approximation itself was deliberately left as-is (a display-positioning concern, not a measurement-accuracy one).
- A real normalization scheme for non-uint8 (16-bit/float) remote-sensing imagery, if a future need justifies the complexity — deliberately not built now (§3.3's input policy rejects it instead).
- An optional, spatially-verified semantic-region overlay in the 3D terrain view (§3.6) — deliberately not built in Phase 6 (height source stays DSM-only), but the categorical artifact and its real dimensions/CRS already exist for a future phase to add this the same way RGB texturing already checks exact-dimension compatibility (§3.5).
- A genuine per-pixel depth-uncertainty model (e.g. ensemble or Bayesian variants of the depth network) if a future need justifies the added inference cost — Phase 6 deliberately does not fabricate one from existing signals (§3.6).
- Real supervised land-cover/object classification layered *on top of* MobileSAM's class-agnostic regions (e.g. a separate classifier scoring each region), if a future phase needs actual semantic labels — Phase 6's region IDs remain deliberately unlabeled until such a model is added and validated.
- Polygon/area-drawing measurement tools (Phase 7, §3.7, only shipped point and two-point line measurements) if a future need justifies the added interaction complexity.
- Sub-pixel (bilinear) value interpolation for terrain-profile sampling (§3.7), in place of the current nearest-pixel simplification — the same tradeoff already accepted for GCP correspondence (§3.4).
- Real building/object height estimation combining a user-selected `semantic_segmentation` region with a DSM elevation difference — deliberately not built in Phase 7, since it would require either manual class confirmation or a validated classifier layered on the class-agnostic regions (§3.6's own extensibility note).

## 7. Known limitations (intentionally not addressed yet)

Phase 2 (resolved, Phase 11 §3.11):
- ~~If the worker process itself crashes mid-job, the job row stays `running` forever~~ — fixed by `app/services/job_reconciliation.py`'s periodic staleness sweep (Phase 11), verified with a real Docker worker-kill.
- ~~RQ's own default job timeout... leaving the row `running`~~ — fixed by an explicit `ANALYSIS_JOB_TIMEOUT_SECONDS` plus the same reconciliation sweep (Phase 11).
- No automatic retry is configured for failed jobs. This is deliberate: a naive retry could re-run a job that partially failed for a reason unrelated to transience (e.g., a genuinely corrupt file), and combined with the duplicate-job invariant, retry semantics need designing on purpose rather than defaulting on. Still not addressed — explicitly evaluated and deferred in the Phase 11 readiness report (Candidate C).

Phase 3:
- Cancellation cannot interrupt an in-flight model forward pass — `torch.inference_mode()` inference is a single blocking call with no cooperative cancellation point inside it. The pipeline's defensive re-checks (§3.3) ensure a cancelled job never gets its result persisted, but the inference compute itself still runs to completion once started. Phase 11 (§3.11) widened cancellation to `running` jobs specifically on this cooperative, checkpoint-bounded basis — it still never claims to interrupt in-flight inference, and the API/UI say so explicitly.
- ~~The `MODEL_REVISION` pinned in `ai/depth_anything.py` is currently `"main"`~~ — fixed by Phase 11 (§3.11): pinned to the exact immutable commit SHA `"main"` resolved to at pin time.
- No GPU has been available to test the `cuda` code path in `ai/device.py` end-to-end (only that it correctly falls back to `cpu` in this environment) — the logic is straightforward, but it is unverified on real CUDA hardware.
- Depth Anything V2 was trained predominantly on general/ground-level photographic scenes, not nadir remote-sensing imagery; no accuracy claims are made for aerial/satellite input, and none should be inferred from this phase's output — see §3.3's output-semantics section for the full disclaimer.

Phase 4 (see §3.4 for the full scientific limitations discussion):
- The Phase 4 `dsm` artifact is numerically identical to `metric_elevation` — no DSM-specific processing (hydro-flattening, void-filling, terrain/object-top separation) has been implemented yet. The artifact type and provenance chain exist so a later phase can add real DSM processing without a schema change.
- GCP-to-pixel correspondence uses nearest-pixel (`floor()`) indexing, not sub-pixel/bilinear interpolation — a documented simplification that adds unquantified positional error, more noticeable at coarser source resolutions.
- The affine calibration fit is only as good as the reference data supplied; a different DEM/GCP set over the same scene could yield a measurably different scale/offset. Validation metrics (MAE/RMSE/bias) describe fit quality against the specific reference actually used, never a universal accuracy claim.
- Calibration cannot distinguish terrain from object tops (buildings, trees, ...) visible in the source image — this is a fundamental limitation of single-view depth, not something a better fit could resolve.
- Large DEM reference rasters are sampled via `rasterio`'s point-sampling API (never loaded fully into memory), but a DEM with an unusual/exotic format or a very high band count is not specifically optimized for — only the standard single-band elevation case has been exercised.
- No resampling/reprojection of an entire reference raster to a common target CRS/resolution is implemented — only point-level coordinate transformation during sampling (§3.4). A future phase adding raster-to-raster calibration outputs at a different resolution than the source would need this.

Phase 5 (see §3.5 for the full "Known Phase 5 limitations" list):
- The 3D DSM view renders exactly Phase 4's DSM output (numerically identical to metric elevation) — visualization adds no terrain/object-top separation and is not itself a form of accuracy validation.
- The geographic-CRS -> local-UTM reprojection path in `geospatial/terrain_grid.py` has less real-world exercise in this project's own fixtures than the already-projected-CRS path (every DEM/GCP test fixture in this repo already uses a projected UTM CRS).
- The 2D map's click-to-pixel mapping is a linear approximation within the reprojected WGS84 bounding box, not a true inverse CRS transform. **Fixed in P1-6 (§3.14).**
- RGB texturing in the 3D view requires an exact width/height match between the source image and the terrain grid's source dimensions; no partial/cropped/resampled texture alignment is attempted.
- First-person flythrough uses a cheap "don't sink below the observed minimum elevation" clamp, not per-pixel ground-collision raycasting. **Replaced in P1-7 (§3.15)** by terrain-aware flight on the rendered surface.

Phase 6 (see §3.6 for the full scientific-honesty discussion):
- MobileSAM is genuinely class-agnostic — this phase does not, and cannot, tell a building from a road from a shadow. Anyone needing real land-cover/object classification needs a different, additional, validated model; region IDs here are never a substitute for one.
- Trained predominantly on natural/ground-level photographic scenes (SA-1B), not nadir remote-sensing imagery — region boundaries on aerial/satellite input have not been validated against any ground truth (property lines, building footprints, land-cover maps) in this project.
- No genuine per-pixel depth uncertainty is available or inferred — Depth Anything V2 (§3.3) has no native uncertainty output, and none is fabricated from depth magnitude, gradient, color, or calibration residual.
- Image-quality metrics (sharpness/exposure/valid-pixel-ratio) are real but simple, uncalibrated heuristics over the uploaded image's own pixels — they are not validated blur/exposure measurements against any photographic standard, and they say nothing about the correctness of any downstream model output.
- Mask-stability scores are only as meaningful as SAM's own training/calibration of that signal — this project has not independently validated that a higher `stability_score` genuinely correlates with a more useful region boundary for remote-sensing imagery specifically.
- Cancellation cannot interrupt in-flight MobileSAM inference (same fundamental limitation as Phase 3's depth inference, §3.3/§7) — the defensive checks before and after inference ensure a cancelled job's segmentation result is never persisted, but the compute itself still runs to completion once started.
- `MAX_SEMANTIC_INPUT_DIMENSION_PX`'s memory-safety downsampling (and the resulting nearest-neighbor upsampling of the label map back to source resolution) means a very large source image's segmentation boundaries are computed at reduced resolution, then coarsened back up — real, but not full-source-resolution precision for images exceeding the bound.
- No 3D visualization of segmentation regions was added in this phase (§3.5/§6) — the categorical layer is 2D-only for now.

Phase 7 (see §3.7 for the full scientific-honesty discussion):
- No polygon/area-drawing measurement tool — only point elevation, two-point distance, two-point profile, and single-point coordinate lookup.
- Terrain-profile value lookup uses nearest-pixel indexing, not sub-pixel/bilinear interpolation — the same documented simplification already accepted for GCP correspondence (§3.4), with the same unquantified positional-error caveat at coarse resolutions.
- A calibrated elevation's real-world unit remains genuinely unspecified (Phase 4's own unresolved limitation, §3.4) — Phase 7 reports this honestly in every measurement result rather than resolving it; this is not a new Phase 7 gap, it is Phase 4's existing one surfaced consistently in a new place.
- Building/object height estimation is not implemented — a DSM surface-elevation difference between two measured points is a real number, but is never automatically presented as a building or object height, since no ground/object-top separation exists in the DSM (§3.4's known limitation #2).
- The 2D map's own image-overlay click-to-pixel approximation (linear interpolation within the reprojected WGS84 bounding box, listed under Phase 5 above) was deliberately left unchanged — Phase 7 added a real backend-authoritative inverse-transform endpoint (`.../measurements/pixel`) for measurement purposes and for the 3D-terrain click fix specifically, but did not retrofit the 2D map's own overlay-placement code path, which remains a display-positioning approximation, not a measurement result. **Fixed in P1-6 (§3.14).**
- The geographic-CRS distance/profile reprojection path (§3.7) shares the same "less real-world exercise than the projected-CRS path" caveat already noted for `geospatial/terrain_grid.py` under Phase 5 — verified with synthetic geographic-CRS test fixtures and an independent haversine cross-check, but no real geographic-CRS DEM/GCP fixture exists elsewhere in this project's own test suite.
- Distance/profile calculations are planimetric (horizontal) only — they do not account for real terrain relief (slope) between the two measured points, and are never claimed to be survey-grade or ground-truth accurate.
