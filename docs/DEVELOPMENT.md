# TERRAIN-X Development Conventions

## Local environment setup

**Backend**
```bash
cd backend
python -m venv .venv
.venv\Scripts\activate        # PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
```
Never install backend/AI/geospatial dependencies into the global Python — always use the venv (or the Docker image, which is the source of truth for what "correct" dependencies look like, since GDAL native installs are unreliable on Windows).

**Frontend**
```bash
cd frontend
npm install
npm run dev
```

**Full stack (DB, Redis, backend, worker)**
```bash
cd docker
docker compose up
```

**Verifying the depth model is installed and working** (Phase 3): the first analysis job in a fresh environment downloads ~99 MB of weights from Hugging Face — this needs outbound network access once. To check it explicitly rather than waiting for a job:
```bash
docker compose exec worker python -c "
from ai.registry import get_depth_estimator
e = get_depth_estimator()
e.load()
print('loaded OK:', e.info())
"
```
A successful run prints the model's `DepthModelInfo` (name/revision/source/license/device) and leaves the weights cached under `storage/model_cache/` (bind-mounted from the host `../storage`, so this survives container restarts — check `du -sh storage/model_cache` on the host to confirm it's populated, roughly 95 MB). If this fails with a network error, the environment lacks the outbound access the first download needs; if it fails any other way, the traceback is the real error to act on (not something the pipeline sanitizes at this level — only the API-facing error message is sanitized).

**Verifying MobileSAM is installed and working** (Phase 6): the checkpoint (~39 MB) is fetched on first use from the pinned commit's raw GitHub URL, verified against a real git blob SHA-1, and cached under `storage/model_cache/mobile_sam/` — a sibling of the Depth Anything V2 cache, same persistent mount, same "survives restarts" property.
```bash
docker compose exec worker python -c "
from ai.registry import get_semantic_estimator
e = get_semantic_estimator()
e.load()
print('loaded OK:', e.info())
"
```
This is a genuinely separate check from the depth model's — `get_semantic_estimator()` is a second, independent `lru_cache` singleton (`ai/registry.py`), not a variant of `get_depth_estimator()`. A real automatic-mask-generation forward pass on a small (~256px) image takes roughly 45 seconds on CPU at this project's configured `points_per_side=16` — this was **measured**, not assumed, and was found to be roughly constant across tested input resolutions (the model's own encoder resizes internally), which is why `MAX_SEMANTIC_INPUT_DIMENSION_PX` is documented as a memory bound, not a speed knob (see `docs/ARCHITECTURE.md` §3.6).

## Repository layout conventions

- `frontend/`, `backend/`, `ai/`, `geospatial/`, `storage/`, `database/`, `docker/`, `docs/` — each is a self-contained concern. `ai/`, `geospatial/`, and `storage/` must never import from `backend/` (backend imports them, not the reverse) — keeps them independently extractable into services later.
- No cross-cutting "utils" dumping ground — a helper lives in the module that owns the concept it helps with.
- Because `ai/`/`geospatial/`/`storage/` are top-level siblings of `backend/`, the backend/worker Docker build context is the repo root (`docker/docker-compose.yml`: `context: ..`, `dockerfile: backend/Dockerfile`) so the image can include all of them; the root `.dockerignore` applies, not one inside `backend/`. In dev, each is bind-mounted individually into the container alongside `backend/` for hot-reload — if you add a fourth top-level package that the backend imports, mount it the same way in `docker-compose.yml` or it will `ModuleNotFoundError` at runtime despite being present on the host.

## Python (backend, ai, geospatial)

- Formatting/linting: `black` + `ruff`.
- Type hints required on function signatures in `backend/` and `ai/`/`geospatial/` public interfaces.
- Pydantic models for all API request/response schemas — no raw dicts crossing the API boundary.
- Migrations via Alembic; never hand-edit the schema in production, never use `Base.metadata.create_all` outside tests. After changing a model, run `alembic revision --autogenerate` inside the backend container and *read the generated file* — autogenerate can't tell PostGIS's own system tables (`spatial_ref_sys`, etc.) apart from a real drop, which is why `alembic/env.py` excludes them via `include_object`; it also doesn't drop enum types it created when generating a `downgrade()`, so add that by hand (see `alembic/versions/*_add_datasets_table.py` for the pattern) or a downgrade-then-upgrade cycle will fail with "type already exists".
- Adding values to an existing native Postgres enum (e.g. new `AnalysisStage` members) is a case autogenerate **silently produces an empty migration for** — it does not diff enum member lists at all. Write the migration by hand: `op.execute("ALTER TYPE my_enum ADD VALUE IF NOT EXISTS 'new_value' AFTER 'existing_value'")` (see `alembic/versions/*_add_depth_pipeline_stages.py`). Postgres enums are append-only — there is no `DROP VALUE` — so treat every enum value you ship as permanent; the corresponding `downgrade()` should say so explicitly (`raise NotImplementedError(...)`) rather than pretend a clean rollback is possible. This is also why removing a since-superseded stage value (e.g. Phase 2's generic `executing`) is never the right move once it's shipped — keep it in the Python enum forever, just stop producing it for new rows.
- A Python `enum.Enum` mapped via SQLAlchemy's `Enum(..., values_callable=...)` needs `values_callable` set explicitly if you want Postgres to store the member's `.value` (e.g. `"valid"`) — without it, SQLAlchemy stores the member's `.name` (`"VALID"`) instead, which will silently mismatch any `server_default` you write as a lowercase string. See `app/models/dataset.py`.
- Run `pytest`/`uvicorn`/etc. via `python -m <tool>`, not the bare console script — the bare script does not reliably put the working directory on `sys.path`, which surfaces as `ModuleNotFoundError: No module named 'app'` even though the code is right there. `uvicorn app.main:app` in the Docker `CMD` works because uvicorn's own app-import machinery inserts `cwd` into `sys.path`; that trick is specific to uvicorn's app-string loader, not general.
- The async DB engine (`app/db/session.py`) uses `NullPool` deliberately: a pooled asyncpg connection gets bound to the event loop that created it, and reusing it from a different loop (a real failure mode across test runs, and potentially across worker/reload cycles) raises `RuntimeError: Event loop is closed`. `NullPool` trades connection reuse for correctness; revisit only after profiling shows it matters under real load (Phase 11).
- Long-running/CPU-heavy work (inference, raster processing) always runs in the RQ worker, never inline in a FastAPI request handler — dataset upload validation is a deliberate, documented exception (Phase 1): it's fast enough to run synchronously in the request, per `docs/ARCHITECTURE.md` §3.1. Analysis job execution (Phase 2) does run in the worker, via `app/jobs/tasks.py:run_analysis_job` driving an async implementation with `asyncio.run` (RQ calls job functions synchronously — there's no running event loop in that context to `await` into).
- `AsyncSession` with `expire_on_commit=False` (our config, for good reason — see the `NullPool` note above) means an ORM object you loaded earlier will **not** pick up changes made by a separate Core-style `update()`/raw SQL statement in the same session, even after `commit()` — you must `await db.refresh(obj)` to see them. This bit us in the analysis job cancel endpoint, which uses an atomic conditional `UPDATE ... WHERE status='queued'` specifically to avoid a read-then-write race; forgetting the subsequent `refresh()` would have returned the pre-cancel object to the client. Prefer this pattern (atomic Core `update()` + explicit `refresh()`) any time a status transition must be race-safe against a concurrent worker/request.
- When you need a job/row to exist in the database for a test but must guarantee a concurrently-running background worker never touches it (e.g. to test a specific failure branch deterministically, or to avoid racing real job completion in a duplicate-detection test), insert it directly via `AsyncSessionLocal` in the test rather than going through the API — a row never enqueued to Redis is one the real worker container has no way to discover. See `tests/test_analysis.py` for several examples of both styles (real end-to-end via the API + real worker, and direct-insert for deterministic edge cases).
- If an `AnalysisJob` row can be deleted mid-execution (e.g. its project/dataset is deleted while the worker holds it — a real, if rare, race), the next ORM-style `job.field = x; await db.commit()` raises `sqlalchemy.orm.exc.StaleDataError` ("expected to update 1 row(s); 0 were matched"), and the session's transaction is then unusable until rolled back — touching *any* attribute on the poisoned `job` object afterward (even just to log its id) raises a second, more confusing `PendingRollbackError` on top of the first. The fix in `analysis_execution.py`: catch `StaleDataError` specifically (before the generic `except Exception`) and just `await db.rollback()` and log — there's no row left to mark failed; and make failure-handling (`_mark_failed`) take a plain `job_id` and do its own conditional Core `UPDATE ... WHERE id = :id` rather than mutating the possibly-poisoned ORM object, so it's safe to call from *any* exception handler regardless of what state the session was left in.
- Heavy dependencies used only by the worker's actual pipeline (`torch`, `transformers`) are imported *inside* the functions that use them (`ai/depth_anything.py`, `ai/device.py`), never at module top level. The backend API process imports the same call chain (`app.services.analysis_jobs` → `app.jobs.tasks` → `app.services.analysis_execution` → `ai.registry`/`ai.depth_anything`) just to get a function reference for RQ to enqueue — it never calls `.load()`/`.predict()` — so a top-level `import torch` there would slow down every backend start/reload for no reason. Keep this pattern for any future heavy, worker-only dependency.
- `pydantic_model.model_dump()` leaves `uuid.UUID` fields as real `UUID` objects, not strings — fine for in-memory use, but SQLAlchemy's default JSON serializer for a `JSONB` column has no encoder for `UUID` and raises `TypeError: Object of type UUID is not JSON serializable` at `commit()` time, deep inside a stack trace that doesn't obviously point back to the `model_dump()` call. Any schema whose `model_dump()` result gets stored into a JSONB column (e.g. `AnalysisParametersV1`, once it gained `dem_reference_dataset_id`/`gcp_reference_dataset_id`) must dump with `model_dump(mode="json")` instead — this asks Pydantic to pre-serialize `UUID`/`datetime`/etc. into plain JSON-safe values first. See `app/services/analysis_jobs.py::create_analysis_job`.
- A `@model_validator(mode="after")` that does `raise ValueError(...)` (Pydantic's documented way to fail cross-field validation) surfaces through FastAPI as a `RequestValidationError` whose `.errors()` list includes a `ctx` dict containing the *actual raised exception object*, not just its message. A naive `content={"details": exc.errors()}` in a custom exception handler will then raise a second `TypeError: Object of type ValueError is not JSON serializable` when Starlette tries to JSON-encode the error response itself — a 500 instead of the intended 422, and the real validation message never reaches the client. This went unnoticed until Phase 4 added the first request-body model validator that could actually fail (`AnalysisParametersV1`'s at-most-one-reference check) — no earlier schema had one. Fix: strip/stringify any `BaseException` found in `ctx` before handing `exc.errors()` to `JSONResponse` (see `app/main.py::_json_safe_validation_errors`). Any new cross-field validator that raises `ValueError` will hit the same path — it's now handled generically, not per-validator.
- `Depends(get_settings)` (or any `Depends(...)`) binds the actual function *object* at route-definition time — i.e. at module import — not by name lookup at request time. `monkeypatch.setattr(some_module, "get_settings", fake)` after the router module has already been imported does nothing to an already-registered route's dependency, so a test that needs a different settings value for one request (e.g. Phase 5's `MAX_TERRAIN_DIMENSION` downsampling test) must use FastAPI's own `app.dependency_overrides[get_settings] = lambda: modified_settings` instead, and clean it up (`del app.dependency_overrides[get_settings]`) in a `finally`/fixture teardown so it doesn't leak into other tests. See `tests/test_visualization.py::test_terrain_downsampling_respects_max_dimension`.
- `rasterio`'s own documented idiom for reading a decimated raster and still knowing its correct map-space transform is `dataset.transform * dataset.transform.scale(source_width / out_width, source_height / out_height)` applied to the `out_shape=(out_height, out_width)` read — used in both `geospatial/raster_preview.py` and `geospatial/terrain_grid.py`. Don't reach for `rasterio.warp.calculate_default_transform` for this same-CRS decimation case; that function is for reprojecting to a *different* CRS (Phase 5's geographic-to-local-UTM terrain path is the one place this project actually does that).
- When pinning a dependency fetched from a git repository at a specific commit (no PyPI release, e.g. `mobile_sam`), verify the exact commit SHA, its LICENSE file, and any file you'll download from it (e.g. a checkpoint) via **direct calls to the GitHub REST API** (`curl https://api.github.com/repos/<owner>/<repo>/...`), not `WebFetch`/an LLM-summarized page render — a summarization step can produce a plausible-looking but subtly wrong hex string for a commit SHA or file hash, and there is no way to tell from the summary alone that it happened. A git **blob** SHA-1 (what `git hash-object`/the GitHub contents API report for a file) is `sha1("blob " + <byte length> + "\0" + <content>)`, not a plain `sha1(content)` — computing the wrong one silently "verifies" a corrupt or substituted download; see `ai/mobile_sam.py::_git_blob_sha1` and its test (`tests/test_semantic_segmentation.py::test_git_blob_sha1_matches_real_git_hash_object`, which cross-checks the implementation against the real `git hash-object --stdin` command rather than re-deriving the same formula in the test).
- A brand-new table (with a brand-new enum type) autogenerates cleanly with Alembic — unlike adding a *member* to an *existing* enum (the case above), this is a case autogenerate handles correctly. The only manual fix still needed is the same one from `4d5fb992ace1_add_datasets_table.py`: autogenerate creates the enum type in `upgrade()` but never adds a matching `sa.Enum(name=...).drop(op.get_bind(), checkfirst=True)` to its generated `downgrade()` — add that one line by hand, then verify with a real downgrade-then-upgrade cycle (not just `alembic check`, which only checks the *current* head, not that a rollback path actually works). See `45fde3a116eb_add_measurements_table.py` (Phase 7).
- A Pydantic v2 discriminated union (`Annotated[Union[VariantA, VariantB, ...], Field(discriminator="field_name")]`) works directly as a FastAPI request body type — no wrapper model needed. Each variant should use `Literal[SomeEnum.MEMBER]` (not `Literal["member_value"]`) for the discriminator field when the field is backed by a real `enum.Enum`, so the discriminator value matches the enum type used everywhere else in the same schema, and give every variant `model_config = ConfigDict(extra="forbid")` individually — it isn't inherited across a `Union`. See `app/schemas/measurement.py::MeasurementCreate`.
- When persisting a computed result that a client also supplied real input for (e.g. Phase 7's "save this measurement"), never trust a client-supplied result value directly — always recompute it server-side from the request's real input fields before writing to the database. The request schema shouldn't even have a field for the result; a client can otherwise persist a fabricated number that looks legitimate everywhere the app displays it later. See `app/services/measurement_service.py::create_measurement`/`_build_input_and_result`.
- Reuse the established pixel-center map-coordinate convention exactly (`transform * (cols + 0.5, rows + 0.5)`, from `geospatial/calibration.py`) any time you convert a pixel index to a real map coordinate elsewhere in this codebase — introducing a second, subtly different convention (e.g. rasterio's own `transform.xy()` helper, which defaults to the same pixel-center semantics but is a different code path) creates a real risk of an off-by-half-pixel mismatch between two parts of the system that are supposed to agree on where "pixel (r, c)" actually is. `geospatial/measurements.py` deliberately reuses the manual `transform * (...)` form for this reason, not `rasterio.transform.xy()`.
- Two real AI models in the same codebase don't need, and often shouldn't get, one unified interface. `ai/semantic_estimator.py`'s `SemanticEstimator`/`SemanticPrediction` is a deliberately separate interface from `ai/depth_estimator.py`'s `DepthEstimator`/`DepthPrediction` — one produces one continuous float array, the other a categorical label map plus a real per-region metadata list; forcing both through one shared "prediction" shape would mean either a lossy lowest-common-denominator type or a type with fields that are meaningless for one of the two models. `ai/registry.py` accordingly has two independent `lru_cache` singleton getters (`get_depth_estimator`, `get_semantic_estimator`), not one dispatcher — see `docs/ARCHITECTURE.md` §3.6 for the full rationale.
- A module-level constant needed by two sibling service modules can create a circular import if you pick the wrong home for it. Phase 8's `ELEVATION_ARTIFACT_TYPES`/`NOT_ELEVATION_ERROR` are needed by both `app/services/analysis_jobs.py` (job-creation validation) and `app/services/analysis_execution.py` (worker-time re-validation) — importing one from the other would cycle back through `app.jobs.tasks` (`analysis_jobs` → `app.jobs.tasks` → `analysis_execution` → back to `analysis_jobs`). The fix: put the shared constant in a third module neither of them already needs to cycle through (`app/services/disaster_pipeline.py`, which has no backend-side dependents of its own) and have both import from there. When two existing modules each need the same small piece of shared state, check the existing import graph before picking which one "owns" it — the natural-seeming choice (put it where it's used first) can silently reintroduce a cycle that only surfaces as `ImportError: cannot import name ... (most likely due to a circular import)` the first time both modules are imported in the same process.
- Not every new native-Postgres-enum column is the "add a member to an existing enum" case from the bullet above — Phase 8's `disaster_status` column is a genuinely **new** enum type on an **existing** table, which is the same "autogenerate handles it, but forgets the `downgrade()` drop" case as a brand-new table (two bullets up), not the silent-empty-migration case. Read what autogenerate actually produced before assuming which lesson applies; the two cases look similar in the model diff but need different manual fixes (a hand-written `ALTER TYPE ... ADD VALUE` for new *members* on an enum other columns already use, vs. a hand-written `sa.Enum(...).create()`/`.drop()` for a whole new enum type). See `alembic/versions/a4f198e31d97_add_disaster_screening_support.py`, which needed both fixes at once (a new `disaster_status` enum type, plus 7 new members appended to the existing `analysis_stage` enum).
- Not every job-outcome field needs the same soft/hard-failure semantics just because it looks like its siblings. `disaster_status` is modeled identically to `calibration_status`/`semantic_status` (same enum shape, same column pattern) but behaves differently on failure: calibration/segmentation are opt-in add-ons to an otherwise-independently-valid depth job, so their failure is soft (`status=FAILED` only for that sub-feature, the job as a whole still completes); a disaster-screening job has no other purpose, so its failure is hard (a real failure sets *both* `disaster_status=FAILED` and the whole job's `status=FAILED`). Don't assume a new status field copied from an existing pattern also copies that pattern's failure-isolation behavior — decide it from what the job is actually for.
- The "create" module / "execute" module split (`analysis_jobs.py` vs. `analysis_execution.py`, and now `report_service.py` vs. `report_execution.py`) isn't just stylistic — it's the fix for a real circular import that recurs any time a new job type is added: `app/jobs/tasks.py` must import the real pipeline function to hand RQ a stable reference, and the "create" module must import `app/jobs/tasks.py` to enqueue it. If the pipeline function instead lived in the same module as the "create" code, `app/jobs/tasks.py` importing it would cycle straight back. When adding a new RQ-backed job type, default to this same two-module split from the start rather than discovering the cycle at import time.
- Choosing a PDF library: prefer a pure-Python one (`reportlab`) over an HTML-to-PDF renderer (`weasyprint`, `wkhtmltopdf`) when a Docker image so far only needs `pip install` — the latter need real system libraries (Cairo/Pango or a headless browser) that would otherwise be the first non-Python system dependency this project's backend image needs. Reserve a test-only, independent parsing library (`pypdf`, used only in `tests/test_reports.py`) to verify generated PDF *content* — never assert PDF correctness by checking only "the generation function didn't raise" or "the byte count is non-zero"; a real assertion needs to actually re-open and read back what was produced, the same "independent validation" principle Phase 8's GDAL-container cross-check already established.
- Before assuming a feature gap needs new engineering, check whether the *generic* layer underneath an artificially-narrow gate already supports the general case — `geospatial/terrain_grid.py::extract_terrain_grid` (Phase 5) reads band 1 of whatever raster path it's given and was never actually specific to a calibrated DSM; the Phase 10 "relative terrain" feature turned out to be relaxing one `artifact_type != "dsm"` check in the service/API layer, not writing new mesh-extraction logic. Read the actual call chain (not just the docstring, which had said "DSM" without meaning it structurally) before estimating a fix's size.

## TypeScript / React (frontend)

- Formatting/linting: `prettier` + `eslint`.
- Components are typed; no `any` for API response shapes — define types matching backend Pydantic schemas.
- Data fetching centralized in an API client layer (`frontend/src/api/`) — components don't construct fetch calls inline.
- No component computes or fabricates an analysis value; it renders what the API returned. If a value isn't available yet (job still processing), show a loading/pending state, not a placeholder number.
- A plain `<img src="...">` cannot attach an `Authorization` header, so every authenticated raster (preview/window PNGs, the terrain grid) is fetched with `fetch()` carrying the real Bearer token, turned into a `Blob`/`ArrayBuffer`, and — for images — exposed as a browser object URL (see `hooks/useObjectUrlBlob.ts`). Never put a token in a query string as a workaround, and always revoke the previous object URL before creating a new one (and on unmount) — an easy leak when switching between datasets/layers.
- Three.js objects (`BufferGeometry`, `Material`, `Texture`, `WebGLRenderer`) are not garbage-collected like plain JS objects — each holds real GPU resources and must be explicitly `.dispose()`d, and the renderer's canvas explicitly removed from the DOM, in the same cleanup path that tears down the scene (component unmount, or the effect re-running for a new dataset/artifact). `components/terrain/TerrainView3D.tsx` is the reference for this pattern.
- A `useEffect` that needs "the latest callback prop" without re-running on every render (e.g. a Three.js event listener registered once at scene-setup time, referencing a prop that changes across renders) should read the callback through a `useRef` kept in sync via a plain assignment each render (`ref.current = callback`), not put the callback itself in the effect's dependency array — an inline arrow function prop is a new reference every render, which would otherwise tear down and rebuild the entire scene constantly.
- Two pieces of UI state that *look* related are not necessarily the same state: Phase 5's cursor-inspection feature originally keyed "which layer to sample a value from" off `activeLayer` (a layer panel selection changed only by clicking a layer's *name*), while the obvious, actually-used interaction for turning a layer on is its separate visibility checkbox. Since `activeLayer` defaulted to `"rgb"` and nothing ever prompted a user to also click a layer's name, clicking the map updated the displayed pixel coordinate (computed client-side, so it "looked like it worked") but silently never called the real `/value` endpoint — no error, no visible sign anything was wrong, just a feature that quietly did nothing. Fixed in `components/terrain/inspection.ts::pickInspectableLayer`, which falls back to the topmost *visible* scientific layer when the "active" one isn't actually shown. The general lesson: when a value is derived from one piece of state but the user only ever interacts with a different, adjacent piece of state, trace what the user actually clicks — not what the code assumes they clicked — before trusting that a "some UI text updated" observation means the whole feature path executed.
- A coordinate produced by one coordinate SYSTEM is not automatically valid input to a function expecting pixel indices in a DIFFERENT one — Phase 7's real bug (found during that phase's own readiness audit, fixed before any measurement feature was allowed to use 3D clicks): `TerrainView3D.tsx`'s raycast click produced a `(row, col)` in the *downsampled display terrain grid's* own coordinate space (capped at `MAX_TERRAIN_DIMENSION`, e.g. 256px), which was then passed directly to the full-resolution `/visualization/value` endpoint as if it were already a full-resolution pixel index. For any DSM larger than the display cap — the common case — this silently sampled the wrong pixel: a real, in-bounds value, just from the wrong location, with no error and no visible sign anything was wrong (the same "quietly does nothing correct" shape as the bug above, one layer deeper). The fix (`geospatial.measurements.coordinate_to_pixel`, `app/api/v1/endpoints/measurements.py::get_pixel_for_coordinate`) resolves the click's real local-CRS map coordinate against the artifact's own real full-resolution transform server-side, rather than rescaling a display-grid index client-side. The general lesson, one level more specific than the bullet above: whenever two parts of a system each have their own "pixel space" (a display-downsampled grid vs. the real stored raster), a raw index from one is never safe to hand directly to a function expecting the other — convert through a real, shared coordinate (map/world space), not through an assumed scale factor.
- A Docker Compose service that mounts a *named volume* over `node_modules` (`frontend_node_modules:/app/node_modules`, so the container's own installed packages survive across bind-mounting the rest of `frontend/` from the host) means `npm install <package>` run on the **host** only updates the host's `node_modules` and `package.json`/`package-lock.json` (the latter two are bind-mounted, so those changes ARE shared) — the container's own `node_modules` volume is untouched, and Vite inside the container will fail with "Failed to resolve import" for the new package until you also run `npm install` **inside the container** (`docker compose exec frontend npm install`). Always install a new frontend dependency in both places (or just run the install inside the container, since `package.json`/`package-lock.json` changes propagate back to the host through the bind mount either way).

## API conventions

- All routes versioned under `/api/v1/...`.
- Consistent error envelope: `{ "error": { "code": ..., "message": ... } }`.
- Auth via `Authorization: Bearer <JWT>`; protected routes use a shared FastAPI dependency, not per-route ad hoc checks.
- Pagination on list endpoints (`limit`/`offset` or cursor) from the start — no unbounded `SELECT *`.

## Logging & error handling

- Structured JSON logs (request ID, user ID where applicable, job ID for pipeline stages).
- Exceptions mapped to typed domain errors (`DatasetValidationError`, `CalibrationError`, etc.) at the point they occur; a single exception handler translates them to the API error envelope. No bare `except Exception: pass`.
- Job failures persist the real error (stage + message) to `analysis_jobs` — never silently mark a failed job as complete.

## Secrets & configuration

- All config via environment variables, loaded through a single settings module (`pydantic-settings` in the backend). `.env.example` committed, `.env` gitignored.
- No secrets, credentials, or API keys committed, ever.

## Testing

- Backend: `pytest` (run as `python -m pytest` — see above), with a real (containerized) PostgreSQL/PostGIS for integration tests — no mocking the database for tests that verify persistence/query correctness. File upload/dataset tests likewise exercise the real `LocalStorageBackend` and real rasterio/GDAL parsing — no mocking the storage layer or the raster-validity check. `tests/fixtures.py` generates real JPEG/PNG/GeoTIFF bytes at test time (Pillow / rasterio `MemoryFile`) rather than committing binary fixture files; an autouse `conftest.py` fixture wipes the `projects/` storage prefix and the `analysis_artifacts`/`analysis_jobs`/`datasets`/`projects`/`users` tables after every test so runs stay isolated from each other and from manual local testing against the same dev storage root.
- Analysis job tests (`tests/test_analysis.py`) exercise the *actual* separate worker container over *actual* Redis/RQ for the happy path and the missing-file failure path — the test creates a job via the real HTTP API and polls the real API until the real worker (running continuously alongside the test suite under `docker compose`) finishes it. One test (the generic-exception branch) monkeypatches `extract_raster_metadata` and calls `execute_analysis_job` directly in-process instead, because reliably triggering a bare, non-domain exception through the real worker process isn't practical from a test; that job row is inserted directly and never enqueued, so there's no race with the real worker over it. Don't mock the job lifecycle (status transitions, the queue, the database) itself — only ever mock the one internal call needed to force a specific, otherwise-hard-to-reach branch, and say so in the test's docstring.
- AI / depth pipeline (`tests/test_depth_pipeline.py`, Phase 3): the input-eligibility policy (`extract_rgb_uint8`) is unit-tested directly with synthetic in-memory arrays, no model involved — fast and exhaustive over band-count/dtype combinations. Everything else — a structured RGB scene actually producing non-constant output, georeferencing carrying through correctly, artifact metadata being real, the full artifact-download API — goes through the real HTTP API, the real separate worker, and the real downloaded model; **do not mock inference to make these pass**. The one place a fake `DepthEstimator` is used is the two cancellation-timing tests, where precise control over *when* `predict()` "runs" relative to a cancellation is the entire point and racing the real model's variable timing wouldn't give reliable enough control — even there, the fake implements the same interface real code calls, so the pipeline logic under test is unmocked. `tests/fixtures.py::make_structured_scene_*` generates a small synthetic-but-structured RGB scene (gradient sky + ground band + a foreground disc) specifically because a real depth model needs actual spatial structure to produce a genuinely non-constant prediction — a flat color block (fine for Phase 1/2's metadata-only tests) or pure random noise (no coherent structure to key off) would not meaningfully exercise "does inference produce real, varying output."
- A model call that's meant to be *slow-but-safe* to race in a test (e.g. simulating "cancelled while this call is in flight") can't actually be interleaved with a sibling `asyncio` task if the call itself is a blocking, synchronous `time.sleep()`-style operation (which real inference is) — it monopolizes the single event loop for its duration, starving any concurrently-`gather`'d coroutine's own `asyncio.sleep()` from ever getting a chance to run *during* that window. `test_cancellation_during_inference_does_not_produce_completed` in `test_depth_pipeline.py` works around this by having the fake estimator's `predict()` perform the cancellation itself, synchronously, via a genuinely separate database connection (a plain `sqlalchemy.create_engine(DATABASE_URL_SYNC)`), which models "an external process cancelled this job while inference was running" deterministically instead of guessing at a sleep duration that happens to interleave correctly.
- Geospatial: tests assert against known reference rasters/CRS transforms with tolerances, using real GDAL/rasterio calls.
- Metric calibration (`tests/test_calibration.py`, Phase 4): the pure math in `geospatial/calibration.py` (sampling, robust fitting, validation metrics) is unit-tested directly with synthetic arrays — including a deterministic case with a **known** `a`/`b` (`Z = a·D + b` computed exactly, no noise) that the fit must recover to floating-point tolerance, and a second case with injected outliers verifying they're actually excluded from the final inlier set, not just diluted. Everything past that — DEM/GCP upload validation, attaching a reference to a job, the full worker-driven calibration → metric elevation → DSM pipeline, provenance-chain metadata, cross-user access denial, the non-georeferenced-source failure path — goes through the real HTTP API, real database, and the real separate worker container; **do not mock calibration, sampling, or raster I/O in these tests**. `tests/fixtures.py::make_dem_geotiff_bytes`/`make_gcp_csv_bytes`/`make_structured_scene_geotiff_bytes` (with matching `origin_x`/`origin_y`/`pixel_size` overrides) share one real-world UTM footprint so a source image + DEM + GCP CSV genuinely overlap in a test — a mismatched footprint (e.g. default GCP points defined outside a smaller test image's extent) fails realistically with "insufficient valid samples," which is correct behavior but not what the test intended, so keep footprints deliberately aligned when adding new fixtures rather than debugging why real sampling found too few points.
- Visualization (`tests/test_visualization.py`, Phase 5): ownership/authentication, real raster metadata/preview/window generation (asserted by actually decoding the returned PNG with Pillow and checking its real dimensions, not just HTTP 200), and terrain-grid extraction are covered directly against `geospatial/raster_preview.py`/`terrain_grid.py` and via the real HTTP API. One test reuses a single real end-to-end DEM-calibrated job (real model, real worker) across several assertions (context, metadata, preview, and terrain-grid-vs-independently-downloaded-DSM byte comparison) specifically to avoid re-running real inference more than once; a handful of others insert an `AnalysisJob`/`AnalysisArtifact` row directly with a real raster file written to the real storage backend (same technique as `tests/test_analysis.py`) to test a specific branch (terrain-requires-dsm, corrupted raster, missing file, downsampling-respects-max-dimension) deterministically without needing the model at all — never mock the raster reader itself. Never assume a `Depends(get_settings)`-injected value can be swapped with `monkeypatch.setattr` on the module — see the Python section above.
- Semantic segmentation (`tests/test_semantic_segmentation.py`, Phase 6): the deterministic overlap/sort/rasterization policy in `MobileSAMEstimator.predict` is unit-tested by constructing the estimator directly and assigning a fake `_mask_generator` (a plain object with a `.generate()` method returning fixed, known mask dicts) — this exercises the *real* policy code with full control over mask geometry/area/overlap, without needing real weights or the real ~45s forward pass. Checkpoint download/verification failure modes (no network, hash mismatch) are tested by monkeypatching `ai.mobile_sam.urllib.request.urlopen`/`_cache_dir`, not by actually simulating a network outage. Exactly one test (`test_real_mobilesam_inference_produces_real_categorical_artifact`) runs genuine end-to-end MobileSAM inference through the real API + real worker + real weights and independently re-opens the downloaded artifact with `rasterio` to confirm dtype/nodata/dimensions/region IDs match the job's own reported metadata — **never mock the segmentation result itself** in a test that's supposed to verify segmentation works; fakes are only for testing orchestration (cancellation timing, soft-failure handling) around a call that's swapped out at the `analysis_execution.run_semantic_segmentation` name (mirroring how depth-pipeline cancellation tests swap `get_depth_estimator`), not the rasterization/model-loading code itself. The categorical visualization endpoints reuse `test_visualization.py`'s direct-row-insertion technique (a real `uint32` GeoTIFF written straight to the storage backend) so metadata/preview/value/ownership behavior can be asserted without waiting on real inference for every case.
- Measurements (`tests/test_measurements.py`, Phase 7): the pure geospatial math (`geospatial/measurements.py`) is unit-tested against synthetic rasters with KNOWN values/CRS/transforms written directly with `rasterio` in a pytest `tmp_path` — a projected-CRS distance check against an exact expected metre value, a geographic-CRS distance check cross-verified against an independently-computed haversine distance (proof degrees were never treated as metres), a linear-gradient raster whose exact expected value at every profile sample is computable in the test itself, and a real single-pixel "spike" in an otherwise-flat 300×300 raster used specifically to prove the profile sampler reads full resolution (a value that decimation would have averaged away). The 3D-terrain coordinate-space bug fix has dedicated regression tests that replicate exactly what `TerrainView3D.tsx` now does — extract a real (possibly downsampled) terrain grid, compute the real map coordinate of one of its own cells, resolve that back to a full-resolution pixel — over a 2048×2048 square raster, a 2048×1024 non-square one, all four corners, the center point, and an out-of-bounds map coordinate. API-level tests reuse `test_visualization.py`'s direct-row-insertion technique (a real float32 GeoTIFF written straight to the storage backend, referenced by a directly-inserted `AnalysisJob`/`AnalysisArtifact` row) for fast, deterministic ownership/CRUD/calibration-gating coverage, plus exactly one real end-to-end test through the actual API with a real depth-model job and real DEM calibration. One easy mistake worth flagging: helper functions that return a raw SQLAlchemy-assigned `uuid.UUID` (e.g. `job.id` right after `db.add`/`commit`) will raise `TypeError: Object of type UUID is not JSON serializable` the moment a test tries to put that value into an httpx `json=` request body — convert to `str(...)` at the point the ID leaves the helper, not at every call site.
- Frontend: component tests with Vitest/React Testing Library; no snapshot tests of values that originate from the backend (those are covered by backend tests + integration tests instead). Phase 5's Leaflet/Three.js components are verified via `tsc --noEmit`, `eslint`, a production `vite build`, and manual/API-level verification instead of component tests — mounting a real Leaflet map or a WebGL-backed Three.js scene in a jsdom test environment needs a much heavier test setup (canvas/WebGL shims) than this project's current Vitest config provides, and the actual rendering correctness (real bounds, real DSM values) is what the backend's own tests and manual E2E already verify independently. Phase 7's Recharts-based `ProfileChart.tsx` follows the same pattern (verified via type-check/build/manual API-level checks, not a mounted-component test) for the same reason.
- When a component's file has heavy, browser-only top-level imports (Leaflet, Three.js) that would load — and likely throw, with no jsdom environment configured — the instant any test file imports that component, extract the actual logic under test into its own small module with no such imports (see `components/terrain/inspection.ts`, extracted from `TerrainWorkspace.tsx`) rather than reaching for a jsdom/canvas-shim dependency just to make the import resolve. `components/terrain/inspection.test.ts` runs under Vitest's plain default (Node) environment because it imports only `inspection.ts`, never `TerrainWorkspace.tsx`/`MapView2D.tsx`/`TerrainView3D.tsx` directly.
- Terrain derivatives (`tests/test_disaster_screening.py`, Phase 8): the pure geospatial math (`geospatial/terrain_derivatives.py`) is unit-tested against synthetic rasters with KNOWN elevation values written directly with `rasterio` in a pytest `tmp_path` — an exact tilted-plane slope check against an independently-computed `atan(hypot(dz/dx, dz/dy))`, three independent directional aspect cases (each hand-verified against the module's own documented ESRI/Horn compass-bearing formula), explicit NoData-propagation checks (a single NoData pixel must blank its own full 3×3 neighborhood in the output, not just itself), and exact classification-boundary checks for both flood screening (`elevation <= water_level` inclusive) and landslide screening (each threshold's `>=`/`<` edge). The full standalone-job lifecycle (creation validation, ownership/cross-project rejection, real worker execution via `analysis_execution.execute_analysis_job`, real artifact/legend persistence, and the soft-vs-hard failure distinction from the bullet above) goes through the real HTTP API and a real completed "parent" job/DSM artifact inserted directly (same direct-row-insertion technique `test_visualization.py`/`test_measurements.py` already use) — never mock the terrain-derivative computation itself in a test meant to verify it works.
- Reports (`tests/test_reports.py`, Phase 9): the pure data assembly (`report_builder.py`) is unit-tested by constructing real `Project`/`Dataset`/`AnalysisJob` model instances directly in Python (never persisted — these are pure attribute containers here, not database rows) and asserting the exact resulting dict shape/values, including that an uncalibrated/no-disaster-job case renders its honest "not available" note rather than omitting the section silently. The pure renderers (`report_render.py`) are tested by independently re-parsing their own output — `pypdf.PdfReader` to extract and assert against real PDF text (never just checking the byte count or magic bytes alone), and the stdlib `zipfile` module to open the real generated ZIP bundle and verify its exact real contents (including that a genuinely-missing artifact file produces a `MISSING.txt` manifest entry, not a silently-shorter archive). Exactly one test (`test_real_e2e_report_reflects_actual_pipeline_outputs`) runs a genuine end-to-end pipeline — real DEM calibration, real Phase 8 disaster screening, real report generation — with only the depth *model* faked for speed (the same established `_FastFakeDepthEstimator` technique `test_semantic_segmentation.py` already uses), then asserts the report's own numbers match the pipeline's own real, independently-fetched results exactly (e.g. the report's flood pixel count equals the disaster job's own `disaster_metadata` value) — never mocking the report's actual content.
- Relative terrain (`tests/test_visualization.py`, Phase 10): before writing any code, the actual `extract_terrain_grid`/`get_terrain` call chain was traced to confirm it was already artifact-type-agnostic — the fix was relaxing a gate, not building new extraction logic, and the tests reflect exactly that scope. Direct-row-insertion tests (matching this file's own established convention) cover the real fallback (`dsm` missing but `relative_depth` present → `height_kind="relative_depth"`, real min/max height values, `min_elevation`/`max_elevation` left `None`), the non-georeferenced case (`crs`/`bounds` genuinely `null`, never fabricated), the calibration-*failed*-not-just-*never-requested* case (falls back the same way — a failed attempt must not be treated differently from no attempt), the true-unavailable case (neither artifact exists), and a regression assertion on the existing real end-to-end calibrated-DSM test (`height_kind="elevation"`, `min_elevation`/`max_elevation` populated, unchanged shape). One easy mistake caught during this phase: a direct-row-inserted test artifact with no `artifact_metadata` dict at all silently reads back as `is_georeferenced=None` (not `False`) via `_artifact_layer`'s `metadata.get(...)` — a real `None` vs `False` distinction, not a bug in the feature under test; the fix was giving the test fixture a realistic metadata dict, matching what a genuine relative_depth artifact actually persists, rather than weakening the assertion.
- Real browser acceptance testing found two genuine defects that a full API-level test suite structurally could not: a `frontend/e2e/phase10-terrain.spec.ts` Playwright spec (minimal `@playwright/test` setup added for exactly this — see `frontend/playwright.config.ts`; it drives the actual running app at `localhost:5173`/`:8000`, no mocking) caught (1) the RGB-texture-loading `useEffect` in `TerrainView3D.tsx` depending on `[showTexture, compatibleTextureBlob]` only — since the Three.js scene is built asynchronously in a *separate* effect, this effect's first (synchronous, pre-scene) run always no-oped via `if (!s) return`, and nothing ever re-triggered it, so the real RGB texture silently never appeared on initial load for *either* the calibrated or relative-depth path (it fell back to plain vertex coloring, visually plausible enough that this had never been noticed) — fixed by adding `loading` to that effect's dependency array; (2) the "Click to enter flythrough mode" hint overlay reading Three's own non-reactive `pointerLock.isLocked` directly in JSX, so it never disappeared after a real, successful pointer lock — a 50%-opacity black overlay permanently dimmed the entire first-person view for the rest of the session — fixed by mirroring real `lock`/`unlock` events into actual React state (`isPointerLocked`) instead. Lesson: a component that reads a third-party library's mutable internal state directly inside JSX (`someRef.current.libraryObject.someFlag`) will silently never react to that flag changing, since mutation alone never triggers a re-render — the flag must be mirrored into real `useState`, updated from that library's own real change events. Neither defect was reachable from a pure API/schema-level test; both needed an actual rendered browser to surface.
- Reliability hardening (`tests/test_analysis.py`, `tests/test_job_reconciliation.py`, Phase 11): widening `cancel_job` to accept a `running` job (not just `queued`) surfaced a *second*, symmetric race the queued-only design never had to consider — a job's own completion/failure write-paths were previously unconditional ORM commits, so a cancellation landing in the narrow window between a job's last checkpoint and its final write could be silently clobbered back to `completed`/`failed`. Both paths were made conditional (`WHERE status='running'`), mirroring the claim step's own pre-existing atomic-UPDATE pattern; `test_cancellation_race_with_completion_leaves_exactly_one_final_state` proves it with a real forced race (a stubbed, deliberately slow `_run_stages`, never a mocked completion/cancel code path). Proving a real cancel HTTP request lands *while a genuinely blocking `predict()`-style call is in flight* cannot be done with a sibling `asyncio` task on the same event loop — a synchronous `time.sleep()` inside one task starves every other task's own `await`, exactly like the Phase 3 lesson above, but this time the workaround needs the *opposite* trick: since the thing under test is a real concurrent HTTP request (not something the fake can trigger itself), `execute_analysis_job` was run in a genuinely separate OS thread (`asyncio.to_thread` + its own `asyncio.run(...)`) so the main event loop stays free to actually send that request — this works safely with this project's async DB engine specifically because `app/db/session.py` uses `NullPool` (a fresh connection per checkout, never cached across event loops). Stale-job reconciliation (`app/services/job_reconciliation.py`) is tested by directly backdating `updated_at` (a real column already advanced by every real stage-transition commit — no fake heartbeat needed) rather than waiting out the real ~20-minute staleness window. The real Docker crash verification for this phase also surfaced an environment-specific gotcha worth knowing: `uvicorn --reload` did not reliably pick up backend file changes over this project's Windows/Docker Desktop bind mount in manual (non-pytest) testing — pytest itself is unaffected (each run imports the app fresh in its own process), but verifying a live code change against the already-running dev server needs an explicit `docker compose restart backend`, the same class of issue the frontend's Vite config already works around with `watch.usePolling`.

## Git conventions

- `main` is always deployable.
- Feature branches per unit of work; PRs required before merging to `main` once collaborators are involved.
- Commit messages: short imperative summary line, body explains *why* when non-obvious.
- Migrations, and any schema-affecting change, called out explicitly in the PR description.

## Definition of done (per feature)

1. Real data flows end-to-end (no stub/mock standing in for a core-pipeline step).
2. Errors are handled and surfaced, not swallowed.
3. Covered by at least one automated test exercising the real path (DB/AI/GDAL, not a mock of it) where feasible.
4. Documented in code only where the *why* isn't obvious from reading it.
